## レビューの進め方

レビューは「確認しました」で終わらせない。**指摘を ID 付きで `work/review-log.md` に記録し、全件が「修正済」または「逸脱承認済」になるまで完了としない。** `scripts/check_traceability.py` に `--review-log` を渡すと、P3 のゲートで `open` の残りを検出する。

### 自己レビューの当て方

自分の成果物を自分で評価すると必ず甘くなる。次の形で当てる。

> **これは他人が書いたものである。** 下のチェックリストに照らして、**不合格な箇所を列挙する**。問題がないことを確認するのではなく、問題を探す。

「特に問題ありません」で終わったレビューは、レビューをしていないのと同じ。1周につき最低限、**チェックリストの各項目に対して「どこを見てそう判断したか」を1行で書ける状態**にする。

### 記録の形式

`assets/templates/review-log.md` をコピーして `work/review-log.md` を作る。1指摘1行。

| 列 | 内容 |
|---|---|
| ID | `RV-<連番3桁>`。振り直さない |
| フェーズ | `P1` / `P2` / `P3` |
| 対象 | ファイル名、関数 id など |
| 指摘 | 何が不合格か。「わかりにくい」ではなく、どの基準にどう反しているか |
| 重大度 | `高`（仕様・安全性に影響）/ `中`（保守性）/ `低`（表記） |
| 状態 | `open` / `fixed` / `accepted` |
| 対応/理由 | `fixed` なら何をしたか。`accepted` なら**なぜ直さないでよいか** |

- `accepted`（逸脱承認）にできるのは**ユーザーの了承を得たときだけ**。自分で承認しない
- 重大度「高」を `accepted` にする場合は、その場でユーザーに個別に提示する
- 指摘ゼロだった場合も、**当てたチェックリスト名と結論を1行残す**（`RV-000 / P1 / 全体 / 指摘なし / — / fixed / チェックリスト1を全項目適用`）

### ユーザーへの提示

各レビューの最後に、次を提示して確認を得る。

```
★P1 関数設計レビュー
  指摘 4件（高 1 / 中 2 / 低 1）
  - RV-001 [高] MotorController::Shutdown : @retval が false のみで、成功時の戻り値が未定義
  - RV-002 [中] MotorController::Update   : @pre がない。Initialize 前提かどうか読み取れない
  ...
  RV-001 は設計側で決める必要があります。判断をお願いします。
```

## 1. 関数設計レビュー（P1）

Doxygen が**仕様として成立しているか**を見る。ここが緩いと、実装も後工程の単体テスト設計も推測で進むことになる。基準は「この記述だけを見て単体テストケースを導出できるか」。

### 仕様としての完全性

- [ ] `@brief` が「何をするか」を言い切っているか（「〜を処理する」のような無内容な記述になっていないか）
- [ ] `@retval` が戻り値の**全パターン**を網羅しているか。成功側だけ書かれていないか
- [ ] `@retval` の各行に**その値が返る成立条件**が書かれているか。同じ値でも成立条件が違えば行が分かれているか
- [ ] `@sideeffect` が全関数にあるか。メンバ変数・グローバル状態の変化が漏れなく書かれているか。変化が無い関数に「なし」と書かれているか
- [ ] `@sideeffect` の内容が観測可能か（変化した状態を getter 等で読み出せるか。読み出せないなら観測手段を設計に足す提案をする）
- [ ] 全 public 関数に `@pre` があるか。事前条件が無い場合も「なし」と書いてあるか
- [ ] `@pre` を**満たさずに呼んだときの振る舞い**が書かれているか（これが無いと異常系のテストが書けない）
- [ ] 引数に有効範囲がある場合、`@param` に範囲が書かれているか（境界値テストの根拠になる）
- [ ] 出力引数の値が、失敗時にどうなるか書かれているか（変更しない / 未定義 / 既定値）
- [ ] 単位のある値（時間、回転数、電圧）に単位が書かれているか

### 設計との一致

- [ ] `work/design-index.json` にある関数がすべて宣言されているか
- [ ] 設計に無い関数・クラスを勝手に足していないか
- [ ] 型が設計と一致しているか。`unknown` を勝手に埋めていないか

### 実装可能性・テスト容易性

- [ ] 依存が注入されているか。具象型を関数内で直接生成していないか（生成していると後工程でモック化できない）
- [ ] モック対象がインタフェース（またはテンプレートパラメータ）を介しているか
- [ ] `@pre` の条件を、テストコードから作り出せるか（時刻・ハードウェア依存が直書きされていないか）

### 規約

- [ ] `references/autosar-cert-rules.md` の「型と変換」「クラス設計」「関数」の方針に反していないか
- [ ] 逸脱がある場合、理由が `@note` に書かれているか

## 2. コードレビュー（P2）

実装が**Doxygen の仕様どおりか**を見る。仕様と実装がずれていたら、直すのは実装側。

- [ ] `work/design-index.json` と Doxygen の仕様どおりに実装されているか
- [ ] `@retval` の各行（値と成立条件）が実装の分岐と一致しているか。仕様に無い戻り値を返す経路、仕様にあるのに実装されていない条件が無いか
- [ ] `@sideeffect` に書かれた状態変化だけを行っているか。書かれていない状態変化（隠れた副作用）が実装に入り込んでいないか
- [ ] Doxygen コメントを実装に合わせて書き換えていないか（P2 以降の書き換えは禁止。仕様を変えるなら P1 に戻る）
- [ ] `TODO` と、P1 の暫定措置（未使用引数の `static_cast<void>` 抑止）が残っていないか
- [ ] `references/autosar-cert-rules.md` のセルフチェック表を当てたか
- [ ] エラー経路が「握りつぶし」になっていないか（戻り値を無視していないか）
- [ ] 同じ処理の重複が無いか
- [ ] 1関数の責務が1つか
- [ ] マジックナンバーが定数化されているか
- [ ] 命名が設計の用語と一致しているか（設計は「目標回転数」なのにコードが `val` になっていないか）
- [ ] 警告0でビルドが通っているか（抑止オプションで消していないか）
- [ ] 静的解析ツールがある場合、実行して指摘を確認したか

## 3. 最終レビュー（P3）

ユーザーの受け入れ判定を得る工程。次を提示する。**都合の悪い項目を省かない。**

- [ ] 実装したクラス・関数の件数（設計の件数と一致しているか）
- [ ] `scripts/check_traceability.py` の結果（終了コードと指摘）
- [ ] レビュー指摘の総数と内訳（`fixed` / `accepted`）。`accepted` は**全件を理由付きで列挙する**
- [ ] `references/autosar-cert-rules.md` のセルフチェック表の結果
- [ ] 静的解析の結果（実施した場合）。していない場合は「ツールなし」と明記
- [ ] ユーザー確認を残した事項（設計の矛盾、判断を仰いだ点）
- [ ] 未達・未実施の項目（**達成したかのように書かない**）

`open` の指摘が1件でも残っている、`check_traceability.py` が 0 を返さない — このいずれかがあれば**完了として報告しない**。残課題として明示する。
