# 関数設計（Doxygen + クラスと関数の箱）

P1 で読む。ここで書く Doxygen コメントが**関数仕様の唯一の出典**になる。後続の実装と、別スキルで行う単体テスト設計はすべてこの記述を参照するので、実装で決めるべきことをここで先に決め切る。

品質基準は「**この記述だけを見て単体テストケースを導出できること**」。関数単位の入力条件・戻り値・異常時の振る舞い・内部状態変化が Doxygen に書かれていないと、後工程の単体テスト設計が実装を正にしてしまう。「実装を書けば決まる」で先送りした事項は、テスト設計の段で必ず詰まる。

## この工程で作るもの

1. クラスごとのヘッダ（`.h`）— 全関数の宣言 + Doxygen コメント
2. 対応する `.cpp` — **空実装**。中身は書かない
3. ビルド構成（CMakeLists.txt）— 空実装のままビルドが通る状態

「空実装のままビルドを通す」のが重要な理由: この時点で型・インクルード・依存関係の破綻がすべて出る。実装を書いてからだと、ビルドエラーが実装の誤りなのか宣言の誤りなのか切り分けられなくなる。

## Doxygen の必須タグ

`scripts/validate_doxygen.py` が機械的に検査する。

| タグ | 必須条件 |
|---|---|
| `@brief` | 全関数 |
| `@param[in]` / `@param[out]` / `@param[in,out]` | 引数の数だけ。方向指定を必ず付ける |
| `@retval` または `@return` | 戻り値型が `void` 以外の全関数 |
| `@sideeffect` | 全関数。副作用（メンバ変数・グローバル状態の変化）を書く。**無い場合も「なし」と明記する** |

使い分け: 戻り値が状態を表す（`bool`、エラーコード）関数は `@retval` を**値ごとに列挙し、その値が返る成立条件を併記する**。同じ値が複数の条件で返るなら、条件ごとに `@retval` 行を分ける。テスト設計の異常系はここから直接起こす。値そのものを返す関数（getter 等）は `@return` に意味を書く。

`@sideeffect` は標準の Doxygen タグではない。ドキュメント生成する場合は Doxyfile に次の ALIASES を定義する（未定義でも警告付きで無視されるだけで、ビルドは壊れない）。

```
ALIASES += sideeffect="\par 副作用:^^"
```

検査対象外だが、**書かないと後工程が推測を始めるので必ず書く**もの:

| タグ | 内容 |
|---|---|
| `@pre` | 事前条件。「この関数を呼ぶ前に Init() が成功していること」など。シーケンス図の呼び出し順から起こす |
| `@post` | 事後条件。呼び出し後に保証される状態 |
| `@note` | 設計上の制約、AUTOSAR / CERT ルールに対する逸脱とその理由 |

### 記述例

```cpp
/**
 * @brief ReadData 要求を処理する。
 *
 * @param[in]  req  要求情報。
 * @param[out] resp 応答情報。失敗時は変更しない。
 *
 * @retval E_OK
 *   正常応答の生成が完了した。
 * @retval E_NOT_OK
 *   req == nullptr のため処理しなかった。
 * @retval E_NOT_OK
 *   RAM 診断に失敗した。
 *
 * @sideeffect
 *   失敗時、m_state を ERROR に更新する。
 *
 * @pre Initialize() が E_OK を返していること。
 */
Std_ReturnType ProcessReadData(const ReadDataReq* req, ReadDataResp& resp) noexcept;
```

同じ `E_NOT_OK` でも成立条件が違えば行を分ける。この1行1条件が、そのまま異常系テストケースの一覧になる。

## 空実装の書き方

戻り値型ごとに、設計上の「失敗側の既定値」を返す。`TODO` コメントを必ず残す（P2 の完了条件がこれの消滅）。

空実装は**ビルド確認と設計レビューの土台**である。この段階で「とりあえず動く実装」を書いてはいけない。実装を書き始めると、レビューの対象が仕様（Doxygen）から実装に移ってしまい、仕様の不備が実装の都合で上書きされる。

```cpp
bool MotorController::SetSpeed(std::int32_t speed) noexcept
{
    static_cast<void>(speed);  // 未使用引数の警告を抑止する（P2 で削除する）
    // TODO: P2 で実装
    return false;
}
```

`static_cast<void>` による抑止は**P1 限定**の措置で、P2 で実装を入れるときに必ず消す。`(void)speed` ではなく `static_cast<void>` を使うのは C スタイルキャストを禁じるルールに合わせるため。

## ヘッダの構成

`assets/templates/header-template.h` の順序を守る。

1. インクルードガード（`#pragma once` ではなく、`<プロジェクト>_<パス>_<ファイル名>_H_` 形式のマクロ）
2. ファイル Doxygen（`@file` / `@brief`）
3. 標準ヘッダ → 外部ライブラリ → プロジェクト内ヘッダ の順の `#include`
4. 名前空間
5. クラス宣言（public → protected → private）

## 型の選び方

| 場面 | 使うもの |
|---|---|
| 整数 | `<cstdint>` の固定幅型（`std::int32_t` 等）。素の `int` / `long` を使わない |
| 真偽 | `bool` |
| 参照渡し（読み取りのみ） | `const T&` |
| 出力引数 | `T&`（ポインタより参照を優先。null 検査が不要になる） |
| 所有権のない参照 | 生ポインタまたは参照。スマートポインタは所有権があるときだけ |

設計側の型が `unknown` のまま残っている場合、この工程で決めてはいけない。P0 に戻ってユーザーに確認する。

## 依存の持ち方（テスト容易性）

後工程の単体テストで依存をモックに差し替えられるかどうかは、この工程の設計で決まる。**後から直すと実装のやり直しになる**ので、ここで決める。

- 他クラスへの依存は、具象型を直接 `new` せず、**コンストラクタで受け取る**（依存注入）
- モック対象になる依存は、純粋仮想のインタフェースクラスを介する
- 仮想関数を禁止している構成では、テンプレートパラメータで依存を差し替える方式にする

設計（クラス図）が具象クラスへの直接依存になっている場合、インタフェースを勝手に挿入しない。**依存注入に変える必要があることをユーザーに提示し、確認を得てから**行う。

## この工程のゲート

```
python scripts/validate_doxygen.py <ヘッダのパス>
```

終了コード 0（ERROR 0件）かつ、空実装のままビルドが警告0で通ること。両方を満たし、`references/review-gates.md` の「1. 関数設計レビュー」を当てて指摘を `work/review-log.md` に記録し、ユーザーの確認を得るまで P2 に進まない。
