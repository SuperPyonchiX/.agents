# Markdown 文書作成スキル

業務用の Markdown 文書を5種別の定型で作る。仕事の中心は**種別を1つに決めること**で、決まった後の手順は種別ごとの参照ファイルにある。種別を取り違えると読者に合わない文書になるので、迷ったら1問だけ聞いて確定させる。

## 種別の判定

**読者に何をさせたいか**と**主語が誰か**で決める。

| 依頼の主眼 | 種別 | 読む参照ファイル | 例 |
|---|---|---|---|
| 読者に**理解**させる（概念・仕組み・制度・背景・設計思想） | 説明資料 | `references/explanation.md` | 「スクラムの考え方をまとめて」「認証基盤の仕組みを説明して」 |
| 読者に**作業を再現**させる（操作・コマンド・設定を順に実行させる） | 手順書 | `references/procedure.md` | 「VPN接続のやり方をまとめて」「デプロイ手順を書いて」 |
| **ツール・スキル・仕組みを紹介**し、導入から使い方・カスタマイズまで1本で完結させる | README 型 | `references/readme.md` | 「このスキルの説明を書いて」「README を書いて」「ツールの紹介資料を作って」 |
| **自分が実際にやったAI活用**を再現可能に残す | AIノウハウ記録 | `references/ai-knowhow.md` | 「今のやり方をノウハウに残して」「さっきの進め方を記録して」 |
| **原因が特定済みの不具合**（実害の無い未遂を含む）を標準章立てで報告する | 不具合報告書 | `references/defect-report.md` | 「不具合報告書を書いて」「この解析結果を報告書にして」 |

- 「まとめて」「ドキュメント化して」は説明資料と手順書の両方に取れる。**どちらが目的か1問だけ聞く。** 答えが得られなければ説明資料として進め、その旨を明示する
- 理解と再現の両方が必要なら1本にまとめず、**2本に分けて相互リンクする**。両方を1本に書くとどちらの読者にも読みにくい。ただし対象が特定のツール・スキルで、読者がそれを導入して使う人なら README 型で1本にする
- 原因が未特定の不具合は不具合報告書の対象外。原因究明（C/C++ なら cpp14-defect-analysis）が先だと伝えて止まる
- 会話中にその場で図を1枚出すだけなら、このスキルは使わず会話の中で示す

**完了条件**: 種別が1つに決まり、対応する参照ファイルを読んだこと。読む前に文書を書き始めない。

## 全種別に共通するルール

参照ファイルの手順に加えて、次を守る。

- **文書タイトルの見出しを付けない。** ファイル名で判別できる。文書は最初のセクション見出しから始める
- **常体（である調）で書く。** 「です・ます」は使わない
- **確認していないことを断定しない。** インプット資料・ヒアリング・実行結果のいずれかに基づかない数値・日付・固有名詞・コマンド・パスを書かない。確認できないまま残す箇所は未確認であることを文書上に明示する
- **環境構築は読者の手数を最小にする。** 理想はコピーして1回貼れば済むコマンドブロック（またはセットアップスクリプトの1行呼び出し）。ただし何を入れるのかが読めるよう、「必要なもの／用途」の表を先に置き、コマンドの各行に何を入れるかのコメントを付け、最後に完了確認のコマンドを置く。管理者権限・GUI でしか入れられないなど1発にできない部分は、理由を書いて分ける。1発にするにはスクリプトの新設が要るなら、文書で取り繕わずユーザーに作成を提案する
- **プレースホルダーは角括弧**（`[対象サーバー]`）。山括弧は HTML タグとして消える掲載先がある
- **リンクは通常の Markdown リンク記法**。`[[記事名]]` の wikilink は Confluence や GitLab Wiki で機能しない
- **すでに会話に出ている項目は質問しない。** 会話から抽出して「〇〇と理解した」と確認提示し、足りない項目だけを聞く。1ターンの質問は最大3つ
- **提示前に `japanese-prose-polish` を当てる。** 説明資料・手順書・README 型・不具合報告書は業務文書モード、AIノウハウ記録は個人発信モード。見出し体系・コードブロック・mermaid のラベル・引用したやり取りは書き換え対象外として渡す
- **mermaid 図を置いたら、提示前に `scripts/check_mermaid.py` を通す。** 線が箱を突き抜ける・ラベルに線が乗る・無関係のサブグラフを横切る、といった崩れはソースを読んでも分からない。ERROR が 0 になるまで直し、WARN（交差・遠回り・かすめ）は直せるものだけ直す。直し方と周回の上限は「スクリプト」節
- **完成品ではなくドラフトとして提示する。** 修正依頼への対応は上限3周。収束しなければ食い違いを整理して方針を確認する

## ユーザーから指摘を受けたとき

ドラフトへの修正依頼のうち、**次の文書でも同じ直しが要りそうなもの**（「手順書の完了条件は表にしないで」「README に導入理由の節は要らない」など）は、このスキルへの指摘として記録する。

1. 指摘どおりに今の文書を直す
2. この SKILL.md と同じディレクトリの `feedback.md` の末尾へ、そのファイル冒頭の「記録の書き方」に沿って1件追記し、「指摘を feedback.md に記録した（スキルへの反映は保留）」と1行で伝える
3. 書き込めないとき（ファイルが無い、読み取り専用、作業フォルダの外へ書けない）は、追記するはずだった節をコードブロックで示し、手元の `feedback.md` に貼ってもらうよう頼んで終える

どこに記録するか:

| 指摘の中身 | 記録先 |
|---|---|
| 種別の選び方、章立て、載せる内容、テンプレート・チェックリストの過不足 | このスキルの `feedback.md` |
| 言い回し・語尾・語の選び方、AIくささ | japanese-prose-polish の `feedback.md` |
| この文書の中身の追加・訂正、事実の誤り、「この文書だけ」と明言された好み | 記録しない |

迷ったら記録し、頻度の見立てを「不明」にする。採否は人が決める。

**禁止事項:**

- 指摘を理由に SKILL.md・references/・templates/ をその場で書き換えること。反映は `feedback.md` の「反映の手順」に従い、ユーザーに頼まれたときだけ行う
- 書き込めなかったときに、別の場所へ記録ファイルを作ること
- 記録したことをユーザーに伝えずに済ませること

## 参照ファイル

種別が決まったら該当する1つだけを読む。全部読まない。

| ファイル | 読むタイミング |
|---|---|
| `references/explanation.md` | 種別が説明資料のとき。ヒアリング項目、章立て、mermaid 選択基準、チェックリスト |
| `references/procedure.md` | 種別が手順書のとき。3フェーズのヒアリング、章立て、完了条件・戻し方の書き方、チェックリスト |
| `references/readme.md` | 種別が README 型のとき。実物からの材料集め、章立て、章ごとの書き方、チェックリスト |
| `references/ai-knowhow.md` | 種別がAIノウハウ記録のとき。会話履歴からの素材抽出、蒸留の基準、索引への追記、検証ループ |
| `references/defect-report.md` | 種別が不具合報告書のとき。章ごとの材料の仕分け、ヒアリングの仕方、禁止事項 |

## スクリプト

### check_mermaid.py（全種別。mermaid 図を置いたとき）

```
python scripts/check_mermaid.py <文書.md> [...] [--font "<読者のフォント>"] [--png <dir>] [--deps <dir>]
```

文書中の mermaid 図をヘッドレスの Chromium で描き（`render_mermaid.cjs` を呼ぶ）、描かれた箱・線・ラベルの座標から崩れを判定する。問題のある図だけを `<ファイル>:<行> <図の種類> <ERROR|WARN> <コード> <内容>` の1行で出し、最後に件数を1行出す。終了コード: 0=ERROR なし（WARN のみも 0）/ 1=ERROR あり / 2=引数の誤り・読めない・Node.js が無い・依存の自動導入に失敗した。

| コード | 重大度 | 直し方の第一候補 |
|---|---|---|
| PARSE | ERROR | 構文を直す。ラベルの括弧・引用符は `A["..."]` で囲む |
| THROUGH / CLUSTER / TITLE | ERROR | ノードの宣言順を入れ替える、箱をサブグラフの内外へ移す、向き（TB / LR）を変える |
| LABEL / SAMELINE | ERROR | ラベルを短くするか箱側へ移す。戻りの線が多ければ図を分ける |
| OVERLAP / CLIP | ERROR | ラベルを `<br/>` で折る、箱の数を減らす |
| CROSS / DETOUR / GRAZE / PARALLEL / CLIPFONT | WARN | 宣言順の入れ替えで消えるなら消す。消えなければ残してよい |

- 直しては再実行する周回は図ごとに3周まで。ERROR が残ったら、残ったコードと行を添えてユーザーに渡し、完成と報告しない
- 判定に納得できないとき（直したのに消えない、どこが崩れているか分からない）だけ `--png` で画像を撮って見る。最初から画像を見ない。トークンが画像1枚ぶん増えるうえ、目視は線の突き抜けを見落とす
- `--font` は閲覧先のフォント（例 `Meiryo`）が分かっていて、文字の見切れを疑うときだけ付ける。mermaid は描いた環境のフォントで枠を決めるので、閲覧先のフォントが違うと見切れる
- 線と箱を測れるのは flowchart・stateDiagram・classDiagram など。sequenceDiagram などは PARSE と CLIP だけを見る
- 依存: Node.js と npm の `playwright`・`mermaid`（v11）、Playwright の Chromium。npm パッケージと Chromium は、無ければスクリプトが利用者のキャッシュフォルダ（`--deps` で変更可）へ自動で入れてそのまま検査を続けるので、事前に入れたり確認を取ったりしない。Node.js と npm は入れない。終了コード 2（Node.js が無い、ダウンロードが遮断されたなど）なら出力をユーザーに伝え、図は「未検査」と明記して提示し、検査済みと書かない。自動導入を止めたいときは `--no-install`
- `render_mermaid.cjs` は check_mermaid.py の部品で、単独では呼ばない

### check_knowhow.py（AIノウハウ記録だけ）

AIノウハウ記録の検証ループで使う。他の種別では使わない。

```
python scripts/check_knowhow.py <knowhow.md> [--index <INDEX.md>]
```

必須5節の有無、概要表の4項目、テンプレートのプレースホルダ残り、「効いたポイント」の件数と理由の有無、再利用プロンプトのコードブロック、行数（101行でWARN、141行でERROR）、`--index` 指定時は索引に当該ファイルへのリンクがあるかを機械的に判定する。終了コード: 0=合格（WARN のみも 0）/ 1=ERROR あり / 2=引数の指定ミスまたはファイルが読めない。依存は標準ライブラリのみ。形式しか見ないので、参照ファイルの目視チェックリストと必ず併用する。
