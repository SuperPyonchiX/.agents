# 種別: ツール・スキル紹介（README 型）

SKILL.md で種別が「ツール・スキル紹介」に決まったときに読む。
ツール・スクリプト・エージェントスキル・社内の仕組みを、**それを使い始めて、自分用にカスタマイズするまで**1本で完結させる文書を作る。説明資料（理解させる）と手順書（再現させる）の中間にあたり、読者は「自分の用途に使えるか」を判断してから、導入し、使い、直す。

説明資料・手順書と違い、**1本にまとめる。** 読者は同じ人で、判断→導入→利用→改造の順に読み進めるので、分けると行き来が増える。

## 材料の集め方

**読者レベルのヒアリングはしない。** 対象読者の欄も文書に書かない。読者は「そのツールを使うかもしれない人」に決まっている。

材料は対象の実物から集める。ヒアリングより先に読む。

| 読むもの | 拾う章 |
|---|---|
| 本体の定義（SKILL.md、README、`--help`、エントリポイント） | 何ができるか、使い方、ワークフロー |
| 制約・禁止事項・「見ないもの」の記述 | できないこと、機械で見ていないもの |
| 検証スクリプト・CI・テスト | 機械で見ているもの |
| 依存の記述（requirements、csproj、package.json、SKILL.md のスクリプト節） | 環境構築 |
| テンプレート・設定ファイル・定数表 | カスタマイズ |
| トラブルシューティング資料 | 困ったとき |

ユーザーに聞くのは次の2つだけ。会話や実物から分かれば聞かない。

1. **対象**：何の紹介か（ツール名・スキル名・パス）
2. **置き場所**：文書をどこに置くか。相対リンクの起点になる。決まらなければ作業用の場所に置き、その旨を伝える

**完了条件**：対象の実物を読み、下の章立ての各章について材料の有無が分かっていること。材料の無い章は、空のまま書かずに章ごと省くかユーザーに聞く。

## 章立て

骨組みを作る直前に [README 型テンプレート](../templates/readme.md) を読み、その構造に沿って埋める。順序は読者の判断の順なので入れ替えない。材料の無い章は省いてよい。

| 章 | 読者の問い |
|---|---|
| はじめに | これは何で、なぜあるのか |
| 何ができるようになるか（＋できないこと） | 自分の用途に使えるか |
| 全体像 | どういう仕組みで、何がどこにあるか |
| 環境構築 | 何を入れれば動くか |
| 使い方 | どう頼めば・どう打てば動くか |
| ベストプラクティス | 何に気をつければ失敗しないか |
| ワークフロー | 誰が何をして、何が自動で検査されるか |
| カスタマイズ | どこを直せば自分用になるか |
| 困ったとき | 動かないとき最初にどこを見るか |
| 関連 | 取り違えやすい隣のツールは何か |

見出しは `#` を章、`##` を節にする。共通ルールどおり文書タイトルの見出しは付けない。

## 章ごとの書き方

### はじめに

- **2〜4文で、何の紹介か（対象の名前と一言の正体）と、なぜ作ったか（どんな困りごとを解くのか）を書く。** 背景は対象の実物（設計上の勘所、禁止事項の理由など）から拾う
- 対象読者・読者レベルは書かない
- できることの列挙・図・コマンドは置かない。次章以降と重複する

### 何ができるようになるか

- **最初の1〜2文で、使うと何ができるようになるかを書く。** 仕組みの説明から始めない
- 方式・モードが複数あるなら「方式／作るもの／向いている場面」の表にする
- 使い方の入口になる**依頼文・コマンドの例を2〜3個**置く
- **「できないこと」を必ず節として置く。** 実物の制約・禁止事項・未検証の範囲から拾う。読者の判断材料として、できることと同じ重さがある

### 全体像

- mermaid 図を1枚置く。人・エージェント・ファイル・検査の流れが見える形にする
- 図の直後に要点を1〜2文で書く
- 構成ファイルのツリーを置き、各ファイルに1行の役割を添える

### 環境構築

SKILL.md の共通ルール「環境構築は読者の手数を最小にする」をこの章で具体化する。

1. **必要なものの表を先に置く。** 列は「必要なもの／用途／どの方式で要るか」。何を入れるのかがコマンドを読まなくても分かるようにする
2. **続けて、コピーして1回貼れば済むコマンドブロックを置く。** 各行の上にコメントで何を入れるかを書く。最後に完了を確認するコマンドを置く
3. 管理者権限が無い場合などの別経路、よくある失敗は `<details>` に畳む
4. 全ツール共通の導入（リポジトリの clone、リンクの作成など）は書き写さず、正本へリンクする

### 使い方

- 番号付きの手順で、**ユーザーが言うこと・聞き返されること・ユーザーがすることを書く。** エージェントが内部でやることはワークフロー章に回す
- 配置先・出力先などのパスは表にする
- 中断・再開の仕組みがあれば1文で書く

### ベストプラクティス

- **利用者が気をつけることだけを書く。** ツールやエージェントが自動でやることは入れない（ワークフロー章と重複する）
- 1項目は「太字で行動」＋「理由1文」。5〜7項目を目安にする

### ワークフロー

- 工程の mermaid 図（戻りの矢印を含む）を置く
- **担当表を置く。** 列は「工程／AI（ツール）が行うこと／ユーザーが行うこと／機械検査」。ユーザーの出番が無い工程は「なし」と書く
- **「機械で見ているもの」と「見ていないもの」を対で書く。** 見ているものだけを書くと、全部検査済みだと誤読される。見ていないものは検証スクリプトの docstring や制約の記述から拾う
- 完了の判定条件（何をもって完了とするか）を1文で書く

### カスタマイズ

- 冒頭でパスの起点を1文で示す
- **表の列は「ファイル／現状／変えたくなる場面と編集方法」。** 現状には実際の値を書く（「組織名」「`net6.0-windows`」）
- **未検証・特定条件でしか確かめていない値は、現状の列でそう明記する。** 知らずに流用されると事故になる
- 2つのファイルを揃えて直す必要があるもの（資料と検査スクリプトの許可リストなど）は、片方だけ直すと何が起きるかを書く
- 編集後に通す検証コマンドがあれば書く

### 困ったとき

- 「症状／まず見るところ」の表に3〜5行。詳しい切り分け資料があればリンクする

### 関連

- 取り違えやすい隣のツールだけを、1行ずつ「何をするか」と書く

## 記述の根拠

- **実物に書かれていないコマンド・パス・値を書かない。** 共通ルールの「確認していないことを断定しない」をそのまま適用する
- **行番号を書くときは実物で確かめる。** 書いた後にずれやすいので、可能なら定数名で示し、行番号は「付近」と添える
- 実物の記述どうしが食い違っていたら、どちらかに寄せて書かずにユーザーへ報告する

## 品質チェック

ドラフトを書いたら `japanese-prose-polish` を業務文書モードで当てる（見出し体系・コードブロック・表のパスと値・mermaid のラベルは書き換え対象外）。続けて次のチェックリストを、他人が書いた文書として当てる。

```
for 周回 in 1..2:
    チェックリストを当てる
    if 未達項目がゼロ:
        break（ドラフト完成）
    未達項目に対応する箇所のみを修正する
    if 今回の未達項目が前回と同一:
        同じ直し方を繰り返さない。材料が無いのか書き方の問題かを切り分け、材料が無ければユーザーに聞く
else:
    2周しても未達 → 残った未達項目を明示して提示する。解消したかのように報告しない
```

### チェックリスト

- [ ] 「はじめに」が2〜4文で、何の紹介かとなぜ作ったかが書かれているか（できることの列挙・図・コマンドを含めていないか）
- [ ] 「何ができるようになるか」の冒頭1〜2文で、使うと何ができるかが分かるか
- [ ] 「できないこと」の節があるか
- [ ] 対象読者の欄や読者レベルの記述を入れていないか
- [ ] 全体像に mermaid 図と構成ファイルのツリーがあるか
- [ ] 環境構築に「必要なもの／用途」の表があるか
- [ ] 環境構築のコマンドが1つのブロックにまとまり、各行に何を入れるかのコメントがあり、最後に完了確認があるか
- [ ] 1発で済まない部分について、理由が書かれているか
- [ ] 使い方に、聞き返される内容（ユーザーが答えるもの）が書かれているか
- [ ] ベストプラクティスに、ツールが自動でやることが混ざっていないか
- [ ] ワークフローの担当表に「ユーザーが行うこと」「機械検査」の列があるか
- [ ] 機械で見ているものと見ていないものが対で書かれているか
- [ ] カスタマイズ表の「現状」に実際の値が書かれ、未検証の値が明記されているか
- [ ] 実物に無いコマンド・パス・値を書いていないか
- [ ] 文体が常体で統一されているか
