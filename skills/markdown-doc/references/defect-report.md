# 種別: 不具合報告書

SKILL.md で種別が「不具合報告書」に決まったときに読む。
不具合解析の結果を報告書に落とす。仕事は「事実の整理」と「足りない情報のヒアリング」の2つで、書くこと自体は難しくない。失敗しやすいのは、**エージェントに分かりようがない項目（流出原因・組織的対策）を推測で埋めて、もっともらしいが事実無根の報告書を作る**こと。分からない項目は空欄のまま質問する。

## 入力

次のいずれか。材料が会話にあるならそこから抽出し、無いものだけ聞く。

- cpp14-defect-analysis の解析結果（同一セッションまたは解析メモ）
- ユーザーが持ち込む解析済みの情報（原因が特定できていること）
- エージェント自身の作業で起きた事故・未遂（このセッションの記録で原因まで追えること）

**実害の無い未遂（ヒヤリハット）も対象にする。** 防げた理由が偶然だった場合ほど残す価値がある。

**原因が未特定の不具合は対象外。** その場合は原因究明が先なので、cpp14-defect-analysis（C/C++ の場合）に切り替えるか、究明を先に行うことをユーザーに伝えて止まる。

## 手順

### 1. 材料を仕分ける

`../templates/defect-report.md` の章立てに対して、手元の材料がどの章を埋められるかを仕分ける。

章の順序は読者が知りたい順である。冒頭の要約と影響範囲で「自分に関係あるか」を判断させ、暫定対処で「今どうすればよいか」を渡し、解析の詳細はその後に置く。

| 章 | 埋める材料 | エージェントだけで書けるか |
|---|---|---|
| 要約 | 下の各章から3行に要約 | 他の章が埋まれば書ける。**最後に書く** |
| 影響範囲 | 影響を受けたもの・影響しえたもの・期間 | 技術的な範囲は書ける。出荷先・顧客はヒアリング |
| 暫定対処 | 修正版までの回避策 | 技術的な回避策は書ける。運用上の回避はヒアリング |
| 現象 | 解析時の再現条件・症状 | 書ける |
| 発生条件・再現手順 | 解析時の確定内容 | 書ける |
| 原因 | 根本原因の解析結果 | 書ける |
| 恒久対策 | 修正内容・修正コミット | 書ける |
| 流出原因 | なぜレビュー・テストで検出できなかったか | **書けない。必ずヒアリング**（エージェント自身の作業工程の事故なら、セッションの記録から書ける。その旨を章に明記する） |
| 再発防止策 | プロセス・チェックリスト・テストの改善 | 技術面は提案可。組織面はヒアリング |
| 水平展開 | 同種パターンの点検結果 | 点検を実施済みなら書ける。未実施なら実施を提案し、実施できるものはその場で実施する |
| 時系列 | 発生・検知・対処の経過 | 記録があれば書ける。時刻が無ければ順序だけで書き、その旨を明記する |

### 2. 足りない情報をヒアリングする

書けない章・材料が無い章について、**章ごとに1問ずつ、選択肢つきで**質問する（「流出原因は a) レビュー観点に無かった b) テストケースが無かった c) 再現条件が特殊で環境が無かった、のどれに近いですか」の形）。一度に全部聞かず、2〜3問ずつに分ける。

技術的な再発防止策（テスト追加、静的解析ルール追加、レビュー観点追加）は先に案を作って提示し、採否を聞く。

### 3. 報告書を書く

`../templates/defect-report.md` をコピーして全章を埋める。**章の追加・削除・並べ替えをしない。** 書き方の基準:

- **文書タイトルの見出しを付けず、章に番号を振らない。** ファイル名で件名が分かる
- **要約は3行（何が起きたか・原因・今の状態）で、他の章を書き終えてから書く。** 冒頭しか読まない読者にも結論が届くようにする
- **暫定対処と恒久対策を分ける。** 暫定対処が不要なら「不要」と理由を書く
- 事実と推定を書き分ける。推定には「〜と推定される（根拠: …）」の形で根拠を添える
- 原因の章は、直接原因 → それを許した要因の順に、因果の連鎖が追えるように書く
- **未遂・軽微で済んだ場合は、済んだ理由を原因の章に書き、偶然か仕組みかを明記する。** 「実害なし」だけでは、次も防げるかが読者に分からない
- 影響範囲・流出原因・再発防止策・水平展開・時系列は表で書く。空欄がひと目で分かる
- コード片・ログは必要最小限の抜粋にし、パスとバージョン（コミットID）を添える
- ヒアリングで「不明・未定」だった項目は、無理に埋めず「未定（〇〇待ち）」と書く

保存先はユーザーに確認する（既定の提案: 対象リポジトリの `docs/` またはユーザー指定のフォルダ。ファイル名 `defect-report_YYYY-MM-DD_[短い件名].md`）。

### 4. 仕上げる

提示する前に japanese-prose-polish スキルを当て、文体を整える（構成・事実は変えない）。

**完了条件: 全章が「事実」「根拠つき推定」「未定（理由つき）」のいずれかで埋まった報告書を提示し、ユーザーの承認を得たこと。** 空欄や「TODO」を残したまま完了としない。

## 禁止事項

- 流出原因・組織的な再発防止策を、ヒアリングせずに創作すること
- 根拠のない再発防止策（「レビューを強化する」「注意する」の類）だけで再発防止の章を埋めること。検証可能な形（何を・どの工程に・どう組み込むか）まで落とす
- テンプレートの章を削って短くまとめること
