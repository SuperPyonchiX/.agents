# 種別: 業務手順書

SKILL.md で種別が「手順書」に決まったときに読む。
社内の汎用的な業務手順書を、構造化されたMarkdown形式で対話的に作成する。
ユーザーへのヒアリングを通じて段階的に手順書を組み立て、Mermaid記法による視覚的な図解、
`<details>` タグによる折りたたみ補足、トラブルシューティングセクションを含む
わかりやすい手順書を生成する。既存のメモや箇条書きからの整形、業務フローの標準化もここに含む。

**背景の説明も必要な場合は1本にまとめず、資料を2本に分けて相互リンクする。** 手順書に背景説明を書き下すと、手を動かしたい読者にとって読みにくくなる。背景は「はじめに」を1〜2文に保ったうえで、説明資料側へリンクする。

## 手順書テンプレート構造

作成する手順書は、以下のセクション構成に従うこと。**順序は読者が作業する順である。** 「何ができるようになるか」で着手を判断し、必要なものを揃え、全体を見てから手を動かし、困ったら調べ、不要になったら戻す。
ヒアリング完了後、ドラフトを書き始める直前に [手順書テンプレート](../templates/procedure.md) を読み、その構造に沿って埋める。

### セクション構成

```
# はじめに
  - 1〜2文で、終わると何ができる状態になるか・作業量（「コマンド1回と再起動」など）
  - 表：終わるとできること / 対象環境 / 動作確認日（確認した範囲も書く）
  - 想定読者・読者レベルは書かない

# 始める前に
  - 表：必要なもの / 用途 / 確認方法
  - まとめて確認できるコマンド（1ブロック）
  - 権限（管理者・開発者モードなど）が要るか要らないか

# 全体の流れ
  - Mermaid図
  - 図の補足1〜2文、総ステップ数と所要時間（計っていなければ作業量で書く）

# 手順
  ## ステップ1：[ステップ名]
    - 操作、完了条件（何が表示されれば成功か）
  ## ステップ2：[ステップ名]
    - ...以降同様。最後のステップを完了確認にしてよい

# うまくいかないとき
  - 症状 / 原因 / 対処 の表

# 元に戻す
  - 全体を導入前に戻す手順。戻せない操作は「戻せない」と書く

# 参考資料（あれば）
  - 事前に読む必要のない関連資料・詳細資料
```

### 見出しレベル

- 手順書タイトルの見出しは**付けない**。ファイル名で判別できるため不要である。文書は `# はじめに` から始める
- `#` ：主要セクション。**章に番号を振らない**（「4.2 ステップ1」のような二重番号を作らない）
- `##` ：各ステップ。番号は「ステップN」だけにする
- `###` ：必要に応じて使用するが、深くなりすぎないよう注意する

### 「はじめに」の記述方針

**簡潔さを最優先**とする。終わると何ができるかが一目で分かる程度にとどめ、図解や背景説明は含めない。背景が要るなら説明資料を別に作ってリンクする。

導入文に続けて、**終わるとできること・対象環境・動作確認日の表を必ず置く**。手順書は文書のなかで最も陳腐化が速い。**「いつ時点の、何を対象にした情報か」が書かれていない手順書は、読者がそれを信じてよいか判断できない。**

良い例：

```markdown
# はじめに

新しい PC に個人用スキル置き場を導入し、Claude Code から使える状態にする。作業はコマンド1回と再起動だけである。

| 項目 | 内容 |
|---|---|
| 終わるとできること | Claude Code の `/` メニューにスキルが出る |
| 対象環境 | Windows 11、コマンドプロンプト |
| 動作確認日 | 2026-10-03（作業用フォルダで確認。本番環境では未確認） |
```

動作確認日は、**手順を実際に確認した日**を書く。一部しか確認していなければ、確認した範囲を括弧で添える。確認していない場合は日付を書かず、未確認であることを明示する（後述の「記述の根拠」参照）。

### 「始める前に」の記述方針

SKILL.md の共通ルール「環境構築は読者の手数を最小にする」をここで具体化する。チェックボックスを並べるだけにしない。

- 「必要なもの / 用途 / 確認方法」の表にする。任意のものは任意と書く
- 確認方法をつないだ1ブロックのコマンドを置く（例：`git --version && python --version`）
- 権限が要らない方法があるならそちらを選び、要らないことを明記する。要るなら理由を書く

### 「全体の流れ」の記述方針

**これから行う作業の全体像を視覚的に示す**。ここが手順書の"地図"の役割を果たす。

Mermaid図は**内容に最も適した図の種類**を選択する：

| 図の種類 | 適しているケース | Mermaid記法 |
|---------|----------------|-------------|
| フローチャート | 作業手順の流れ、分岐のある判断プロセス | `flowchart TD` / `flowchart LR` |
| システム構成図 | サーバー構成、ネットワーク構成、ツール間の関係 | `graph TD` / `graph LR` でブロック構成を表現 |
| シーケンス図 | 複数の人・システム間のやりとりの順序 | `sequenceDiagram` |
| 状態遷移図 | 状態の変化を伴うプロセス | `stateDiagram-v2` |

- 「作業の流れ・順序」が主題 → フローチャート
- 「何と何がどう繋がるか」が主題 → システム構成図
- 「誰が誰に何を渡すか」が主題 → シーケンス図
- 複数の観点が必要な場合は、2つ以上の図を組み合わせてもよい

Mermaid図の後には、図を補足する簡潔なテキスト説明を必ず添える。**あわせて総ステップ数と所要時間の目安を書く**。読者が着手前に「今やれるか」を判断できるようにするためで、待ち時間（承認待ち、ビルド待ちなど）があればその旨も書く。所要時間を計っていなければ数字を作らず、作業量（「コマンド1回と再起動」）で書く。

### 「元に戻す」の記述方針

各ステップの戻し方を折りたたみに散らすのではなく、**導入前の状態に戻す手順を1章にまとめる**。戻したい読者はこの章だけを読めばよい。

- 消してよいものと残るものを書き分ける（「リンクだけを消す。実体は残る」）
- 誤ると被害が大きいオプションは禁止として書く（「`rmdir /S` を付けない」）
- 戻せない操作があれば、その操作のステップ冒頭にも「戻せない」と書く

### 手順書の文体

手順書全体の文体は「である・となる」調（常体）で統一すること。
「です・ます」調（敬体）は使用しない。

良い例：「〇〇をインストールする」「以下のコマンドを実行する」「正常に完了した場合、△△が表示される」

悪い例：「〇〇をインストールします」「以下のコマンドを実行してください」

## ヒアリングプロセス

ユーザーから手順書作成を依頼されたら、**一度に全てを聞かず**、以下のフェーズに分けて対話的に情報を収集すること。各ターンの質問は **最大3つ** までとする。

**ヒアリング開始前に、会話・提示された資料・既存メモから埋まる項目を先に抽出すること。** 埋まった項目は質問せず、「対象作業は〇〇、ゴールは△△と理解した」と**確認として提示**し、足りない項目だけを質問する。既にすべてのフェーズ分の材料が揃っているなら、ヒアリングを飛ばしてフェーズ4のドラフト生成に進む。

各フェーズの完了条件は、そのフェーズの項目すべてについて回答または確認提示への同意が得られたこと。埋まらないまま次のフェーズに進まない。

### フェーズ1：基本情報の収集

まず以下を確認する：

1. **対象作業**：何の手順書を作るのか
2. **作業のゴール**：この手順を完了すると何ができる状態になるのか
3. **実行環境**：OS、使うシェル（コマンドプロンプト / PowerShell / bash）、権限の有無

### フェーズ2：詳細情報の収集

基本情報をもとに、以下を深掘りする：

1. **インプット資料**：参照すべきドキュメント、URL、社内Wikiなどがあるか（手順書では末尾の「参考資料」に置く）
2. **前提条件と対象環境**：必要なアカウント・権限に加え、**OS とツールのバージョン、手順を確認した日**。手順書の陳腐化を読者が判断する材料になるため、前提条件とは分けて聞く
3. **大まかな作業ステップ**：ざっくりとした流れ

### フェーズ3：手順の詳細化

大まかな流れをもとに、各ステップを詳細化する：

1. **具体的なコマンドや操作**：各ステップで実行する具体的な内容
2. **注意点・ハマりポイント**：経験上つまずきやすい箇所。**元に戻しにくい操作が含まれるか、含まれる場合の戻し方**もここで聞く
3. **確認方法**：各ステップの完了条件（何が表示されれば成功か）と、最終的な完了確認の方法
4. **所要時間**：全体の目安。待ち時間（承認待ちなど）が含まれるか

### フェーズ4：ドラフト提示とレビュー

収集した情報をもとに手順書のドラフトを生成する。ユーザーに提示する前に、後述の「出力品質チェックリスト」を当て、未達項目に対応する箇所のみを修正すること。

チェックを通過したらユーザーにレビューを依頼し、フィードバックを受けて修正する。この対話ループには終了条件を守ること。

```
for 周回 in 1..3:
    ドラフトを提示してレビューを依頼する
    if ユーザーから修正指示がない（合意が得られた）:
        break（完成）
    指摘された箇所のみを修正する（手順書全体を再生成しない）
    if 今回の指摘が前回と同趣旨:
        同じ直し方を繰り返さない。ヒアリングで取り違えた前提を疑い、
        どこを誤解していたかを挙げてユーザーに確認する
else:
    3周しても合意に至らない → 残っている論点と試した修正を整理して報告する。
    完成したかのように報告しない
```

## 記述ルール

### 記述の根拠

手順書は読者がそのとおりに手を動かす文書である。**間違ったコマンドやパスを書けば、読者の環境が壊れる。** 次を守る。

- **確認していないコマンド・パス・UI の遷移を、確認済みであるかのように書かない。** ヒアリングでユーザーが述べた内容、インプット資料に書かれている内容、実際に実行して確かめた内容のいずれかに基づくこと
- **エージェントが実行できるコマンドは、実際に流して確かめる。** 本物の環境を壊さないよう、作業用のフォルダに置き換えて流す。このとき `%USERPROFILE%` や `$HOME` のような環境変数を一時的に書き換えて試さない（cmd は `set` より先に行全体を展開するため、本物のパスに対して実行される）。パスを直接埋め込んだスクリプトで試す。流せなかった部分は手順書上で未確認と書く
- **インプット資料にないコマンドやオプションを推測で補わない。** 「たぶんこのオプションだろう」で書かず、不明な箇所を挙げてユーザーに確認する
- バージョン番号・URL・ファイルパス・画面上のメニュー名は、裏が取れているものだけを書く
- 確認が取れないまま手順書に残す場合は、その箇所に**未確認であることを明記する**（例：「※ v3.2 での画面名。以降のバージョンでは異なる可能性がある」）

### 各ステップの完了条件

各ステップの末尾に **完了条件** を書く。「操作したこと」ではなく **「何が表示されれば成功か」** を書くこと。これがないと、読者は失敗に気づかないまま次のステップに進み、原因が分からなくなる。

```markdown
**完了条件**：VPNクライアントの証明書一覧に、受領した証明書が「有効」と表示されること。
```

判定材料が画面に出ない場合は、確認用のコマンドを添える。

### 失敗時の戻し方

**元に戻しにくい操作を含むステップには、戻し方を書く。** 対象となるのは、インストール、設定ファイルの上書き、再起動、権限やアカウントの変更、データの削除・移行など。

- 戻せる場合：戻す手順は「元に戻す」章にまとめる。ステップごとに戻し方が大きく違うときだけ、そのステップに折りたたみ補足で添える
- 戻せない場合：**戻せないことをステップの冒頭で明示する。** 「この操作は取り消せない。実行前に [対象] のバックアップを取ること」のように、事前にすべきことをセットで書く

途中で中断してよいステップの区切りが決まっている場合は、それも書く（例：「ステップ2まで完了していれば、ここで中断して翌日に再開してよい」）。

### 折りたたみ補足（details / summary）

初心者向けの用語解説、背景情報、コマンドの詳細オプション説明など、
本筋の手順を読む上では必須ではないが知っておくと理解が深まる補足情報は、
`<details>` / `<summary>` タグで折りたたみにすること。

```html
<details>
<summary>補足：〇〇とは？</summary>

ここに補足情報を記載する。
コードブロックや箇条書きも使用可能。

</details>
```

**重要**：`<details>` タグの開始タグ直後と `</details>` 閉じタグ直前には**空行を入れる**こと。
空行がないとMarkdownパーサーによっては内部のMarkdown記法が正しくレンダリングされない。

### コマンド・コード記載

- コマンドは必ずコードブロック（` ``` `）で囲み、言語識別子を付与する
- 長いコマンドは改行して可読性を確保する
- 変更すべきパラメータは `[角括弧]` で囲んでプレースホルダーとして明示する

```bash
# 例：接続確認コマンド
ping -c 4 [対象サーバーのIPアドレス]
```

**山括弧（`<対象サーバー>` の形）は本文中で使わないこと。** Markdown では生の HTML タグとして解釈され、レンダリング時に丸ごと消える掲載先がある。コードブロック内は安全だが、表記が2系統に割れると読者が混乱するため、**プレースホルダーは角括弧に統一する**。

### うまくいかないとき

「症状 / 原因 / 対処」の表で書く。症状の列には、**読者の画面に出る文言をそのまま**書く（エラーメッセージは原文で）。読者は画面の文言で検索して該当行を探す。

```markdown
| 症状 | 原因 | 対処 |
|---|---|---|
| `Cannot create a file when that file already exists.` | リンク先が既にある | 中身を確かめてから消し、該当コマンドだけを再実行する |
```

対処が3手順を超える症状だけ、表の後に `## 症状：[文言]` の見出しを立てて番号付きで書く。

## 出力品質チェックリスト

手順書のドラフトを生成したら、まず `japanese-prose-polish` スキルを**業務文書モード**で当て、AIくさい言い回しを除去する。
このスキルが定める見出し体系・必須セクション・コマンド・コードブロックは書き換え対象外として渡すこと。

そのうえで、以下の観点でセルフチェックを行うこと：

- [ ] 手順書タイトルの見出しを付けていないか（文書が `# はじめに` から始まっているか）
- [ ] 章の順序が はじめに → 始める前に → 全体の流れ → 手順 → うまくいかないとき → 元に戻す → 参考資料 になっているか
- [ ] 章に番号を振っていないか。ステップの見出しが「ステップN：」だけになっているか
- [ ] 「はじめに」が1〜2文で、終わると何ができるかを述べているか。図解や背景説明を含めていないか
- [ ] 「はじめに」に終わるとできること・対象環境・動作確認日（確認範囲つき）の表があり、想定読者を書いていないか
- [ ] 「始める前に」が「必要なもの / 用途 / 確認方法」の表と、まとめて確認するコマンドになっているか
- [ ] 環境の導入が、コピーして1回貼れば済むコマンドブロック（各行にコメント、最後に完了確認）になっているか。1発にできない部分は理由が書かれているか
- [ ] 「全体の流れ」にMermaid図と、総ステップ数・所要時間（計っていなければ作業量）が書かれているか
- [ ] 各ステップに完了条件（何が表示されれば成功か）が書かれているか
- [ ] 「元に戻す」章があり、消えるものと残るもの、付けてはいけないオプションが書かれているか
- [ ] エージェントが流せるコマンドを、作業用のフォルダで実際に流したか。流せなかった部分を未確認と書いたか
- [ ] 確認していないコマンド・パス・メニュー名を断定していないか（未確認なら手順書上に明示されているか）
- [ ] Mermaid図の種類が内容に適しているか（フロー、構成図、シーケンスなど）
- [ ] Mermaid図の後にテキストによる補足説明があるか
- [ ] 各手順ステップに番号が振られ、1ステップ1操作になっているか
- [ ] コマンドやコードがコードブロックで囲まれているか
- [ ] 変更すべきパラメータがプレースホルダー（`[角括弧]`）で明示されているか（山括弧を使っていないか）
- [ ] 補足情報が `<details>` タグで折りたたまれているか
- [ ] 「うまくいかないとき」の表に最低1行あり、症状が画面の文言そのままか
- [ ] 文体が「である・となる」調で統一されているか（「です・ます」が混在していないか）

## 入出力例

### 入力例

```
新しい PC に ~/.agents を導入する手順書を作って
```

### 出力の流れ

1. フェーズ1：会話と README から対象作業・ゴール・実行環境を抽出して確認提示する
2. フェーズ2：README のセットアップ節から前提とステップを拾い、コマンドを作業用フォルダで実際に流す
3. フェーズ3で各ステップを深掘り
4. ドラフトを生成し、レビューを依頼

### 生成される手順書の例

完成例は [~/.agents 導入手順書の例](../examples/procedure.md) を参照。
