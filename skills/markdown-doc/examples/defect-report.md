# 暫定対処

不要。実害が無く、同じ方法での再試行はしていない。2回目以降は作業用フォルダのパスを直接埋め込んだバッチファイルで試した。

# 現象

作業用フォルダ `scratchpad\home` を仮のホームにして、`~/.agents` の導入コマンド（clone → `.claude` 作成 → リンク作成）を試した。次のエラーで止まった。

```
fatal: could not create leading directories of '"C:\Users\ksk01\.agents"': Invalid argument
```

clone 先が作業用フォルダではなく、本物のホームを指していた。

# 発生条件・再現手順

1. bash から `cmd //c` で、1行に `set USERPROFILE=<作業用フォルダ>&& git clone ... "%USERPROFILE%\.agents" && ...` を渡す
2. cmd が行全体を解析する時点で `%USERPROFILE%` を本物の値に展開し、そのあとで `set` が実行される

再現率は100%と推定される（根拠：cmd の `%変数%` は行の解析時に展開される仕様である。遅延展開 `!変数!` を有効にしない限り変わらない）。

# 原因

1. **直接原因**：同じ行で `set` した値を `%USERPROFILE%` で参照した。cmd は行の解析時に `%変数%` を展開するので、参照は `set` より前の値、つまり本物のホームになった
2. **それを許した要因**：環境変数を一時的に書き換えれば作業用フォルダで試せる、という前提で1行のコマンドを組んだ。本物の環境を指していないことを実行前に確かめる手順が無かった
3. **被害が出なかった理由**：bash から cmd へ渡すときの引用符のエスケープが崩れ、パスに `"` が混ざって clone が失敗した。**防いだのは偶然であり、仕組みではない**

# 恒久対策

- 作業用フォルダのパスを、環境変数ではなく直接埋め込んだバッチファイルで試すように切り替えた（同セッション内で実施。clone・ジャンクション作成・削除を作業用フォルダで確認済み）
- `markdown-doc` の手順書の規約に、次のルールを追加した（コミット `4d25c58`）：「エージェントが流せるコマンドは作業用のフォルダで実際に流して確かめる。このとき環境変数を一時的に書き換えて試さない。パスを直接埋め込んだスクリプトで試す」

# 流出原因

| 工程 | 検出できなかった理由 |
|---|---|
| コマンドの組み立て | cmd の展開タイミングを考慮せず、bash の感覚で1行にまとめた |
| 実行前の確認 | 実行するコマンドが本物の環境を指していないかを、実行前に表示して確かめる手順が無かった |
| スキルの規約 | 手順書の規約は「確認していないコマンドを断定しない」だけで、確認の**やり方**（本物の環境を壊さずに試す方法）を定めていなかった |

本章はこのセッションの記録に基づく。エージェント自身の作業工程の話なので、ヒアリングで補う項目は無い。
