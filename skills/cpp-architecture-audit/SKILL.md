# C/C++ Architecture Audit

コードベースの「構造」だけを見るスキル。規約違反や個々のバグは見ない。失敗しやすいのは、(1) 依存関係を目視で追って見落とす・間違える、(2) 問題の列挙で終わって「どの順で直すと安全か」まで落とさない、(3) 一度に大きく直す計画を立てて検証不能にする、の3つ。依存の抽出は必ずスクリプトで行い、計画は「1ステップ＝検証可能な小さな変更」に刻む。

## ワークフロー

直列3フェーズ。機械抽出 → 目視監査（台帳化）→ 計画。

## 手順

### 1. 対象範囲の確定と機械抽出

対象のソースルート（複数可）と、除外するディレクトリ（サードパーティ、生成コード）をユーザーと確認する。確定したらスクリプトを実行する:

```
python scripts/include_graph.py <ソースルート> [<ルート2> ...] [--top N]
```

出力: サマリ / 循環依存（強連結成分）/ ファンイン上位（変更影響が大きい）/ ファンアウト上位（責務過多の疑い）。終了コード 0=正常（循環があっても0。循環の有無は出力で見る）、2=引数エラー。依存は標準ライブラリのみ。`#ifdef` は解釈しないため、条件コンパイルが多いコードでは実際より多めにエッジが出ることを結果の解釈時に踏まえる。

### 2. 目視監査と台帳化

スクリプトの結果を起点に、次の観点で目視監査する。**スクリプトが挙げた上位から読む**（全ファイルを網羅しようとしない）。

| 観点 | 見るもの |
|---|---|
| 循環依存 | 強連結成分の各ファイル。どのエッジを切れば解消するか |
| 神モジュール | ファンイン・ファンアウトともに高いファイル。責務の数 |
| レイヤ違反 | 下位層（ドライバ・ユーティリティ）が上位層（アプリ）を include していないか |
| 密結合 | ヘッダに実装詳細（privateメンバ、内部型）が露出し、変更が波及する箇所 |
| テスト容易性 | ハードウェア・グローバル状態への直接依存で、ホスト環境で切り離せない箇所 |

指摘は台帳にする（ID / 対象 / 観点 / 問題 / 影響 / 改善案の6列）。**推測でエッジを語らない**。依存の主張はスクリプト出力か、実際に読んだ include 行を根拠にする。

### 3. リファクタリング計画に落とす

台帳の指摘を、安全に実行できる順序の計画にする。順序付けの原則:

1. **検証手段の確保が先**（テストがない箇所は、特性テスト・ビルド確認の整備をステップ0に置く）
2. 依存される側（ファンイン大）の変更は影響が大きいので、依存の切断（インターフェース挿入）を先に、移動・分割を後に
3. 1ステップは「ビルドが通り、既存テストがパスする」単位に刻む。ビッグバン統合を計画に入れない

各ステップに: 対象 / 変更内容 / 検証方法（ビルド・テスト・スクリプト再実行での数値変化）を書く。計画の提示で完了とし、**実施はユーザーの指示があってから**着手する（実施時の規約チェックは cpp14-code-review を併用する）。

**完了条件: 台帳と、全ステップに検証方法がついた計画書を提示したこと。**

## 禁止事項

- スクリプトを実行せずに依存関係を目視だけで語ること
- 検証方法のないステップを計画に入れること
- 監査のついでに規約違反の指摘を混ぜること（それは cpp14-code-review の台帳でやる。混ぜると両方のクローズ判定が壊れる）

## 想定外の扱い

- 対象が巨大（数千ファイル）でスクリプト出力が読み切れない場合: ユーザーとサブシステム単位に分割し、1サブシステムずつ監査する
- include 以外の結合（グローバル変数、リンク時依存）が支配的と分かった場合: スクリプトでは拾えない旨を明示し、その部分は目視監査の範囲と限界を報告する

## スクリプト

```
python scripts/include_graph.py <ソースルート> [<ルート2> ...] [--top N]
```

手順1で使う。詳細（対象拡張子・出力・終了コード・制約）はスクリプト冒頭の docstring にもある。
