# 生成AI活用ノウハウ記録スキル

直前の作業で生成AIから意図どおりの成果物が得られたとき、その**出し方**を短い Markdown として残す。
狙いは記録の網羅ではなく**再現**である。読んだ人（未来の自分を含む）が同じ手を打てることだけが成果物の条件で、
やり取りの全文を残すことは目的ではない。

設計上の勘所は2つ。**会話履歴の再構成は捏造の温床**であること、そして
**「効いたポイント」は放っておくと一般論に落ちる**こと。この2点を工程2と工程3で潰す。

## 使用タイミング

- 直前の作業で生成AIから狙いどおりの成果物が出せ、その手順を残しておきたいとき
- 「今のやり方をノウハウに残して」「さっきの進め方を記録して」と依頼されたとき
- プロンプトの工夫や進め方の勘所を、次回以降に再利用できる形にしたいとき

**このスキルは同一セッション内の直前の作業を対象とする。** 会話履歴に materials が無い過去の作業を
書き起こす依頼を受けた場合は、その旨を伝えて工程2をヒアリングに置き換えるか、対象の作業を
このセッションでやり直してから使うことを提案する。勝手に思い出しで埋めない。

## 他のドキュメント系スキルとの使い分け

| 依頼の主眼 | 使うスキル |
|---|---|
| **自分が実際にやったAI活用の記録**を残す（どう指示して、どこで外して、どう直したか） | **このスキル** |
| 概念・仕組み・背景を読者に**理解**させる | `markdown-explanation-doc` |
| 読者に作業を**再現**させる汎用の業務手順書（AI活用に限らない） | `markdown-procedure-doc` |

判断がつかないときは「この記録の主語は誰か」で決める。主語が自分の作業実績ならこのスキルである。

## ワークフロー

```
1. 対象の特定と出力先確認
2. 会話履歴から素材を抽出        ← 捏造しない
3. ノウハウへ蒸留                ← 一般論を落とす
4. knowhow/<slug>.md を書く
5. INDEX.md に1行追記
6. 検証ループ（機械 + 目視、上限2周）
7. ドラフトとして提示
```

### 1. 対象の特定と出力先確認

会話から「何を作ったか」を抽出し、**確認として提示する**（「今回の成果物は〇〇、使ったのは△△と理解した」）。
すでに会話に出ている項目は質問しない。

**ユーザーに必ず聞くのは出力先ディレクトリの1問だけ。** 既定候補として、現在のリポジトリ配下の
`docs/ai-knowhow/` を提示する。以下の配置になる。

```
<出力先>/
├── INDEX.md              # 索引。無ければ assets/templates/index-template.md から作る
└── knowhow/<slug>.md     # 本体。1件1ファイル
```

`<slug>` は内容が分かる kebab-case にする（`meeting-notes-triage` など）。日付は入れない（日付は本文の概要表に持つ）。

**完了条件**：出力先ディレクトリが確定し、成果物の理解についてユーザーの同意または訂正が得られたこと。

### 2. 会話履歴から素材を抽出

このセッションの履歴から次を拾う。**拾えなかった項目は空のままにする。**

- 実際に投げた指示と、その狙い
- 出力が外れた箇所と、直しに使った追加指示
- 使ったAI・モデル・ツール、所要時間、日付

**禁止事項：履歴で確認できないやり取りを書かない。** 「たぶんこう指示したはず」で埋めるのは、
このスキルで最も起きやすく、最も害が大きい失敗である。記録が実際と違えば再現できず、
読んだ人は原因を特定できない。埋まらない項目はユーザーに1回だけ確認し、答えが得られなければ
その項目を落とすか「不明」と書く。

### 3. ノウハウへ蒸留

- **「やったこと」は再現に必要な手数だけに絞る。** 試行錯誤の全記録ではない。目安5〜8手。
  ただし「一度外して直した」経緯は、外し方そのものが勘所である場合に限り残す
- **「効いたポイント」は3〜6個。各項目に必ず理由を添える。** 理由とは「なぜ効いたか」であり、
  効かなかったときとの差が書けていること
- **一般論を書くことを禁止する。** 「プロンプトは具体的に書く」「段階的に指示する」のような、
  今回の作業をやらなくても言えることは1つも書かない。判定基準は
  **その記述を読んで、今回と別の作業をしていた人が「それは自分の場合も同じだ」と言えてしまうなら一般論**である
- **「つまずいたこと」は次回避けるべきものだけ残す。** 解決済みの些末な失敗は書かない

### 4. knowhow/<slug>.md を書く

`assets/templates/knowhow-template.md` をコピーして埋める（**工程4に入る直前に読む**）。
構成は 概要 → やったこと → 効いたポイント → つまずいたこと・避けること → 再利用プロンプト の5節で固定する。
**節を増やさない。** 増やしたくなったら、それは1件に2つのテーマが入っている合図なので件を分割する。

分量は**本文60〜100行**。100行を超えたら項目を削るのではなく、**テーマで件を分割して2ファイルにし、相互リンクする**。
記事タイトルの見出しは付けない。文書は `# 概要` から始める。

### 5. INDEX.md に1行追記

出力先に `INDEX.md` が無ければ `assets/templates/index-template.md` から作る（**このときだけ読む**）。
あれば一覧の先頭に1行追記する。既存の書式には手を入れない。

```
- [タイトル](knowhow/<slug>.md) — 何を作ったか一言（YYYY-MM-DD）
```

### 6. 検証ループ

```
for 周回 in 1..2:
    python scripts/check_knowhow.py <出力先>/knowhow/<slug>.md --index <出力先>/INDEX.md
    下記の目視チェックリストを、他人が書いた記事として当てる
    if 終了コード0 かつ 目視の未達がゼロ:
        break（ドラフト完成）
    指摘された箇所のみを修正する（全文を書き直さない）
    if 今回の指摘が前回と同一:
        同じ直し方を繰り返さない。構成そのものを疑い、ユーザーに方針を確認する
else:
    2周しても未達 → 残っている未達項目を明示して報告する。
    解消したかのように報告しない
```

スクリプトは形式しか見ない。**中身の判定はこちらが本体である。**

- [ ] 「やったこと」だけを読んで、同じ作業を再現できるか
- [ ] 「効いたポイント」が一般論になっていないか（別の作業をしていた人にもそのまま当てはまるものは削る）
- [ ] 会話履歴で確認できない事実を書いていないか（指示の文言、所要時間、モデル名）
- [ ] 「つまずいたこと」が、次に避けるべきものだけになっているか
- [ ] 「再利用プロンプト」がそのまま投げられる形か（可変部分が角括弧で示されているか）
- [ ] 成果物そのものの説明に紙面を使いすぎていないか（記録すべきは**出し方**である）

### 7. ドラフトとして提示

完成品ではなく**ドラフト**として提示し、事実誤認がないかユーザーに確認してもらう。
特に工程2で不明として残した項目を明示して聞く。修正依頼への対応は上限3周とし、
収束しなければ食い違いを整理して方針を確認する。

## 終了条件と失敗時の扱い

- **成功**：`check_knowhow.py` が終了コード0、目視チェックリストの未達ゼロ、ユーザーがドラフトを確認したこと
- **上限**：検証ループ2周、修正依頼への対応3周
- **収束しない場合**：残っている未達項目と試したことを列挙して報告する。合格したかのように報告しない
- **止まる条件**：会話履歴に対象作業の素材が無い、成果物が「意図どおり」と言えるか怪しい、
  「効いたポイント」が2個も書けない —— このいずれかならユーザーに確認し、勝手に進めない。
  ポイントが書けない作業は、そもそも記録に残す価値があるか疑う

## テンプレート

| ファイル | 読むタイミング |
|---|---|
| `assets/templates/knowhow-template.md` | 工程4で記事を書き始める直前 |
| `assets/templates/index-template.md` | 工程5で `INDEX.md` が存在しなかったときだけ |

## スクリプト

```
python scripts/check_knowhow.py <knowhow.md> [--index <INDEX.md>]
```

工程6で実行する。必須5節の有無、概要表の4項目が埋まっているか、テンプレートのプレースホルダ残り、
「効いたポイント」の件数と理由の有無、再利用プロンプトのコードブロック、行数（101行でWARN、141行でERROR）、
`--index` 指定時は索引に当該ファイルへのリンクがあるかを機械的に判定する。

| 終了コード | 意味 |
|---|---|
| 0 | 合格（WARN のみの場合も0。内容は表示される） |
| 1 | ERROR あり。直すまでユーザーに提示しない |
| 2 | 引数の指定ミス、またはファイルが読めない |

依存は標準ライブラリのみ。見るのは形式だけなので、目視チェックリストと必ず併用する。
