# Three.js ゲーム

ブラウザで遊べる Three.js ゲームを、**まず遊べるループ、次に見た目、最後に実際に動かした証拠**の順で作る。

設計上の勘所は2つ。

- **何を作るかはユーザーが決める。** ジャンル・画風・カメラ・規模・2D/3D の選択にこのスキルは口を出さない。ここにあるのは「遊べるか」を確かめる手順と、困ったときの資料だけ。
- **動いたと言うのは、動かしてから。** ビルドが通っただけ、スクリーンショットが出ただけでは完了にしない。

```
依頼 → [1 範囲を決める] → [2 設計メモ(新規・大改修のみ)] → [3 実装] → [4 検証ループ ≤3周] → [5 報告]
                                                         ↑______ 修正 ______|
```

## 1. 範囲を決める

依頼の言葉をそのまま基準にする。

- 「小さなゲーム」「ちょっと遊べるもの」は小さく作って止める。頼まれていない演出・レベル・メニューを足さない
- 「作り込んで」「リリースできる品質で」「もっとリッチに」と言われたときだけ、見た目と手触りを作り込む
- 既存ゲームの部分修正は、関係ない仕組みに手を入れない
- 画風・ジャンル・操作方法がユーザーの指定とスキルの資料で食い違ったら、ユーザーの指定を採る
- 結果が大きく変わる選択（2D か 3D か、1人用か対戦か など）が決まっていないときだけ質問する。それ以外は自分で決めて、報告で書く

## 2. 設計メモ（新規作成・大きな改修のときだけ）

プロジェクトの `artifacts/design.md` に、次の3つを短く書く。部分修正なら書かず、既存のメモがあれば更新する。

- **ブリーフ**: 一言でどんな体験か／主な操作／5〜30秒ごとに繰り返すこと／数分で何が変わるか／どう負けてどう再挑戦するか／上手い人は何が違うか／今回やらないこと
- **コアループ**: 「プレイヤーは [操作] で [目的] を目指し、[圧力] がリスクになる。成功すると [報酬]、失敗すると [代償/リトライ]」
- **ステージ・遭遇の計画**: 開始位置、最初の判断・脅威・報酬、難度がどう上がるか、危険の予告の仕方

「かっこいいシーンを歩き回れる」は設計ではない。判断・圧力・結果が1つ以上入っていること。

ジャンルごとの定石が欲しいときは `references/genre-design.md` を読む（ランナー・レース・シューター・タワーディフェンス・パズルなど）。

## 3. 実装

**空のフォルダから始めて Vite + TypeScript が合うなら**、雛形を使ってよい。

```bash
python scripts/create_threejs_game.py ./my-game     # --force で空でないフォルダにも上書きコピー
cd my-game && npm install && npm run dev            # http://127.0.0.1:5188（雛形の vite.config.ts で固定）
```

雛形は「リレーを集めるだけ」の最小ゲームで、入力（キーボード＋タッチ）・固定順の更新ループ・HUD・シード付き乱数・検証用フックが入っている。**中身は例なので、ゲームに合わなければ遠慮なく消して書き換える。** 残す価値があるのは次の2つ。

- `window.__THREE_GAME_TEST_HOOKS__`（`seed` / `setState` / `setPausedForScreenshot` など）。検証で状態を再現するのに使う。状態名はゲームに合わせて自由に決める
- ゲーム中の乱数をすべてシード付き乱数（`src/utils/random.ts`）から取ること。撮影と自動操作の再現性がこれで保たれる

既存プロジェクトや雛形を使わない場合も、上の2つは同じ考え方で入れておくと検証が楽になる。入れないなら、検証は実際の入力操作だけで行う。

実装は「いつでも遊べる状態」を保ちながら小さく足す: 入力 → 状態 → エンティティ → 当たり判定 → フィードバック（HUD・音・演出）。1つの代表的な場面が実際のカメラで遊べてから、敵やステージを増やす。

必要になったら読む資料:

| ファイル | 読むとき |
|---|---|
| `references/game-feel.md` | 動くが気持ちよくない。ヒットストップ・画面の揺れ・イージング・音と映像の同期を足すとき |
| `references/physics-engine-selection.md` | 物理（車両・転がる球・キャラクターコントローラ・センサー）を入れる・変えるとき |

## 4. 検証ループ

```
for 周回 in 1..3:
    npm run build（型チェック込み）
    開発サーバーを起動し、見せたい状態ごとにキャンバスを撮影する
    撮影画像を自分の目で見る（画面外への切れ・文字の折り返し・真っ黒/真っ白）
    実際のキー入力で「主な操作 → 報酬 → 失敗 → リトライ」を1回通す
    if 完了条件をすべて満たす: break
    if 前の周と同じ不具合: 同じ直し方を繰り返さず、原因を疑い直すかユーザーに相談する
    見つかった箇所だけを直す
else:
    残った不具合と試したことを報告する。直ったとは書かない
```

撮影（雛形のゲームならプロジェクト内に同じスクリプトがある）:

```bash
node scripts/inspect-threejs-canvas.mjs --url http://127.0.0.1:5188 --state <状態名> --run-id pass-1 --out artifacts/qa
# --mobile でモバイル表示、--seed <n> で乱数固定、--state 省略で今の画面だけ撮る
```

出力は `<out>/desktop-<状態名>.png` と同名の `.json`（`consoleErrors`・`pageErrors`・色の分布などの指標）。キャンバスが空、またはエラーがあると終了コード 1。周回ごとに `--run-id` と `--out` を変え、前の周の結果を使い回さない。初回は Playwright のブラウザが要る（`npx playwright install chromium`）。

実入力の操作は、Playwright でページを開き `page.keyboard.down/up` で操作して、`window.__THREE_GAME_DIAGNOSTICS__` のスコアや状態が変わるかを読む（書き方は `references/playtest-bot.md`、雛形の `tests/bot-playtest.template.ts`）。フックが無いゲームなら画面の撮影で変化を確かめる。

**完了条件**（すべて満たしたら抜ける）:

- ビルドと型チェックが通る
- 撮影したすべての状態で `consoleErrors` と `pageErrors` が空、終了コード 0
- 撮影画像を見て、プレイ領域の切れ・HUD の崩れがない
- 実際の入力で、主な操作が効く・報酬で状態が変わる・失敗が起きる・リトライできる、の4点を確認した

アニメーション・見た目の回帰テスト・公開用ビルドまで頼まれたときは、`references/visual-test-harness.md`（撮影の基準画像・動きの確認）と `references/release-checks.md`（モバイル・本番ビルド・公開時の落とし穴）を読む。

## 5. 報告

先頭に「何を作ったか・動くか・URL・操作方法」。続けて、確かめたこと（ビルド、撮影した状態、実入力で通した流れ）と、確かめていないこと・残った不具合を書く。大きく作ったときは設計メモの場所も添える。

開発サーバーは起動したままにして、URL をユーザーのブラウザで開く。

## 禁止事項

- 撮影や自動操作を通すために、ゲーム本体のロジックを検証専用の分岐で書き換えない（フックは状態を作るだけにする）
- 失敗している状態を撮影対象から外して完了条件を満たしたことにしない
- 動かしていない操作・状態について「動く」と書かない

## スクリプト

| スクリプト | 使い方 | 終了コード |
|---|---|---|
| `scripts/create_threejs_game.py` | `python scripts/create_threejs_game.py <作成先> [--force]`。`assets/threejs-vite-game/` をコピーし、package.json の name を作成先の名前に書き換える | 0 成功／それ以外は雛形が無い・作成先が空でない（メッセージを表示） |
| `assets/threejs-vite-game/scripts/inspect-threejs-canvas.mjs` | 上の「撮影」。雛形から作ったゲームでは `npm run inspect:canvas -- <引数>` でも呼べる | 0 成功／1 キャンバスが空・エラーあり・状態フックの失敗 |

依存: Python 3（標準ライブラリのみ）、Node.js 20 以上、npm。撮影と自動操作は Playwright（雛形の devDependencies に入っている）。
