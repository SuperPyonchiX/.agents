# AGENTS.md / CLAUDE.md Advisor

常時読み込みされる指示ファイルを「作る」と「削る」の両方から扱う。最初に**モードを1つに決める**。

| リポジトリの状態 | モード | 成果物 |
|---|---|---|
| AGENTS.md / CLAUDE.md が無い、または数行の雛形しか無い | **導入診断** | 導入提案書1枚（AGENTS.md 草案を含む） |
| 既に運用中で、行数が増えている・効いていない | **監査** | 指摘台帳と、判定済み指摘の適用 |

判定に迷う場合（雛形はあるが中身が薄い）は導入診断を選び、既存の記述は診断シートの「既存のAI設定」に取り込む。

共通の前提: チームは Claude Code / GitHub Copilot / Codex / Gemini CLI のどれを使うか分からない。**全ツールが読む資産（AGENTS.md、`.agents/skills/` の Agent Skills、リポジトリ内ドキュメント）を主とし、ツール固有機能は分離した節に書く。** CLAUDE.md は AGENTS.md を参照するだけの薄い形にする。

---

## モード A: 導入診断

失敗しやすいのは、(1) リポジトリを見ずに一般論の提案書を書く、(2) 特定ツールでしか動かない構成を勧める、(3) 一度に全部入れる提案をして定着しない、の3つ。**提案は必ずリポジトリで確認した事実に紐づけ、段階導入で書く。**

### A1. リポジトリを診断する

診断シートを埋める。**確認した事実（ファイルパス・コマンド）を必ず添える。**

| 診断項目 | 見るもの |
|---|---|
| 言語・規模 | 主要言語、ファイル数、モジュール構成 |
| ビルド・テスト | コマンドが何か、README等に書かれているか、実行時間 |
| CI | 有無、何をチェックしているか（エージェントの出力を機械検証できるか） |
| 既存ドキュメント | README・設計書・手順書の所在と鮮度 |
| 既存のAI設定 | CLAUDE.md / AGENTS.md / .github/copilot-instructions.md 等の有無 |
| 定型作業 | コミット規約、レビュー手順、リリース手順など、繰り返される作業（スキル候補の種） |
| 機密・制約 | 社外送信してはいけない情報、ライセンス制約、規制要件 |

対象がモノレポで巨大な場合は、最初に効かせたいサブプロジェクトを1つ選んでもらい、そこに絞る。

### A2. ヒアリングする

リポジトリから読めないことを2〜3問ずつ聞く: チームの人数と AI 利用経験 / 使う予定のツール / 最初に効かせたい作業（レビュー・実装・ドキュメント）/ セキュリティ上の制約（社内ポリシー）。

### A3. 提案書を書く

章立ては固定（追加・削除しない）:

1. **現状診断** — 診断シートと、導入に効く強み・障害
2. **段階導入プラン** — Phase 1（AGENTS.md 整備＋ビルド・テストコマンドの明文化）→ Phase 2（定型作業のスキル化 2〜3本）→ Phase 3（CI 連携・チーム展開）。各 Phase に完了条件を書く
3. **AGENTS.md 草案** — 実際に使える形の全文。診断で確認した事実だけで書き、推測箇所は TODO と明記
4. **スキル候補一覧** — 定型作業ごとに「スキル名案 / 何をするか / 効果の根拠（その作業が繰り返されている証拠）」。作成は workflow-skill-architect で別途
5. **運用ルール** — レビュー必須の範囲、コミットの扱い、機密の扱い、うまくいかないときの見直し先
6. **ツール固有の補足** — ツールごとに1節。使わないツールの節は読まなくてよいと明記

保存先はユーザーに確認する（既定の提案: 対象リポジトリの `docs/ai-adoption-proposal.md`）。

**完了条件**: 6章すべてが埋まった提案書を提示し、Phase 1 に着手するか否かの判断をユーザーから得たこと。

### A の禁止事項

- リポジトリを解析せずに一般論だけで提案書を書くこと
- 特定ツールの独自機能を Phase 1 の必須項目に置くこと
- AGENTS.md 草案に、診断で確認していないコマンドや規約を書くこと（推測は TODO と明記）

## モード B: 監査

指示ファイルは1行残らず毎セッションのコンテキストを消費する。仕事は「消せる行を見つけて、勝手に消さずに判定を仰ぐ」こと。失敗しやすいのは、(1) 一括で書き換えて運用上の理由がある記述を壊す、(2) 短くすることが目的化して発火や安全に効いている指示を削る、の2つ。**適用は必ず1件ずつユーザー判定を経る。**

```
対象ファイルを読み、指摘台帳を作る（B1〜B2）
for 各指摘（重要度順）:
    指摘・根拠・修正案を提示し、ユーザー判定を得る
    判定どおりに適用する（削除 / 修正 / スキル切り出し / 維持）
    台帳の状態を更新する
完了条件: 台帳の全件が「クローズ（適用済み or 維持と判定）」になったこと
```

上限はない（件数分で必ず終わる）。ユーザーが「残りは任せる」と言った場合のみ残件をまとめて適用してよいが、**削除の適用前に削除対象の全文を提示する**。

### B1. 対象と現状を確定する

CLAUDE.md / AGENTS.md / `.claude/` 配下の指示ファイルを列挙し、行数と参照関係（@import や「〜を参照」）を把握する。行数を報告し、どのファイルを監査するか合意する。

### B2. 検査して台帳を作る

`references/audit-checklist.md` を読み、観点ごとに指摘を拾って台帳にする。

```
| # | 対象（ファイル:節） | 観点 | 指摘 | 提案 | 状態 |
|---|---|---|---|---|---|
| 1 | AGENTS.md: ディレクトリ構成 | 導出可能 | ls で分かる内容の羅列 | 削除 | 未判定 |
| 2 | CLAUDE.md: レビュー手順 | 手順書化 | 12行の手順に育っている | スキル切り出し | 未判定 |
```

台帳を全件提示してから判定ループに入る。**台帳提示前に修正を始めない。**

### B3. 判定ループを回す

重要度順（削減行数が大きい順・誤動作リスクが高い順）に1件ずつ、指摘・根拠・修正案（削除なら削除対象の全文、修正なら before/after）を示して判定を得る。

- 「スキル切り出し」と判定された節は、ここで切り出しまで行わない。対象節と切り出し方針をメモにまとめ、workflow-skill-architect で別途作ることを提案する
- 判定に迷っているユーザーには「維持」を提案する。消して困る指示は戻しにくい
- 指示ファイル間の矛盾を見つけたら台帳に「矛盾」として積み、どちらを正とするかの判定を仰ぐ

### B4. 結果を報告する

before/after の行数と削減見積り、切り出し候補として残った節の一覧を報告する。対象が git 管理下ならコミットの要否を確認する。

### B の禁止事項

- ユーザー判定を得ずに削除・書き換えを適用すること（台帳作成のための読み取りは自由）
- 発火条件・安全に関わる指示（禁止事項、確認ゲート）の削除を提案する際に、リスク注記を省くこと
- 短さを理由に、根拠を添えず削除を推すこと。1件ごとに「なぜ消しても動作が変わらないか」を書く
