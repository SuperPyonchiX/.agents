# AUTOSAR C++14 / CERT C++ — レビューする側の視点

R2（目視レビュー）で読む。**毎回読むこと。**

ここに載せているのは規格そのものではなく、**レビューで判断が要る箇所の整理**である。プロジェクトが規格文書や静的解析ツール（Coverity / PC-lint / clang-tidy の autosar・cert チェッカ等）を持っている場合は、**そちらが優先**。ツールがあるなら R0 で確認し、出力を `--tidy-log` で取り込む。

## 方針3点が効いてくる場所

R0 で確定させた `work/review-scope.json` の `policy` によって、同じコードが違反にも正当にもなる。

| 方針 | `forbidden` のとき | `allowed` のとき見るところ |
|---|---|---|
| `exceptions` | `throw` / `try` / `catch` はすべて違反（POL-001）。エラーは戻り値で表す | 例外安全性（強い保証か基本保証か）、デストラクタから例外を投げていないか、`noexcept` 関数から漏れていないか |
| `dynamic_memory` | 生の `new` / `delete` と `malloc` 系はすべて違反（POL-002 / BAN-003） | 確保失敗の扱い、断片化、確保が周期処理の中に無いか。`init_only` なら**初期化フェーズ限定か**を目視で確認する |
| `virtual_rtti` | `dynamic_cast` / `typeid` は違反（POL-003）。仮想関数も使えないので、依存の差し替えはテンプレート（静的ポリモーフィズム）で行う | 多態基底のデストラクタが `public virtual` か `protected` 非 virtual か、仮想関数呼び出しのコストが周期処理に見合うか |

**`unknown` のまま R2 に入らない。** 判断の土台が無い状態で「例外を使っている」と指摘すると、レビュー全体の信用が落ちる。

## スキャナ候補の採否判断

`medium` の候補は、次の観点で1件ずつ判定する。判定結果は台帳に `fixed` / `open` / `rejected` として残す。

| ルールID | 採用してよい | 不採用にしてよい（`rejected`） |
|---|---|---|
| `TYPE-001` | 内部のロジックで幅を意識すべき値に `int` / `long` を使っている。ビット演算の対象。プロトコルのフィールド | 外部 API のシグネチャに合わせた宣言。`main` の戻り値。標準ライブラリの戻り値受け |
| `TYPE-002` | 計算結果の一致判定に `==` を使っている | センチネル値（`NaN` 検査、初期値との比較）で、ビット一致が意図されている |
| `CLS-001` | 意味の違う型からの暗黙変換が通ってしまう | 単一引数だが可変長テンプレート引数の展開。意図的な変換型（ラッパ） |
| `CLS-002` | 多態的に `delete` されうる基底で、デストラクタが非 virtual | 基底クラスがレビュー範囲外にあり判定できない（**理由に「判定不能」と書く**）。多態的に破棄されないことが設計で保証されている |
| `CLS-003` | 手動でリソースを持つクラスで、コピー・ムーブの一部だけ宣言されている | メンバがすべて RAII 型で、Rule of Zero が成立している（この場合は**全部消す**のが正解で、一部だけ残っているなら採用） |
| `CLS-004` | 基底の同名仮想関数を上書きしている | 派生クラスで**新規に**導入した仮想関数。基底が範囲外で判定不能 |
| `FUNC-001` | 深さが入力に依存する。上限が文書化されていない | 深さが型で決まる（テンプレート再帰、木の高さが定数）。上限が `@note` に書かれている |
| `MNT-002` | 意味のある値が使用側に直接書かれている。同じ値が複数箇所に散っている | ビットシフト量、配列の次元、`0` オリジンの添字、既に名前の付いた定数の定義行 |
| `MNT-003` | 責務が複数ある。分割してもテストが壊れない | ステートマシンの `switch` など、分割するとかえって読めなくなる構造 |
| `CTRL-004` | 意図が読み取れない。バグの可能性がある | 意図的で、コメントで明示されている（この場合はスキャナが既に抑止している） |

**`rejected` を空欄で済ませない。** 次回また同じ候補が出たときに、同じ議論をやり直すことになる。

## スキャナが検出できない規約違反

正規表現では届かないが、規約上は明確に違反であるもの。**目視で当てる。**

### 型と変換

- 符号付き ↔ 符号なしの混在比較（`static_cast` を挟まずに `int` と `size_t` を比較していないか）
- 縮小変換（`std::int32_t` を `std::int16_t` に代入する経路。範囲検査があるか）
- `static_cast` を使っているが、**変換が安全であることが保証されていない**箇所
- `reinterpret_cast`（原則禁止。使う場合は理由が `@note` にあるか）

### 初期化

- 全メンバがコンストラクタの**全経路で**初期化されているか
- メンバ初期化子リストの順序が宣言順に一致しているか（ずれると読み違える）
- 変数の宣言と初期化が離れていないか
- 配列・構造体の一部だけ初期化していないか

### 関数

- 例外を投げない関数に `noexcept` が付いているか（組込みでは大半がこれに当たる）
- 全経路で戻り値を返しているか（到達しないはずの経路も既定値を返して終える）
- 入力引数を関数内で再代入していないか
- 戻り値の無視を許さない旨が `@note` に書かれているか（C++14 に `[[nodiscard]]` は無い）

### クラス

- 仮想関数をコンストラクタ・デストラクタ内から呼んでいないか（派生の実装は呼ばれない）
- 多重継承がインタフェース（純粋仮想のみ）に限られているか
- `override` した関数の**既定引数**を変えていないか（既定引数は静的に解決される）

### 前処理

- マクロで条件付きコンパイルした先が、両方ともビルド可能か
- ヘッダのインクルードガードが一意か（コピー元の名前が残っていないか）
- `#include` の順序が、依存を隠していないか（自分のヘッダを最初に置いているか）

## 規約とテスト容易性がぶつかったとき

規約を満たしていてもテストが書けないコードは、レビューで指摘してよい。典型と解き方。

| ぶつかる点 | 解き方 |
|---|---|
| 仮想関数禁止でモック化できない | テンプレートパラメータで依存を差し替える（静的ポリモーフィズム） |
| 例外禁止で異常系を検証できない | 戻り値のエラーコードで表し、`@retval` に列挙する。それがテスト観点になる |
| 動的メモリ禁止で可変長データを扱えない | 固定長バッファ + 長さで表し、境界値テストの対象にする |
| ハードウェアに直接触っていてテストできない | レジスタアクセスを薄い層に閉じ込め、ロジック側をその層に依存させる |
| private をテストしたい | テストしない。public 経由の経路として観点に含める |

## 逸脱を認めてよい条件

**自分で承認しない。** `accepted` にできるのはユーザーの了承を得たときだけで、重大度「高」はその場で個別に提示する。

そのうえで、ユーザーに「逸脱として残す」提案をしてよいのは次のいずれかに当たるときだけ。

- 外部 API・ベンダ提供ヘッダのシグネチャに合わせるために、規約側を曲げざるをえない
- 規約に従うと実行時間・スタック・コードサイズの制約を満たせない（**測定値を根拠として示せる場合のみ**）
- ハードウェア仕様が直接そう要求している（レジスタのビット位置、エンディアン）

逸脱を残す場合、**コード側に理由が `@note` として残っているか**を必ず確認する。台帳にだけ書いて、コードから理由が読めない状態にしない。次に読む人には台帳が無い。
