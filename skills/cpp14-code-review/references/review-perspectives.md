## 当て方

**これは他人が書いたものである。** 各観点について、**不合格な箇所を列挙する**。問題がないことを確認するのではなく、問題を探す。

1観点につき最低限、**「どこを見てそう判断したか」を1行で書ける状態**にする。書けないなら、その観点は当てていない。指摘が出なかった観点も、見た箇所を `work/review-report.md` の観点別所見に1行残す。

差分レビュー（`mode: "diff"`）でも、**ファイル全体を読んでから差分を見る**。差分行だけを見ると、変更が既存の前提を壊しているかどうかが判断できない。ただし**差分の外に見つけた問題は `区分` を `差分外` にして分けて記録する**。混ぜると、直すべき差分の話が流れる。

## 1. 設計意図との一致

コードが規約に沿っていても、設計と違うことをしていれば意味がない。**設計書やヘッダの Doxygen コメントが手に入る場合は、それを仕様の出典として当てる。**

- [ ] Doxygen の `@brief` / `@pre` / `@retval` と、実装の振る舞いが一致しているか
- [ ] `@retval` に書かれた戻り値が**全部返りうる**か。書かれていない値を返していないか
- [ ] `@pre` を満たさずに呼ばれたときの振る舞いが、仕様どおりか（未定義のまま進んでいないか）
- [ ] 変更に伴って Doxygen コメントが更新されているか。**コードだけ変わってコメントが古いまま**になっていないか
- [ ] 単位のある値（時間、回転数、電圧、圧力）の単位が、呼び出し側と一致しているか
- [ ] 設計に無い機能が勝手に足されていないか

**設計書が手に入らない場合**は、この観点を「判定不能」として `work/review-report.md` に明記する。推測した設計を根拠に指摘しない。

## 2. エラー処理と異常系

組込みで最も事故になりやすい領域。**指摘の重大度は原則「高」**。

- [ ] 戻り値でエラーを返す関数の**呼び出し側が、戻り値を確認しているか**（握りつぶしていないか）
- [ ] エラーを検出したあと、処理を続行してよいのか。続行するなら、その状態で後続が成立するか
- [ ] 出力引数が、失敗時にどうなるか（変更しない / 未定義 / 既定値）が定まっていて、そのとおりか
- [ ] 早期 return でリソース解放や状態の巻き戻しが漏れていないか
- [ ] エラーコードを上位に伝える途中で、情報が潰れていないか（複数の失敗が同じ値になっていないか）
- [ ] ハードウェアの応答待ちにタイムアウトがあるか。無限に待つ経路が無いか
- [ ] 除算の前に 0 の検査があるか
- [ ] 符号付き整数の加減乗算で、オーバーフローしうる箇所に範囲検査があるか（**未定義動作**）
- [ ] 配列・バッファへのアクセスに境界検査があるか。長さと添字の型が一致しているか
- [ ] ポインタの参照外しの前に、null でないことが保証されているか

## 3. 責務と構造

- [ ] 1つの関数が1つのことをしているか。`MNT-003`（関数が長い）の候補が出た箇所は特に見る
- [ ] 変更が既存の抽象を壊していないか（本来クラスの内側にあるべき知識が、呼び出し側に漏れていないか）
- [ ] 同じ処理の重複が増えていないか。既にある関数で足りるのに新規に書いていないか
- [ ] 条件分岐のネストが深くなっていないか。早期 return で平坦にできないか
- [ ] 依存が注入されているか。具象型を関数内で直接生成していないか（**していると単体テストが書けない**）
- [ ] public に出す必要のないものが public になっていないか
- [ ] ヘッダに実装の詳細（private の型、内部定数、不要な `#include`）が漏れていないか

## 4. リソースとライフタイム

- [ ] 確保したリソース（ハンドル、ロック、DMA チャネル、ペリフェラル）が、全経路で解放されるか
- [ ] RAII で持てるものを、手で獲得・解放していないか
- [ ] 参照・ポインタが、指す先より長く生きていないか（ローカル変数のアドレスを返していないか）
- [ ] コンテナや配列への参照を保持したまま、要素を変更・再確保していないか
- [ ] 静的オブジェクトの初期化順序に依存していないか（翻訳単位をまたぐ初期化順序は不定）
- [ ] `POL-002` の候補が出た箇所は、確保が初期化時に限られているか。周期処理の中で確保していないか

## 5. 割込み・並行安全性

**スキャナは一切見られない。ここは必ず目視で当てる。**

- [ ] 割込みハンドラとメインループが共有する変数に、`volatile` と適切な排他があるか
- [ ] `volatile` だけで済ませていないか（`volatile` は最適化を抑えるだけで、アトミック性は保証しない）
- [ ] 複数バイトの共有データ（構造体、64bit 値）の読み書きが、途中で割り込まれても壊れないか
- [ ] 割込みハンドラの中で、ブロックしうる処理（ロック取得、待ち、長いループ）をしていないか
- [ ] ロックの獲得順序が一貫しているか（デッドロックの経路が無いか）
- [ ] クリティカルセクションが必要以上に長くないか
- [ ] 再入しうる関数が、静的変数・グローバル変数を持っていないか

## 6. 実行時間とスタック

- [ ] ループの繰り返し回数に上限があり、静的に見積もれるか
- [ ] 周期処理の中に、実行時間が入力に依存する処理が無いか
- [ ] `FUNC-001`（再帰）の候補が出た箇所は、深さの上限が保証されているか
- [ ] 大きなローカル配列・構造体をスタックに置いていないか
- [ ] 割込みコンテキストのスタック消費が見積もられているか

## 7. 移植性とハードウェア依存

- [ ] エンディアン依存の解釈をしていないか（バイト列を構造体にそのままキャストしていないか）
- [ ] 構造体のパディングやアラインメントを前提にしたサイズ計算をしていないか
- [ ] ビットフィールドの並び順に依存していないか（実装定義）
- [ ] レジスタアクセスが1箇所に閉じているか。ロジックの中に直接アドレスが書かれていないか
- [ ] `char` の符号の有無に依存していないか（実装定義）
- [ ] シフト量が型の幅未満か（幅以上のシフトは**未定義動作**）

## 8. テスト十分性

レビュー対象に単体テストが含まれる場合、または含まれるべき場合に当てる。

- [ ] 変更した関数に対応するテストがあるか。**無いなら、それが指摘**
- [ ] 追加されたテストが、期待結果を**具体値**で検証しているか（`EXPECT_TRUE(true)` のような無意味な検証が無いか）
- [ ] 期待値が実装の定数式をそのまま持ち込んだものになっていないか（実装と一緒に間違える形）
- [ ] 引数の有効範囲に対して、下限-1 / 下限 / 上限 / 上限+1 が取られているか
- [ ] 異常系（`@retval` の失敗値それぞれ）に対応するテストがあるか
- [ ] `DISABLED_` / `GTEST_SKIP()` / コメントアウトされたテストが無いか
- [ ] テスト間で状態を共有していないか（`static` / グローバル / 実行順依存）

## 9. 可読性と命名

**重大度は原則「低」〜「中」。** ここばかり指摘して上の観点が薄いレビューは、レビューとして不合格。

- [ ] 命名が設計の用語と一致しているか（設計が「目標回転数」なのにコードが `val` になっていないか）
- [ ] 単位が名前に含まれているか（`timeout` ではなく `timeout_ms`）
- [ ] 否定形の bool 名になっていないか（`is_not_ready` は二重否定を生む）
- [ ] コメントが「何をしているか」ではなく「なぜそうするか」を書いているか
- [ ] `MNT-002`（マジックナンバー）の候補のうち、意味のある値が定数化されているか
- [ ] 変更に伴って、意味の変わった変数名・コメントが残っていないか
