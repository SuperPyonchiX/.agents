# 指摘の書き方と重大度の判定

R3（台帳化）で読む。**毎回読むこと。**

レビューの価値は、見つけた数ではなく**相手が直せるかどうか**で決まる。「わかりにくい」で終わる指摘は、受け手に判断を丸投げしているだけで、結局直らない。

## 指摘の4要素

1指摘につき、次の4つがそろっていること。1つでも欠けたら台帳に登録しない。

| 要素 | 内容 | 欠けるとどうなるか |
|---|---|---|
| **場所** | ファイルと行（範囲なら `42-58`） | どこの話か特定に時間がかかる |
| **基準** | どの規約・設計・観点に反しているか | 好みの押し付けに見える |
| **影響** | 何が起きうるか。具体的な失敗シナリオ | 直す優先度が判断できない |
| **是正案** | どう直せばよいか。選択肢が複数あるならそれも | 受け手が同じ調査をやり直す |

### 書き換えの例

| 悪い | 良い |
|---|---|
| この関数はわかりにくい | `Update()` が 120 行あり、状態遷移・センサ読み取り・ログ出力の3つを担っている（MNT-003）。状態遷移だけを切り出せば、遷移表の単体テストが書ける |
| キャストが良くない | 42行目の `(int)raw` は double からの縮小変換で、`raw` が `INT32_MAX` を超えると**未定義動作**になる（CAST-001）。範囲検査のうえ `static_cast<std::int32_t>` にする |
| エラー処理を検討してください | 58行目で `SetSpeed()` の戻り値を確認せずに次へ進んでいる。設定失敗時も回転指令が出るため、意図しない速度で動作する。戻り値が false なら `Stop()` して早期 return する |
| マジックナンバーです | 120行目の `3000` が何を表すか読み取れない。同じ値が 88 行目にもある。片方だけ変更されると不整合になるので `kMaxRpm` として定数化する |

**是正案が思いつかない場合は、そう書く。** 「この経路で何が正しいのか、設計から読み取れなかった。意図を確認したい」は、有効な指摘である。曖昧な言い方で誤魔化すより良い。

## 重大度の判定

| 重大度 | 基準 | 例 |
|---|---|---|
| **高** | 仕様・安全性に影響する。未定義動作、誤動作、リソースリーク、データ競合を引き起こしうる | 未初期化変数の使用、戻り値の握りつぶし、境界検査なしの配列アクセス、割込みと共有する変数の排他漏れ、符号付きオーバーフロー |
| **中** | 動作は正しいが、保守性・テスト容易性を損なう。将来のバグの温床になる | 責務過多、依存の直接生成（テスト不能）、重複、抽象の漏れ、Rule of Five 不整合 |
| **低** | 表記・可読性の問題。動作にも保守性にも直接は影響しない | 命名、コメント、書式、単位の明示 |

**迷ったら上げる。** ただし上げた根拠（どう誤動作しうるか）を書けないなら、それは「中」以下である。

`rejected`（スキャン候補の不採用）には重大度を付けない（`—`）。指摘ではないため。

### 「高」の扱い

- R4 の報告で**全件を個別に列挙する**。件数が多くても省略しない
- `accepted`（逸脱承認）にする場合は、その場でユーザーに個別提示して了承を得る。**まとめて承認を取らない**
- 「高」が残っている状態で「レビュー完了」と報告しない

## 差分レビューでの区分

`mode` が `diff` のとき、指摘は2つに分ける。

| 区分 | 対象 | 扱い |
|---|---|---|
| `差分` | 変更行、および変更によって振る舞いが変わる箇所 | 今回の修正対象 |
| `差分外` | 対象ファイル内だが、元からあった問題 | **今回の修正を求めない。** 別課題として起票を提案する |

差分外の問題を差分の指摘として出すと、レビューが「ついでに直せ」の場になり、本来の変更の議論が流れる。**見つけたことは記録し、扱いは分ける。** ただし重大度「高」の差分外は、R4 の報告で別枠として提示し、対応の判断をユーザーに仰ぐ。

## 指摘0件だったとき

**「特に問題ありません」で終わらせない。** 当てた観点と、どこを見てそう判断したかを1行残す。

```
| RV-000 | 全体 | — | 指摘なし | 目視 / 割込み安全性 | — | — | — | fixed | 共有変数は g_status のみで、読み書きが割込み禁止区間に入っていることを確認 |
```

これが無いと、レビューをしたのか省いたのかが後から区別できない。

## 書いてはいけない指摘

- **推測を根拠にしたもの** — 「たぶん〜だと思うので」。設計が読めないなら「判定不能」と書く
- **レビュー範囲外のファイルを根拠にしたもの** — 範囲の追加は R0 に戻って合意する
- **好みの押し付け** — 基準（規約・設計・観点表）を示せないものは指摘にしない
- **人に向けたもの** — コードについて書く。書いた人について書かない
- **同じことの繰り返し** — 同一原因で複数箇所に出ているなら1指摘にまとめ、対象欄に全箇所を並べる
- **ついでの修正** — このスキルはレビューであって修正ではない。コードを直すのは R5 で、依頼を受けてから
