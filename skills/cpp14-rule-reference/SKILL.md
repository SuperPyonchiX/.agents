# C++14 Rule Reference

規約の記憶に頼らず、手元の資料から根拠を引くためのスキル。仕事は「番号→内容」「事象→番号」の2方向の引き当てだけ。失敗しやすいのは、資料を確認せずに学習知識でルール本文を復元してしまうことで、番号ずれ・条文の言い換えが混入する。**資料で確認できたことと、できなかったことを必ず区別して返す。**

## 資料の置き場（前提）

規約資料はこのスキルの `local/` ディレクトリに置く。**著作権保護された資料のため git 管理外**（.gitignore 済み。入手元と復元手順は `vendor/NOTICE.md` を参照）。

```
skills/cpp14-rule-reference/local/
├── autosar/   # AUTOSAR C++14 ガイドライン（PDF またはテキスト抽出済みファイル）
├── cert/      # CERT C++ 関連資料
└── inhouse/   # 社内規約・適用プロファイル（あれば）
```

**`local/` が空、または該当する規約の資料が無い場合は、引き当てを始めずに止まり、資料の配置をユーザーに依頼する。** 学習知識だけで代用して回答しない。ただし CERT C++ は公開 Wiki（SEI CERT C++ Coding Standard）があるため、資料が無い場合に限り Web 上の該当ページを参照してよい（参照した URL を出典として明記する）。

初回利用時は `local/` の中身を一覧し、どのファイルがどの規約に対応するかを確認してから引き当てに入る。

## 手順

### A. 番号から引く（「A5-1-1 とは？」）

1. ルール番号の体系から規約を判別する（A/M＋数字 → AUTOSAR C++14、3文字＋2桁-CPP（例 EXP34-CPP）→ CERT C++）
2. `local/` の該当資料から番号を検索する。PDF はページを絞って読み、テキストならGrepする
3. 見つかった条文を出力形式に沿って返す

### B. 事象から引く（「この書き方は何番に違反する？」）

1. 事象を規約の語彙に言い換える（例: 「生ポインタのnewの結果を放置」→ リソース管理・所有権）
2. 候補となるルール番号を挙げる（この段階では学習知識を使ってよい。**候補出しまで**）
3. 候補の各番号を手順Aで資料と突き合わせ、**条文を確認できたものだけ**を該当として返す。確認できなかった候補は「資料で未確認」と明示して分ける

### C. 複数規約の突き合わせ（「AUTOSARとCERTの両方の該当ルールは？」）

規約ごとに手順A/Bを行い、対応表の形で返す。片方にしか該当が無い場合はその旨を書く。

## 出力形式

1件ごとに次の形で返す。複数件はこの形を並べる。

```
- ルール番号: A5-1-1（AUTOSAR C++14）
- 分類: required / advisory（資料の記載どおり）
- 要旨: <条文の要点を1〜2文。資料の記述に忠実に>
- 根拠: <なぜこのルールがあるか。Rationale の要約>
- 出典: local/autosar/<ファイル名> p.<ページ> （CERT公開Wikiなら URL）
- 確認状態: 資料で確認済み / 資料で未確認（学習知識のみ）
```

## 他スキルからの利用

cpp14-code-review・cpp14-defect-analysis・implementation-plan-grill・static-analysis-triage の実行中に規約の根拠が必要になったら、このスキルの手順で `local/` を引き、上の出力形式で根拠を添える。呼び出し元の工程は中断しない（引き当ては1問1答で完結する）。

## 禁止事項

- 資料を確認していないルール本文を、確認済みであるかのように断定して返すこと
- ルール番号だけを答えて根拠と出典を省くこと（このスキルの存在意義が根拠の提示にある）
- `local/` の資料を要約したファイルを git 管理下に作ること（要約でも派生物として著作権が及ぶ。作業用の抜き書きは local/ 内か会話にとどめる）

## 想定外の扱い

- 番号が資料に見つからない場合: 版の違い（規約のリビジョン）の可能性を伝え、資料の版をユーザーに確認する
- 社内プロファイルで適用除外されているルールの可能性がある場合: `local/inhouse/` に適用プロファイルがあれば突き合わせ、無ければ「社内での適用有無は未確認」と添える
