# レビューを頼むときの見せ方

ユーザーにレビューを頼むたびに読む。目的は、ユーザーが短い時間で判断でき、何を判断したかが後から追えること。

根拠: 長い仕様の Markdown はコードよりレビューが重いという報告（[Böckeler, 2025-10](https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)）と、変更は小さく、文脈と確認の証拠を添えて渡すべきという勧め（[Willison, Agentic Engineering Patterns](https://simonwillison.net/guides/agentic-engineering-patterns/)）。以下の具体的な形（5つまで、番号で答える等）はそれを受けたこのスキルの設計で、出典が直接定めたものではない。

## 1回の依頼の形

`REVIEW_LOG.md` に節を1つ足し、会話では次の順に示す。

1. **見てほしいこと**: 5つまで。判断が要るもの（採否、仕様の選択）を先に、確認だけのもの（誤字、表記）を後に置く。各項目に推奨の答えと理由を1行で添える
2. **前回からの変更**: 2回目以降は、前回の指摘ごとに「どこを（ファイル:節）どう変えたか」を1行ずつ。指摘の ID を付ける
3. **全文の場所**: レビュー対象のファイルのパス。会話に全文を貼らない

答え方も添える。「1 は推奨どおり、3 は〜に変えて、のように番号で答えてもらえれば十分です」。

## 粒度

- 1回に見せるのは、1つの判断単位（提案表、1つの設計の節、1つの画面）にする。複数をまとめて見せない
- 文書が長いときは、全文ではなく、判断が要る箇所の抜粋と全文のパスを示す
- 変更が多いときは、変更点を「判断が変わったもの」と「表現だけ直したもの」に分けて書く。後者は件数だけでもよい
- コードは差分（`git diff` か、変更前後の抜粋）で見せる。説明だけで済ませない

## 記録の仕方

- ユーザーの指摘は、要約せずにそのまま「指摘」列に写す。言い換えると意図がずれる。言葉の中の `|` は `\|` に、改行は `<br>` に置き換える
- 1つの発言に複数の指摘があれば、1件1行に分ける
- 指摘への対応は「何を・どこで」まで書く（「修正済み」だけにしない）
- 指摘の意図が読み取れないときは、推測で直さず、状態を「確認待ち」にして聞き返す
- 見送るときは、理由を書き、ユーザーの了承を得てから「見送り」にする
- 自己レビューやサブエージェントのレビューで出た指摘は、ユーザーの指摘と混ぜず「## S<回> <日付> 自己レビュー」の節に ID `S1-1` の形で書く。ユーザーに見せるのは、判断が要るものだけ「見てほしいこと」に載せる
- 残っている指摘の一覧は `check_review_log.py` の出力で見る。手で一覧を作らない

## やらないこと

- 指摘を記録せずに直すこと（後から何を判断したか追えなくなる）
- 1回の依頼で6つ以上の判断を求めること。多ければ判断の重い順に分けて、複数回にする
- 未対応・確認待ちを残したまま「レビュー完了」と報告すること。`check_review_log.py` が終了コード 0 になってから報告する
