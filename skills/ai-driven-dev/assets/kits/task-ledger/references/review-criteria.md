# レビューの観点

`SKILL.md` の手順4d で使う。サブエージェントに渡すときは、このファイル・差分・台帳の該当行だけを渡す。自分で当てるときは、差分を他人が書いたものとして読み、1項目ずつ当てる。

## 進め方

1. 台帳の該当行の「完了条件」を読み、差分がそれを満たすかを先に判定する
2. 下の観点を上から順に当てる。当てはまる指摘が無い観点は飛ばしてよい
3. 指摘を下の「出力形式」で返す。指摘が0件でも、見た観点と結論を1行返す

やらないこと: コードを書き換えない。好みの問題（命名の流儀、書き方の癖）で、リポジトリの既存コードと揃っているものは指摘しない。判断がつかないものは「要確認」として返し、推測で「問題あり」にしない。

## 観点

### 1. 完了条件と範囲

- 差分が台帳の完了条件を満たしているか。満たしていない条件があれば、どれかを書く
- 完了条件に関係のないファイル・行が変わっていないか（範囲外の修正、ついでのリファクタリング、整形だけの大量差分）
- 振る舞いの変更とリファクタリングが混ざっていないか

### 2. テスト

- 追加したテストが、完了条件の振る舞いを実際に確かめているか。実装の中身をなぞっただけ（モックの呼び出し回数だけを見る等）になっていないか
- 実装を壊したら落ちるか。常に通るテスト（assert が無い、例外を握りつぶしている）になっていないか
- 既存のテストが削除・スキップされていないか。期待値が書き換えられていれば、その理由が台帳か差分にあるか
- 正常系だけでなく、完了条件に含まれる異常系・境界値が確かめられているか

### 3. 正しさ

- 境界値（空・0件・1件・最大・負数）、null や未定義の値、文字コード、タイムゾーンで壊れないか
- エラーが握りつぶされていないか。失敗したときに呼び出し元が気づけるか
- 並行・非同期の処理で、順序や共有状態の前提が崩れないか
- 既存の呼び出し元が、変更後の関数・API を前提どおりに使えるか

### 4. 安全

- 秘密情報（API キー、パスワード、トークン）がコード・ログ・テストデータに入っていないか
- 外部入力をそのままシェル・SQL・ファイルパス・HTML に渡していないか
- ユーザーに断りなく外部へ通信・送信する処理が増えていないか

### 5. 読みやすさと保守

- 既存コードの書き方（命名、ファイル構成、エラー処理の流儀）と揃っているか
- 将来の読み手に必要な「なぜ」がコメントか命名で分かるか。逆に、コードを読めば分かることを繰り返すだけのコメントが増えていないか
- 使われていないコード・デバッグ出力・一時ファイルが残っていないか

## 出力形式

```markdown
完了条件: 満たす / 満たさない（満たさない条件: ...）

| # | 重さ | 場所 | 指摘 | 直し方の案 |
|---|---|---|---|---|
| 1 | 必須 | src/import.py:42 | 空行の判定が `\r\n` を考慮していない | `line.strip()` で判定する |
| 2 | 推奨 | tests/test_import.py:10 | 期待値の行数が直書きで意図が読めない | 入力の非空行数から求める |
| 3 | 要確認 | src/import.py:58 | 例外を握りつぶしているが、仕様か分からない | 仕様を確認する |
```

重さは3段階にする。

- 必須: 完了条件を満たさない、テストが振る舞いを確かめていない、正しさ・安全の問題。直すまでコミットしない
- 推奨: 直したほうがよいが、残しても壊れないもの。直さないなら理由を台帳に1行残す
- 要確認: 仕様や意図が分からず判定できないもの。実装した側が仕様を確かめて、必須か推奨か問題なしかに振り分ける
