# AI Adoption Advisor

チームへの AI エージェント導入を「勘」ではなく「リポジトリの実態」から設計するスキル。成果物は導入提案書1枚。失敗しやすいのは、(1) リポジトリを見ずに一般論の提案書を書く、(2) 特定ツールでしか動かない構成を勧めてチームの実態（複数ツール併用）と合わない、(3) 一度に全部入れる提案をして定着しない、の3つ。**提案は必ずリポジトリで確認した事実に紐づけ、段階導入で書く。**

## 前提: ツール非依存を主とする

チームは Claude Code / GitHub Copilot / Codex / Gemini CLI のどれを使うか分からない前提で提案する。

- **主**: 全ツールが読む資産 — AGENTS.md（CLAUDE.md は参照のみの薄い形）、`.agents/skills/` の Agent Skills、リポジトリ内ドキュメントの整備
- **補足**: ツール固有機能（Claude Code の hooks・サブエージェント、Copilot の設定等）は「そのツールを使う人向けの追加設定」として分離した節に書く

## 手順

### 1. リポジトリを診断する

対象リポジトリを解析し、診断シートを埋める。**確認した事実（ファイルパス・コマンド）を必ず添える。**

| 診断項目 | 見るもの |
|---|---|
| 言語・規模 | 主要言語、ファイル数、モジュール構成 |
| ビルド・テスト | コマンドが何か、README等に書かれているか、実行時間 |
| CI | 有無、何をチェックしているか（エージェントの出力を機械検証できるか） |
| 既存ドキュメント | README・設計書・手順書の所在と鮮度 |
| 既存のAI設定 | CLAUDE.md / AGENTS.md / .github/copilot-instructions.md 等の有無 |
| 定型作業 | コミット規約、レビュー手順、リリース手順など、繰り返される作業（スキル候補の種） |
| 機密・制約 | 社外送信してはいけない情報、ライセンス制約、規制要件 |

### 2. ヒアリングする

リポジトリから読めないことを2〜3問ずつ聞く: チームの人数と AI 利用経験 / 使う予定のツール / 最初に効かせたい作業（レビュー？実装？ドキュメント？）/ セキュリティ上の制約（社内ポリシー）。

### 3. 提案書を書く

章立ては固定（追加・削除しない）:

1. **現状診断** — 手順1の診断シートと、導入に効く強み・障害
2. **段階導入プラン** — Phase 1（AGENTS.md 整備＋ビルド・テストコマンドの明文化）→ Phase 2（定型作業のスキル化 2〜3本）→ Phase 3（CI 連携・チーム展開）。各 Phase に完了条件を書く
3. **AGENTS.md 草案** — 実際に使える形の全文。診断で確認した事実（コマンド・構成・規約）だけで書き、推測箇所は TODO と明記
4. **スキル候補一覧** — 定型作業ごとに「スキル名案 / 何をするか / 効果の根拠（その作業が繰り返されている証拠）」。作成は workflow-skill-architect で別途
5. **運用ルール** — レビュー必須の範囲、コミットの扱い、機密の扱い、うまくいかないときの見直し先
6. **ツール固有の補足** — ツールごとに1節。使わないツールの節は読まなくてよいと明記

保存先はユーザーに確認する（既定の提案: 対象リポジトリの `docs/ai-adoption-proposal.md`）。

**完了条件: 6章すべてが埋まった提案書を提示し、Phase 1 に着手するか否かの判断をユーザーから得たこと。**

## 禁止事項

- リポジトリを解析せずに一般論だけで提案書を書くこと（全提案に確認した事実の根拠をつける）
- 特定ツールの独自機能を Phase 1 の必須項目に置くこと
- AGENTS.md 草案に、診断で確認していないコマンドや規約を書くこと（推測は TODO と明記）

## 想定外の扱い

- 対象がモノレポで巨大な場合: 最初に効かせたいサブプロジェクトを1つ選んでもらい、そこに絞って診断する
- 既に CLAUDE.md / AGENTS.md が充実している場合: 新規提案ではなく監査が適切なので、claude-md-audit への切り替えを提案する
