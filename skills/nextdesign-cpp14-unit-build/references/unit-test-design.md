# 単体テスト設計

P2 で読む。ここで作る観点表 `work/test-design.md` が、P3 で書くテストコードの仕様書になる。

## 原則

**テスト観点は設計と Doxygen から導く。実装からは導かない。** 実装を見てから観点を起こすと、実装の誤りをそのまま期待値にしてしまう。P1 で書いた `@pre` / `@post` / `@retval` と `work/design-index.json` だけを見て起こす。

## 観点の導出手順

関数1個につき、次の順に当てる。

### 1. 戻り値から起こす

`@retval` に列挙した値ごとに1件。`true` を返す経路と `false` を返す経路は別のテスト。

### 2. 引数から起こす（等価分割 + 境界値）

各引数について、有効値の集合を区分に割り、区分ごとに1件。加えて**境界値**を取る。

| 引数の性質 | 取る値 |
|---|---|
| 範囲のある数値（`0..kMax`） | `-1`, `0`, `1`, `kMax-1`, `kMax`, `kMax+1` のうち、型が表現できるもの |
| 符号なし整数 | `0`, `1`, 最大値, 最大値+1（ラップアラウンド） |
| ポインタ | 有効値、`nullptr` |
| コンテナ・配列 | 空、要素1、要素複数、最大長 |
| 列挙型 | 全列挙子。加えて範囲外の値をキャストして渡せる設計なら不正値も |

引数が複数ある場合、全組み合わせは取らない。**各引数を1つずつ境界に置き、他は代表的な有効値に固定する**（1因子間法）。組み合わせでしか起きない仕様（引数間の大小関係の制約など）が Doxygen に書かれている場合だけ、その組み合わせを追加する。

### 3. 事前条件から起こす（異常系）

`@pre` に書いた条件を**満たさない状態で呼ぶ**テストを1件起こす。「Initialize() を呼ばずに SetSpeed() を呼ぶ」など。事前条件違反時の振る舞いが Doxygen に書かれていなければ、その関数を一覧にしてユーザーに確認する（推測しない）。

### 4. 状態遷移から起こす

内部状態を持つクラスは、状態ごとに同じ関数の振る舞いが変わる。設計の状態一覧（またはシーケンス図の代替フロー）から、`(状態, 呼び出し)` の組を起こす。特に**遷移が許されない組**（停止中に加速を呼ぶ等）を落とさない。

### 5. シーケンスから起こす（相互作用）

シーケンス図で「この関数は依存先の X() を Y 回、この順で呼ぶ」ことが決まっている場合、**呼び出し回数と順序を検証するテスト**を1件起こす（P3 で gmock の `EXPECT_CALL` / `InSequence` になる）。

### 6. 多重度から起こす

関連の多重度が `0..1` / `0..*` の依存は、**未設定・空の状態で呼ぶ**テストを起こす。

## テストIDの規約

`UT_<クラス名>_<関数名>_<3桁連番>`

例: `UT_MotorController_SetSpeed_001`

- オーバーロードがある場合は関数名の後に `_<引数型の頭文字>` を付けて区別する（`SetSpeed_I32`）
- **この ID を P3 のテスト名にそのまま使う**。`scripts/check_traceability.py` はこの一致で突合するので、途中で変えない

## 観点表の書式

`assets/templates/test-design-template.md` をコピーして使う。1行1テストで、次の列をすべて埋める。

| 列 | 内容 | 空欄にしてよいか |
|---|---|---|
| テストID | 上記の規約 | 不可 |
| 対象関数 | `work/design-index.json` の `functions[].id` と一致させる | 不可 |
| 区分 | `正常` / `境界` / `異常` / `相互作用` | 不可 |
| 観点 | 何を確かめるのか1行 | 不可 |
| 事前条件 | テスト開始時に作る状態。無ければ「なし」 | 不可（「なし」と書く） |
| 入力 | 引数の具体値 | 不可 |
| 期待結果 | 戻り値、出力引数、状態変化、依存先への呼び出し | 不可 |
| 根拠 | この観点を起こした設計上の出典（`@retval false`、シーケンス図名など） | 不可 |

**「期待結果」に「正しく動くこと」と書かない。** 検証可能な具体値にする。決まらないならユーザーに確認する。

## 網羅の下限

全 public 関数について、次を検討したうえで表に反映する。

- 正常系: 最低1件
- 境界値: 引数に範囲がある場合は必須。無い場合は「該当なし（引数に範囲制約なし）」と書く
- 異常系: `@pre` または `@retval` の失敗値がある場合は必須。無い場合は理由を書く

**「該当なし」は空欄と違う。** 検討したうえで不要と判断したことを表に残す。空欄は P2 の完了条件を満たさない。

## 純粋仮想関数（インタフェース）の扱い

純粋仮想関数は実装を持たないので、**テスト観点を起こさない**。`work/design-index.json` で `is_pure_virtual: true` にしておくと `scripts/check_traceability.py` が突合の対象から外す。これらは P3 で gmock のモックとして実装され、実装クラス側のテストで間接的に使われる。

インタフェースを継承した**具象クラス**の関数は通常どおり観点を起こす。

## private 関数の扱い

private 関数は直接テストしない。**public 関数経由で到達する経路として観点に含める**。public 経由で到達できない private 関数がある場合は、デッドコードか設計漏れなのでユーザーに報告する。テストのために可視性を緩めることは行わない。

## ユーザーへの提示

観点表ができたら、次の粒度で提示して過不足の確認を得る。

```
テスト観点 62件（正常 24 / 境界 21 / 異常 13 / 相互作用 4）

確認したい点:
  - MotorController::Calibrate は @pre に「電源投入後1秒以上経過」とありますが、
    時間依存をテストで作る手段が設計から読み取れません。時刻源を注入する設計に変えますか。
  - SpeedSensor::Read の異常系（センサ断線）が設計に記載されていないため観点なしとしています。
```
