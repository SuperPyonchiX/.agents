# 切り分け手法

D0 の最小再現、D1 の二分探索、D3 の検証方法を決めるときに読む。

**手法を選ぶ基準は「何を観測すれば白黒つくか」**であって、使い慣れているかではない。仮説ごとに、支持と棄却の判定条件を先に決めてから手法を選ぶ。

---

## 手法の選び方

| 状況 | 使う手法 |
|---|---|
| 前は動いていた。いつから壊れたか分かる | 二分探索（bisect） |
| 現象は再現するが範囲が広い | 削り込みによる最小再現 |
| 実機でしか出ない | 観測の追加（ログ / トレース） |
| 環境差（最適化・構成・ボード）で挙動が変わる | 差分実験 |
| 特定の関数の入出力を疑う | ホスト上の単体テストへの持ち込み |
| 落ちる・止まる | ポストモーテム（フォールト情報・コアダンプ） |
| 間欠発生で1回のテストで判定できない | 統計的比較 |

**間欠不具合に bisect と単発テストを使わない。** 1回のテストで判定できないため、誤った結論に着地する。統計的比較を使う。

---

## 二分探索で差分を絞る

前は動いていた場合、最も費用対効果が高い。

```
git bisect start
git bisect bad <現在のコミット>
git bisect good <動いていたことが確実なコミット>
# 以降、各段階でビルドして再現手順を実行し、good / bad を答える
git bisect reset
```

判定を自動化できるなら `git bisect run <スクリプト>` にする。スクリプトは再現したら非ゼロ、しなければ 0 を返す。

**使う前提条件**（1つでも欠けたら別の手法にする）:

- 再現性が `yes`（間欠なら不可）
- 各コミットがビルドできる（できない場合は `git bisect skip`）
- 1回の判定が現実的な時間で終わる

**コード以外の差分を忘れない。** ツールチェーンのバージョン、ビルド設定、ベンダ提供 BSP、ハードウェアリビジョンは git 履歴に出ないことがある。bisect で「壊したコミット」が無害に見えるときは、この線を疑う。

## 最小再現ケースを作る

範囲が狭いほど D3 の1周が速くなる。**削る方向は「残したまま再現するか」を毎回確認しながら**進める。

1. 入力を削る。データ量、周期、接続機器の数を減らす
2. 経路を削る。呼び出し元を直接呼ぶ、中間層を素通しにする
3. 環境を削る。RTOS のタスクを止める、割込みを1つだけ残す
4. **ホストへ持ち出せないか試す。** 対象関数がハードウェアに触らないなら、ホスト上の GoogleTest に持ち込めることが多い。持ち込めれば `-fsanitize=address,undefined` と `valgrind` が使えるようになり、切り分けの速度が桁違いになる

削っている途中で再現しなくなったら、**直前に削った要素が原因に関与している**。これ自体が有力な観測結果なので、台帳の「検証結果」に残す。

---

## 観測を追加する

### ログ

最も安全だが、**タイミングを変えるため症状が消えることがある**（PTN-TIME-002）。消えたら、それ自体がタイミング依存の証拠として使える。

- 割込みハンドラ内では printf 系を使わない。リングバッファへ書いて main 側で吐く
- 出力にタイムスタンプと発生元（タスクID / コンテキスト）を必ず入れる
- **既定で無効、マクロで有効化**にする。デバッグ用のログを恒久的に残さない

### アサート

「ここでは必ずこうなっているはず」を書けるなら、ログより強い。**壊れた瞬間に止まる**ので、原因と結果の距離が縮む。

### ハードウェアの観測

- GPIO トグル + ロジックアナライザ — タイミングを乱さずに時系列が取れる。割込み処理の実測に有効
- トレース機能（ETM / ITM 等）— 対応していれば実行履歴がそのまま取れる
- ウォッチポイント — 「どこで書き換わったか分からない」変数破壊に対する最短手

## 差分実験

環境や設定を1つだけ変えて挙動を比較する。**同時に2つ変えない。**

| 振る軸 | 何が分かるか |
|---|---|
| 最適化レベル（`-O0` / `-O2`） | UB の可能性（PTN-UB-001） |
| ビルド構成（Debug / Release） | マクロ差・アサート有無（PTN-BUILD-001） |
| 割込みの有無 | 並行性（PTN-INT-001） |
| ボード個体 | ハードウェア個体差（PTN-HW-001） |
| ツールチェーンのバージョン | コンパイラ起因 |

差が出たら、**なぜ差が出るのかを説明できるまで**は原因を特定したことにしない。「`-O0` なら動く」は原因ではない。

---

## ホスト上の単体テストへ持ち込む

対象がハードウェアに直接触らないなら、これが最も費用対効果が高い。

- `-fsanitize=address` — 境界踏み越え、解放後参照（PTN-MEM-002 / 003）
- `-fsanitize=undefined` — 符号付きオーバーフロー、アライメント違反、null 参照（PTN-UB-001、PTN-TYPE-004）
- `-fsanitize=thread` — データ競合。ただし RTOS の割込みモデルは再現できないので、ホスト上でスレッド化できる場合に限る
- `valgrind` — 未初期化読み出し（PTN-INIT-001）

ハードウェア依存部はモックに置き換える。**置き換えたことで消える現象は、その依存部が原因である**という観測になる。

## ポストモーテム

落ちた・止まった場合。

1. **フォールト要因レジスタを読む**（Cortex-M なら CFSR / HFSR / MMFAR / BFAR）。アライメント違反か、範囲外アクセスか、命令フェッチの失敗かがここで分かる
2. **スタックを巻き戻す**。フォールト時のスタックフレームから PC と LR を取り、マップファイルで関数を特定する
3. **リセット要因を読む**。ウォッチドッグか、電源か、ソフトリセットかを区別する
4. リンカマップで、壊れていた変数の**アドレス的な隣人**を確認する。隣接領域の踏み越え（PTN-MEM-001 / 002）の裏付けになる

---

## 統計的比較（間欠不具合）

1回の実行で判定できないため、**発生率を比較する**。

1. 試行回数と観測時間を先に決める。「10分の負荷試験を3セット」のように、実行前に台帳へ書く
2. 条件を1つだけ変えた2群を用意し、同じ回数を回す
3. 発生率を比較する

**判断の目安**: 元の発生率が低い（数十回に1回など）と、少ない試行では差が偶然と区別できない。**元の条件で最低5回は発生する試行回数**を確保する。確保できないなら、まず発生率を上げる工夫（負荷を上げる、周期を詰める、条件を極端にする）を先にする。

「1回試して出なかったから直った」は最も多い誤りである。**修正の検証にも同じ試行回数を使う。**
