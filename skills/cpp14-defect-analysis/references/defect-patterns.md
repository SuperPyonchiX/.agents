# 組込み C++ の原因パターン集

D2（仮説の列挙）の直前に読む。**コードを眺めて思いつくより、既知のパターンを機械的に当てるほうが網羅性が高い。**

各パターンは次で構成する。

- **症状の指紋** — この原因のときに出やすい現象。D0 で記録した `symptom` と照合する
- **確認方法** — D3 でこの仮説を白黒つける手段
- **grep** — D6 の水平展開で使う検索パターン。**ヒットは候補であって違反ではない**

grep の例は POSIX 拡張正規表現（`grep -nE`）で書いてある。Windows なら `rg` か、Bash ツール経由で使う。

---

## 使い方

D2 では次の順で当てる。

1. `symptom.frequency` で絞る。**常時発生と間欠発生では容疑者が全く違う**
   - 常時 → INIT / LOGIC / TYPE / BUILD
   - 間欠 → INT / MEM / TIME / HW
2. `environment` の差で絞る。最適化レベル・ビルド構成で挙動が変わるなら UB / BUILD / MEM を最優先で疑う
3. `suspect_range` に該当する変更があるパターンの確度を上げる

## INIT — 初期化まわり

### PTN-INIT-001: メンバ・変数の未初期化

**症状の指紋**: 起動直後だけおかしい。電源再投入で挙動が変わる。デバッグビルドでは出ない（`-O0` が偶然ゼロ埋めする、スタックの残骸が違う）。値が毎回違う。

**確認方法**: 生成直後に全メンバをダンプして既定値と照合する。コンストラクタの初期化リストと宣言順を突き合わせる。

```
grep -nE '^\s*(class|struct)\s+\w+' --include=*.h -r .   # 宣言を洗い、初期化子の有無を目視
grep -nE '\w+\s+\w+\s*;\s*(//.*)?$' --include=*.cpp -r . # 初期化子なしのローカル宣言
```

### PTN-INIT-002: 静的初期化順序の問題

**症状の指紋**: 翻訳単位をまたぐグローバル・静的オブジェクトの参照で落ちる。リンク順やファイル追加で症状が変わる。

**確認方法**: 該当オブジェクトのコンストラクタにブレークを張り、参照側との順序を確認する。

```
grep -nE '^\s*(static\s+)?[A-Z]\w*\s+g_\w+\s*(\(|=|;)' --include=*.cpp -r .
```

### PTN-INIT-003: 初期化前のハードウェアアクセス

**症状の指紋**: クロック・ペリフェラルの初期化順を変えると症状が動く。特定のレジスタ読み出しだけ 0 や 0xFF になる。

**確認方法**: 初期化シーケンスとアクセス箇所の時系列をログで並べる。

## INT — 割込み・並行性

### PTN-INT-001: 割込みハンドラと共有する変数の排他漏れ

**症状の指紋**: 負荷が高いときだけ出る。発生率が割込み頻度と相関する。デバッガで止めると再現しない。値が「中途半端」（2バイト目だけ更新された値など）。

**確認方法**: 該当区間を割込み禁止で囲んだビルドを作り、発生率を比較する。**症状が消えたことは仮説の支持であって、恒久対策ではない**（D5 の対症療法の項を参照）。

```
grep -nE '\b(ISR|IRQHandler|_isr|Handler)\b' -r .        # ハンドラを列挙し、触る変数を洗う
grep -nE '\bvolatile\b' -r .                              # volatile だけで済ませている箇所
grep -nE '\bstatic\s+(?!const)' --include=*.cpp -rP .     # 関数内 static（再入で壊れる）
```

`volatile` は**最適化の抑止であって排他ではない**。read-modify-write（`++`、`|=`）は volatile を付けても不可分にならない。

### PTN-INT-002: 非再入関数の再入

**症状の指紋**: 割込みからも main からも呼ばれる関数の周辺でだけ壊れる。関数内 `static` バッファの内容が混ざる。

**確認方法**: 呼び出し元を全て洗い、割込みコンテキストからの経路があるか確認する。

### PTN-INT-003: 優先度逆転・デッドロック

**症状の指紋**: 特定のタスク組み合わせでだけ止まる。ウォッチドッグでリセットがかかる。

**確認方法**: RTOS のタスク状態ダンプを取り、ブロック中のタスクと保持中のミューテックスを確認する。

## MEM — メモリ

### PTN-MEM-001: スタックオーバーフロー

**症状の指紋**: 特定の関数を通ると落ちる。再帰や大きなローカル配列がある。別のタスクの変数が壊れる（隣接領域を踏む）。最適化レベルを変えると症状が動く。

**確認方法**: スタック領域をパターンで埋めてから実行し、消費量の最大値を測る。リンカマップでスタックサイズを確認する。

```
grep -nE '\b\w+\s+\w+\s*\[\s*[0-9]{3,}\s*\]' --include=*.cpp -r .  # 大きなローカル配列
grep -nE '\balloca\b|\bchar\s+\w+\[\w+\]' -r .                     # 可変長・alloca
```

### PTN-MEM-002: バッファ境界の踏み越え

**症状の指紋**: 無関係な変数が書き換わる。配列サイズやループ上限を変えると症状が動く。

**確認方法**: 該当バッファの前後にガードパターンを置き、破壊を検出する。境界値でループ条件を手計算する。

```
grep -nE '\b(memcpy|memset|strcpy|strcat|sprintf)\b' -r .
grep -nE 'for\s*\(.*<=\s*\w*(SIZE|LEN|COUNT|N)\b' -r .   # <= による off-by-one
```

### PTN-MEM-003: 解放後・スコープ外の参照

**症状の指紋**: 間欠的に値が化ける。ポインタや参照を返す関数の周辺。

```
grep -nE 'return\s+&\w+' -r .                             # ローカルのアドレスを返す
grep -nE '\breturn\s+\w+\.c_str\(\)' -r .
```

### PTN-MEM-004: 動的確保の失敗・断片化

**症状の指紋**: 長時間稼働で出る。確保サイズが変動する処理の後。

**確認方法**: ヒープ使用量を時系列でログに出す。**そもそも動的確保が許容される方針かを D0 の環境確認で押さえておく。**

---

## TIME — タイミング・時間

### PTN-TIME-001: カウンタのオーバーフロー・ラップアラウンド

**症状の指紋**: 一定時間後（`49.7` 日、`65.5` 秒など 2 の冪に対応する周期）に1回だけ出る。再現に時間がかかる。

**確認方法**: カウンタを上限付近に初期化して短時間で再現させる。比較が `a > b` ではなく `a - b > 0` になっているか確認する。

```
grep -nE '\b(tick|Tick|millis|GetTime|timestamp)\w*\s*(>|<|>=|<=)' -r .
```

### PTN-TIME-002: 競合するタイミング依存（レース）

**症状の指紋**: ログを増やすと再現しなくなる。最適化を下げると出ない。

**確認方法**: 意図的に遅延を挿入して発生率が変わるか見る。**遅延で消えることは根本対策ではない。**

### PTN-TIME-003: ウォッチドッグ

**症状の指紋**: 周期的にリセットがかかる。特定の重い処理の直後。

**確認方法**: リセット要因レジスタを読む。WDT クリアの周期と最悪処理時間を突き合わせる。

---

## TYPE — 型・演算

### PTN-TYPE-001: 整数昇格・符号の混在

**症状の指紋**: 負値や大きな値で結果が破綻する。`if (unsigned_var - 1 >= 0)` が常に真になる。境界値だけ間違う。

**確認方法**: 該当式の各項の型を確定させ、昇格後の型で手計算する。

```
grep -nE '\b(unsigned|uint\w+)\b.*\b(-|<|>)\b' -r .
grep -nE '\bsizeof\b.*[-<>]' -r .                          # size_t との比較
```

### PTN-TYPE-002: 縮小変換・キャストによる情報落ち

**症状の指紋**: 大きな値でだけおかしい。上位ビットが落ちている値になる。

```
grep -nE '\(\s*(u?int(8|16|32)_t|char|short|int|long|float)\s*\)\s*\w' -r .   # C スタイルキャスト
grep -nE '\bstatic_cast\s*<\s*(u?int(8|16)_t|char|short)\s*>' -r .
```

### PTN-TYPE-003: 浮動小数点の等値比較・精度

**症状の指紋**: 「ほぼ正しいが最後の桁が違う」。等値判定が通らない。ハードウェア FPU の有無で結果が変わる。

```
grep -nE '(float|double)\s+\w+.*==|==\s*[0-9]+\.[0-9]' -r .
```

### PTN-TYPE-004: アライメント違反

**症状の指紋**: 特定アドレスのアクセスでハードフォルトする。ポインタキャストの直後。バイト列をそのまま構造体に被せている。

```
grep -nE 'reinterpret_cast\s*<' -r .
grep -nE '\(\s*\w+\s*\*\s*\)\s*&?\w*(buf|buffer|data|raw)' -r .
```

## UB — 未定義動作と最適化

### PTN-UB-001: 最適化レベルで挙動が変わる

**症状の指紋**: `-O0` では出ないが `-O2` で出る。コンパイラのバージョンを上げたら出た。ログを1行足すと消える。

**確認方法**: 両方のレベルでビルドして比較し、差が出たら該当関数を逆アセンブルして消えている処理を探す。**UB がある限り、最適化を下げるのは対症療法である。**

典型的な UB: 未初期化読み出し、符号付き整数のオーバーフロー、strict aliasing 違反、null 参照、範囲外アクセス、非アトミックなデータ競合。

```
grep -nE '\bmemcpy\b|\bunion\b|reinterpret_cast' -r .      # aliasing 違反の温床
```

**まず `-fsanitize=undefined` を有効にしたホストビルドで単体テストを回す**。実機で追う前に落とせることが多い。

### PTN-UB-002: 未定義の評価順序に依存

```
grep -nE '\w+\+\+.*\w+\+\+|\[\s*\w+\+\+\s*\].*\w+\+\+' -r .
```

## BUILD — ビルド・リンク・配置

### PTN-BUILD-001: マクロ・ビルド構成の差

**症状の指紋**: 特定の構成でだけ出る。ヘッダとソースで構造体サイズが食い違う（ODR 違反、パディング指定の不一致）。

**確認方法**: 前処理後のソース（`-E`）を両構成で取って差分を見る。`sizeof` を実行時に出力して比較する。

```
grep -nE '^\s*#\s*(if|ifdef|ifndef)\b' -r .
grep -nE '#pragma\s+pack|__attribute__\s*\(\s*\(\s*packed' -r .
```

### PTN-BUILD-002: セクション配置・リンカスクリプト

**症状の指紋**: 変数を1つ追加したら別の場所が壊れた。特定のアドレスの変数だけおかしい。DMA 対象領域。

**確認方法**: リンカマップで該当シンボルのアドレスと領域の境界を確認する。キャッシュ有効領域と DMA 領域の重なりを確認する。

### PTN-BUILD-003: ビルド成果物の不一致

**症状の指紋**: ソースを直したのに挙動が変わらない。クリーンビルドすると直る。

**確認方法**: フルクリーンしてから再現する。**これで直る場合は不具合ではないので、D0 の再現手順に「クリーンビルド後」を明記して仕切り直す。**

---

## HW — ハードウェア・外部要因

### PTN-HW-001: 個体差・ロット差

**症状の指紋**: 特定のボードでだけ出る。他の個体では再現しない。

**確認方法**: 複数個体で再現を試す。**D0 の `environment.notes` にボードのシリアルを残す。**

### PTN-HW-002: 電源・ノイズ・温度

**症状の指紋**: 環境条件で発生率が変わる。特定の外部機器を接続したときだけ。

### PTN-HW-003: 外部デバイスの応答・プロトコル

**症状の指紋**: 通信相手を変えると挙動が変わる。タイムアウト値の変更で症状が動く。

**確認方法**: バスをロジックアナライザで観測し、仕様書のタイミングと突き合わせる。

---

## LOGIC — 仕様・ロジック

**組込み特有の原因を先に疑いがちだが、単純な仕様誤解・条件式の誤りが原因であることは多い。** 上の各パターンを当てても確度が上がらないときは、ここへ戻る。

### PTN-LOGIC-001: 仕様の解釈違い

**確認方法**: 設計書・要求仕様の該当箇所を読み、期待動作が本当に「期待」なのかを確認する。**報告者の期待が仕様と違うだけ、という結論もありうる。**

### PTN-LOGIC-002: 条件式・境界の誤り

**確認方法**: 境界値（最小、最小+1、最大-1、最大、0、負値）を単体テストで当てる。

### PTN-LOGIC-003: 状態遷移の抜け

**確認方法**: 状態遷移表を書き出し、全遷移に対する扱いがあるか確認する。`switch` の `default`、想定外イベントの扱い。

```
grep -nE 'switch\s*\(' -r .    # default の有無を目視
```
