# クラスタリングの設計

T2 の直前に読む。フィンガープリントの作り方と、代表1件の判定を横展開してよいかの判断基準をここにまとめてある。

## 何のためにやるか

静的解析の指摘は、件数のわりに**種類が少ない**。1,000件の指摘が実際には30種類の問題の繰り返し、ということが普通に起きる。1件ずつ読むと1,000回の判断になるが、束ねれば30回で済む。トリアージの所要時間はクラスタ数にほぼ比例するので、**圧縮率がそのまま短縮率になる**。

目安として、圧縮率が10倍（1,000件 → 100クラスタ）に届かない場合はフィンガープリントの材料が足りていない。`code` 列や `function` 列を `form-spec.json` に足せないか検討する。

## フィンガープリント

`cluster_findings.py` が次の順で材料を連結し、SHA-1 の先頭12桁を取る。

```
fingerprint = sha1( rule_id | normalized_message | normalized_code )[:12]
```

正規化は「同じ問題なら同じ文字列になり、違う問題なら違う文字列になる」ことを狙う。やりすぎると別の問題まで束ねてしまうので、次の範囲に留める。

| 対象 | 正規化 | 理由 |
|---|---|---|
| 数値リテラル（10進・16進） | `N` に置換 | `buf[10]` と `buf[20]` は同じ問題 |
| 文字列・文字リテラル | `S` / `C` に置換 | 中身は問題の種類に影響しない |
| メッセージ中の引用部分（`'...'` `"..."` `` `...` ``） | `ID` に置換 | ツールが引用するのは変数名なので、名前違いの同じ指摘を束ねる |
| コード断片の識別子 | **型と修飾子だけ残し、他は `ID` に置換** | 下記参照 |
| 空白・タブ・改行 | 単一空白に畳む | 整形の違いを吸収する |
| ファイルパス・行番号 | **使わない** | これを入れると束ねられなくなる |

コード断片の識別子正規化がクラスタリングの効きを決める。**変数名を残すと `value_0` と `value_1` が別クラスタになり、まったく束ねられない。** 一方で全部潰すと `(uint16_t)x` と `(volatile uint32_t*)p` が同じになってしまう。

そこで **C++ のキーワードと固定幅整数型（`uint16_t` など）だけを残し、残りの識別子を `ID` に潰す**。問題の種類を決めているのは型と修飾子であって、変数名ではない。

```
(uint16_t)value_0              → (ID)ID        ✗ 全部潰すと型の違いが消える
(uint16_t)value_0              → (uint16_t)ID  ○ 型を残す
(volatile uint32_t*)0x40020000 → (volatile uint32_t*)N
```

この2つは別クラスタになり、前者は `fix`、後者は `DV-HW` の逸脱候補として正しく分かれる。

`code` 列が無い場合は `rule_id | normalized_message` だけになる。これでも大半のルールは束ねられるが、「同じルールで違う原因」が混ざりやすくなるので、T3 で代表を見たときに違和感があればクラスタを分けてよい（`clusters.json` を手で編集し、`status` を `pending` に戻す）。

## uniformity — 横展開してよいか

**これがこのスキルで最も事故りやすい箇所**。同じルールIDでも、判定が文脈に依存するルールとしないルールがある。

| uniformity | 意味 | T3 での扱い |
|---|---|---|
| `uniform` | クラスタ内の全メンバーが同じ判定でよい | 代表1件を見て一括判定 |
| `individual` | メンバーごとに判定が変わりうる | 全メンバーを見て個別判定 |
| `unknown` | スクリプトが判断できなかった | T3 で人が決めてから進む |

### 判断の基準

**そのルール違反が、指摘箇所のコードだけを見て判定できるか**。できるなら `uniform`、周辺の状態・呼び出し元・実行時の値を見ないと判定できないなら `individual`。

`uniform` 寄りのルール（構文・字面で決まる）:

- キャスト形式、ブレース省略、`goto` の使用、マジックナンバー
- 命名規約、ヘッダガード、インクルード順
- 型の暗黙変換、符号付き・符号なしの混在
- `switch` の `default` 欠落、`enum` の網羅性

`individual` 必須のルール（データフロー・文脈で決まる）:

- **ヌルポインタ参照の可能性** — 呼び出し元が保証しているかで変わる
- **配列境界・値域** — 入力の範囲で変わる
- **未初期化変数の使用** — 経路によって変わる
- **リソースリーク・二重解放** — 所有権の設計で変わる
- **並行性・割込み安全性** — 実行文脈で変わる
- **到達不能コード・デッドコード** — 条件コンパイルや設定で変わる
- **除算のゼロ除数** — 入力の範囲で変わる

スクリプトはルールIDとメッセージに含まれるキーワードでこの区別を推定する。**推定でしかないので、T3 で代表を見たときに違和感があれば上書きしてよい。** 迷ったら `individual` に倒す。一括で誤判定するより、余分に読むほうが安い。

### 外部提供コードは自動で分離される

同じ字面の違反でも、外部提供コード（変更できない → `DV-EXT` の逸脱）と自社コード（直せる → `fix`）では判定が割れる。そのため `cluster_findings.py` は、`triage-scope.json` の `external_paths` に該当するメンバーを**別クラスタに分ける**。

このとき使う識別子が `cluster_id` である。

```
cluster_id = fingerprint            （自社コード）
cluster_id = fingerprint + "@external"  （外部提供コード）
```

判定DBのキーもこの `cluster_id` である。外部コードの逸脱と自社コードの修正が、DB 上でも混ざらない。

`external_paths` の設定漏れがあると分離されない。T3 で「同じクラスタなのに直せるものと直せないものが混ざっている」と気づいたら、T0 に戻って `external_paths` を足す。

## 判定DBの再適用

`decisions.json` は `cluster_id` をキーに過去の判定を持つ。同じ `cluster_id` の指摘が出たら、`auto_applied: true` を付けて判定を引き継ぐ。

**再適用は便利だが、無条件に信用してはいけない。** フィンガープリントは正規化後の字面が一致することしか保証しない。次の場合は前提が変わっている。

- 前回は「呼び出し元がヌルチェック済み」を根拠に誤検知としたが、その呼び出し元が変わった
- 前回は「この型では値域が保証される」を根拠にしたが、型が変わった
- ツールのバージョンが上がり、同じメッセージでも解析の意味が変わった

だから T2 で**抜き取り確認を3件行う**。1件でも妥当でなければ、そのルールIDの自動再適用をすべて解除する。ルール単位で解除するのは、同じルールなら同じ前提に依存している可能性が高いためである。

`individual` のクラスタに対する再適用は、スクリプトが**自動では行わない**。文脈依存の判定を字面で引き継ぐのは危険なので、参考情報として前回の判定を表示するに留める。

## clusters.json の構造

```json
{
  "version": 1,
  "generated_at": "2026-08-11T10:00:00+09:00",
  "source": "work/findings.json",
  "clusters": [
    {
      "cluster_id": "a1b2c3d4e5f6",
      "fingerprint": "a1b2c3d4e5f6",
      "external": false,
      "rule_id": "A5-2-2",
      "tool": "Helix QAC",
      "uniformity": "uniform",
      "uniformity_source": "heuristic",
      "representative": { "file": "src/motor.cpp", "line": 42, "message": "...", "code": "..." },
      "member_count": 87,
      "members": [ { "row": 12, "id": "0001", "file": "src/motor.cpp", "line": 42 } ],
      "status": "pending",
      "verdict": null,
      "code": null,
      "rationale": null,
      "alternative": null,
      "auto_applied": false,
      "previous_decision": null
    }
  ]
}
```

| 項目 | 意味 |
|---|---|
| `cluster_id` | クラスタの識別子。判定DBのキー。外部提供コードは `@external` が付く |
| `external` | メンバーが `external_paths` 配下か |
| `uniformity_source` | `heuristic`（スクリプトの推定）/ `manual`（T3 で人が決めた） |
| `status` | `pending` / `done`。T3 で1クラスタ終えるたびに更新する |
| `verdict` | `fix` / `deviate` / `false_positive` / `deferred` |
| `code` | `false_positive` なら FP コード、`deviate` なら DV コード。`fix` と `deferred` は `null` |
| `rationale` | 判定の根拠。**全 verdict で必須**。`fix` なら修正方針、`deferred` なら何が足りないか |
| `alternative` | 代替措置。`deviate` でのみ必須 |
| `auto_applied` | 判定DBから引き継いだか。T2 の抜き取り確認の対象を選ぶのに使う |
| `previous_decision` | `individual` のクラスタに過去の判定があったときの参考表示。自動適用はされない |

`uniformity` を T3 で人が決めたら、`uniformity_source` を `manual` に書き換える。`unknown` のまま残っていると `check_triage.py` が通らない。

`individual` のクラスタは、メンバーごとに判定が要る。その場合は `members[]` の各要素に `verdict` / `code` / `rationale` を持たせ、クラスタ側の `verdict` は `null` のままにする。`check_triage.py` はこの形も受け付ける。
