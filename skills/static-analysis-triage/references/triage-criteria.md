# トリアージの判定基準

T3 の直前に読む。修正 / 逸脱 / 誤検知をどう切り分けるか、逸脱理由の DV コード、根拠の書き方をここにまとめてある。誤検知の FP コードは `tool-messages.md` にある。

## 判定の順序

**必ずこの順で当てる。** 順序を変えると、直せるものを逸脱にしたり、本物の不具合を誤検知にしたりする。

```
1. これは本当にルール違反か？
     違う → false_positive（FP コードを付ける。付けられないなら deferred）
2. 直せるか？ 直したときの影響は許容できるか？
     直せる → fix
3. 直せない技術的・契約的な理由があるか？
     ある → deviate（DV コードと代替措置を書く）
4. ここまでで決められない
     → deferred（何が足りないかを書く）
```

**既定は `fix`**。「直すのが面倒だから逸脱」は逸脱ではない。逸脱は「直せない」ときの手段であって、「直したくない」ときの手段ではない。

## fix — 修正する

次のいずれかに当てはまるなら `fix`。

- ルール違反であり、修正が局所的で副作用がない（キャスト形式、ブレース、命名）
- 本物の不具合が潜んでいる（ヌル参照、境界超過、未初期化、リーク）
- 規約への適合が浅い（`const` の付け忘れ、明示的な型変換の欠落）

`rationale` には**修正方針を1行**書く。「修正する」では不十分で、「`static_cast` に置換する」「呼び出し前にヌルチェックを追加する」まで書く。後工程で誰が直しても同じ結果になる粒度にすること。

### 本物の不具合を見つけたときの扱い

トリアージ中に規約違反ではなく**動作上の不具合**を見つけたら、その旨を `rationale` に明記し、T5 の報告で個別に挙げる。ルール違反の件数に紛れ込ませない。優先度が違う。

## deviate — 逸脱を申請する

**逸脱は「規約に違反したまま出荷する」という決定**であり、組織の承認が要る。このスキルが行うのは申請書と記録書の作成までで、**承認は必ずユーザーと組織が行う**。自分で承認しない。

### DV コード

| コード | 意味 | 典型例 |
|---|---|---|
| `DV-HW` | ハードウェア制約 | メモリマップドレジスタへのアクセスで `volatile` ポインタのキャストが避けられない |
| `DV-PERF` | 性能・メモリ制約 | 割込みハンドラで規約準拠の実装では実行時間要件を満たせない |
| `DV-EXT` | 外部提供コード | ベンダ提供のドライバ・ミドルウェア・自動生成コードで、変更が許されない |
| `DV-COMPAT` | 既存資産との互換 | 既存の公開 API を変えると影響範囲が広すぎる |
| `DV-LANG` | 言語仕様・ツールチェーン上の制約 | コンパイラ拡張に依存せざるをえない |
| `DV-STD` | 規格間の衝突 | 別の適用規格・社内規約と要求が矛盾している |

「工数がない」「影響が読めない」は DV コードに該当しない。それは `deferred` である。

### 逸脱に必須の3点

1. **DV コード** — 上の表から選ぶ
2. **根拠 (`rationale`)** — なぜ規約準拠の実装ができないのか。**代案を検討したうえで不可だった**ことを書く。「他に方法がない」だけでは通らない
3. **代替措置 (`alternative`)** — 逸脱によって生じるリスクを何で抑えるか。レビュー強化、テスト追加、実行時アサーション、使用箇所の局所化、コメントでの明示など

3が最も落としやすい。**代替措置のない逸脱は、リスクを放置しているのと同じ**。書けないなら `deferred` にしてユーザーに相談する。

### 逸脱が積み上がっているとき

同じルールIDで逸脱が多数出ている場合、それは個別の逸脱ではなく**規約の適用方針そのものの問題**である可能性が高い。T5 の報告で「このルールは逸脱が N 件」と挙げ、規約側の見直し（適用除外の設定、ツール設定の調整）を選択肢として提示する。個別申請を N 件積むのは最善ではない。

## false_positive — 誤検知

**最も慎重に扱う判定**。楽な逃げ道であり、本物の不具合を見逃す経路でもある。

`tool-messages.md` の FP コードを付けられるときだけ使う。**「見た限り問題なさそう」は誤検知の根拠ではない。** ツールがなぜ誤ったのかを、解析の限界として説明できる必要がある。

`rationale` には次の2点を書く。

1. ツールが何を仮定して指摘したか
2. その仮定が実際には成り立たない理由（何がそれを保証しているか）

例: 「ツールは `p` が `NULL` になりうる経路を想定しているが、`p` は同一関数内の 38 行目で初期化され、その間に再代入がない。ツールはループ内の関数呼び出しをまたいで値を追跡できていない（FP-PATH）」

**保証の主体を書くのが肝**。「大丈夫だと思う」ではなく「何がそれを保証しているか」。保証の主体を書けないなら、それは誤検知ではなく `deferred` か `fix` である。

## deferred — 保留

判定できないものを無理に判定しない。次の場合は `deferred` にする。

- 判定に申請書外の情報（設計書、ハードウェア仕様、他モジュール、呼び出し元）が要る
- 誤検知に見えるが FP コードを特定できない
- 逸脱の必要がありそうだが代替措置を決められない
- 工数・影響範囲の判断が必要で、技術的に一意に決まらない

`rationale` には**何が足りないか**を具体的に書く。「判断できない」では次に進めない。「`MotorCtrl::init()` の呼び出し元がスコープ外のため、`p` の非ヌルが保証されるか確認できない」まで書く。

`deferred` は T5 の報告で**全件を個別に列挙する**。判定DBには保存しない。

## 根拠の書き方（全 verdict 共通）

| 悪い例 | なぜ悪いか | 良い例 |
|---|---|---|
| 「問題ない」 | 何を見てそう言えるのかが無い | 「38行目で初期化され、以降再代入がない」 |
| 「規約に準拠できない」 | 理由が無い | 「レジスタが `volatile uint32_t*` として定義されており、規約準拠の型では書けない」 |
| 「誤検知」 | 解析限界の説明が無い | 「ツールが関数境界をまたいで値域を追跡できていない（FP-PATH）」 |
| 「修正する」 | 方針が無い | 「`static_cast<uint16_t>` に置換する」 |
| 「影響が大きいので逸脱」 | 影響の中身と代案検討が無い | 「公開 API のシグネチャ変更が必要で、依存する12モジュールの再検証が要る。内部実装での吸収も検討したが、引数の型が規約違反の本体のため不可（DV-COMPAT）」 |

判定は**後から他人が読んで再現できる形**にする。トリアージの結果は監査で見られる。半年後の自分が読んで判断を追えないなら、書き足りていない。
