# ツールの特性と誤検知の類型

T3 の直前に読む。CodeSonar / Helix QAC が何をどう見ているか、誤検知がどこで生まれるか、FP コードの選び方をここにまとめてある。

## 2つのツールの性格の違い

判定の当て方が変わるので、どちらの指摘かを意識する。

| | Helix QAC | CodeSonar |
|---|---|---|
| 主軸 | **規約適合**（MISRA / AUTOSAR C++14 の条文単位） | **欠陥検出**（データフロー・シンボリック実行による不具合探索） |
| 指摘の性質 | 字面・構文で決まるものが多い | 実行経路の推論に基づくものが多い |
| 典型的な判定 | `fix` か `deviate`。誤検知は比較的少ない | `fix` か `false_positive`。経路の実現可能性が争点になる |
| uniformity | `uniform` になりやすい | `individual` になりやすい |
| 誤検知の主因 | 解析設定・スタブ不備、規格解釈の相違 | 経路の実現可能性、別名解析、外部要因 |

**QAC の指摘を「誤検知」と判定するときは特に慎重に**。規約は字面で決まるものが多く、字面が違反しているなら違反である。「意図としては問題ない」は誤検知ではなく**逸脱**である。ここを取り違えると、逸脱申請すべきものが誤検知として処理され、監査で問題になる。

## FP コード — 誤検知の解析限界の類型

`false_positive` と判定するときは、次のどれに当たるかを必ず指定する。**どれにも当てはまらないなら、それは誤検知ではない。**

| コード | 解析限界 | 典型的な状況 | 判定時に確認すること |
|---|---|---|---|
| `FP-PATH` | 経路の実現可能性を判定しきれない | 指摘された経路が、実際には成立しない条件の組み合わせでしか通らない | **経路が本当に不成立か**をコードで確認する。条件の相関（`if (a) ... if (a)` のような）を追う |
| `FP-RANGE` | 値域を絞りきれない | 入力値の範囲が呼び出し規約や上流で保証されているが、ツールがそれを知らない | 保証の主体を特定する。アサーション・型・上流のチェックのどれが保証しているか |
| `FP-ALIAS` | ポインタの別名解析の限界 | 別のポインタ経由で書き換えられうるとツールが仮定しているが、実際には別名が存在しない | 該当オブジェクトへの参照が本当に他に無いか確認する |
| `FP-EXT` | 外部要因を追えない | ハードウェアレジスタ、DMA、割込み、他コアが値を書くため、ツールの推論と実態が食い違う | `volatile` が正しく付いているかも同時に確認する。付いていないなら誤検知ではなく `fix` |
| `FP-MACRO` | マクロ展開・条件コンパイルの解釈 | 展開後のコードに対する指摘で、実際のビルド構成では成立しない | 対象のビルド構成で本当に成立しないか確認する。他の構成では成立するなら誤検知ではない |
| `FP-CFG` | 解析設定・スタブの不備 | インクルードパス不足、コンパイラ定義の未設定、ライブラリ関数のモデルが不正確 | **これは誤検知ではなく設定不良である可能性が高い。** 設定を直して再解析できないかを先に検討する |
| `FP-STD` | 規格・規約の解釈の相違 | ツールの実装が規約条文の意図と食い違っている | 条文を実際に引用して示す。「解釈が違うと思う」だけでは不十分 |

### FP-CFG の扱いに注意

`FP-CFG` は誤検知として処理してしまいがちだが、**解析設定を直せば消える指摘は、誤検知ではなく設定不良**である。同じ設定で解析している限り毎回出続け、毎回トリアージのコストがかかる。

`FP-CFG` が一定数（目安として全体の5%以上）出たら、T5 の報告で「解析設定の見直しで N 件が消える見込み」として挙げる。個別に誤検知処理するより、設定を直すほうが安い。

### FP-EXT の落とし穴

「ハードウェアが書き換えるから」を理由に誤検知とするとき、**そのオブジェクトが `volatile` で宣言されているかを必ず確認する**。付いていない場合、ツールの指摘は正しく、コンパイラが最適化で読み飛ばす本物の不具合である。この場合は `false_positive` ではなく `fix`。

## メッセージ類型ごとの当たり方

| メッセージの型 | 主に見るべきこと | 典型的な判定の傾向 |
|---|---|---|
| ヌルポインタ参照の可能性 | 呼び出し元の保証、初期化からの距離 | `individual`。`fix` か `FP-PATH` / `FP-RANGE` |
| バッファ境界超過 | インデックスの上限を何が保証しているか | `individual`。誤検知にするなら保証の主体を明示 |
| 未初期化変数の使用 | 全経路で初期化されるか。`switch` の `default` 抜けが典型 | `fix` が多い。誤検知は `FP-PATH` |
| リソースリーク・二重解放 | 所有権の設計。早期 return と例外経路 | `individual`。設計の問題なら `fix` |
| 型変換・キャスト | 字面で決まる | `uniform`。`fix` か `DV-HW`（レジスタアクセス） |
| マジックナンバー・命名 | 字面で決まる | `uniform`。ほぼ `fix` |
| 到達不能コード | ビルド構成、条件コンパイル | `FP-MACRO` の候補だが、本当に死んでいるなら `fix`（削除） |
| 再帰・スタック深さ | 組込みではスタック上限が固定 | `fix` か `DV-PERF`。誤検知にしにくい |
| 並行・割込み安全性 | 実行文脈、割込み禁止区間、`volatile` と `atomic` | `individual` 必須。安易に誤検知にしない |
| 標準ライブラリ・動的メモリの使用 | プロジェクト方針で決まる | 方針次第で `fix` か `deviate` |

## 判定DBを育てるときの注意

判定DBは資産だが、**ルールIDとメッセージの字面が同じでも、判定の前提は違いうる**。特に次の類型は、判定DBからの自動再適用を信用してはならない（`clustering.md` の通り、`individual` のクラスタには自動再適用しない）。

- ヌル参照、値域、未初期化、リーク、並行性 — 文脈で変わる
- `FP-PATH`、`FP-RANGE`、`FP-ALIAS` を根拠にした誤検知 — 周辺コードが変われば前提が崩れる

逆に自動再適用が効くのは、`DV-HW` / `DV-EXT` のようにコードの性質そのものに紐づく逸脱と、字面で決まるルールの `fix` である。

ツールのバージョンが上がったときは、**判定DBの再適用を一度止めて全件見直すか、少なくとも抜き取り確認の件数を増やす**。同じメッセージでも解析の意味が変わっていることがある。
