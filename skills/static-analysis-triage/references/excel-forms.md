# Excel 様式の扱いとスクリプトの使い方

T0 の直前に読む。様式定義の書き方、Excel を壊さないための決まり、全スクリプトの引数と終了コードをここにまとめてある。

## なぜ列名をスクリプトに埋め込まないのか

社内様式は組織ごと・年度ごとに変わる。列名をスクリプトに書くと、様式が変わるたびにスクリプトを直すことになり、他プロジェクトへ持ち出せない。`work/form-spec.json` に対応表を持たせ、**スクリプトは論理項目名だけを知っている**状態にする。

論理項目は次の8つ。`rule_id` / `file` / `message` の3つが必須で、残りは任意（無ければフィンガープリントの精度が落ちるだけで動く）。

| 論理項目 | 必須 | 用途 |
|---|---|---|
| `rule_id` | ○ | ルール識別子。クラスタリングの第1キー |
| `file` | ○ | 指摘箇所のファイルパス |
| `message` | ○ | 指摘メッセージ。正規化してクラスタリングの第2キーにする |
| `line` | | 行番号。ソースを読むときに使う |
| `tool` | | ツール名。無い場合は `triage-scope.json` の `tools` から補う |
| `severity` | | 重大度。処理順の参考にする |
| `function` | | 関数名。フィンガープリントの精度が上がる |
| `code` | | 指摘箇所のコード断片。**あるとクラスタリングの精度が大きく上がる** |

`id` 列（申請書の通番）がある場合は `id_column` に指定する。書き戻し時の行の突き合わせに使い、行の並べ替えに強くなる。無い場合はシート上の行番号で突き合わせる。

## 書式を壊さないための決まり

openpyxl は**読み込んで保存し直すと、グラフ・図形・ピボットテーブル・一部の条件付き書式・コメントを落とす**。社内様式の申請書は装飾が多いので、これは実害になる。次の4点を `write_forms.py` は必ず守る。

1. **原本を直接開いて保存しない。** `out/` にファイルをコピーし、コピーに対して書く
2. **書き込むのはセルの値だけ。** 書式・列幅・行の挿入削除・シートの追加削除をしない
3. **書き込み後に検算する。** シート名の集合、各シートの最大行・最大列、書き込み対象外セルの値が、書き込み前と一致すること
4. **検算に失敗したらコピーを破棄して終了コード 1 を返す。** 壊れたファイルを残さない

それでも落ちるもの（グラフ等）はある。**原本は必ず別途保管し、`out/` の生成物は提出前に人が目で開いて確認する。** これはスクリプトでは保証できない。

### 検算だけでは防げない誤り

書式検算は「**書き込み対象外**のセルが変化していないこと」しか見ない。裏を返すと、**書き込み先の列を誤って指摘データの列（`指摘内容` など）に指定した場合、そのセルは書き込み対象なので検算をすり抜ける**。元の指摘が消えたまま合格してしまう。

そのため `write_forms.py` は、`application_form.columns` の列が `source.columns` や `id_column` と重なっていたら、書き込む前に終了コード 1 で止まる。この停止に遭ったら、様式の記入欄がどの列かを `--inspect` の出力で確認し直すこと。**指摘データの列を記入欄として使い回している様式なら、その様式自体を見直す必要がある。**

`.xlsm`（マクロ付き）は openpyxl の既定では保存時にマクロが失われる。`write_forms.py` は拡張子が `.xlsm` の場合 `keep_vba=True` で開くが、**マクロ付き様式は検算だけでは安全を確認しきれない**ので、T0 の合意時にユーザーへ明示すること。

## form-spec.json の構造

`assets/templates/form-spec.json.template` をコピーして埋める。3ブロックからなる。

| ブロック | 役割 |
|---|---|
| `source` | 指摘一覧をどこから読むか（ブック、シート、ヘッダ行、列対応） |
| `application_form` | 判定結果をどの列に書き戻すか |
| `deviation_record` | 逸脱記録書をどの雛形からどう作るか（`deviate` が0件なら不要） |

`header_row` は1始まり。ヘッダ行の次の行からデータとして読む。結合セルのヘッダは左上のセルにだけ値が入るため、`--inspect` の出力で空欄に見える列があれば、そこは結合セルを疑う。

`deviation_record.template` を省略すると、逸脱記録書は新規ブックとして生成される。社内様式がある場合は必ず指定すること。

## スクリプトの使い方

依存はスクリプトごとに違う。`read_findings.py` と `write_forms.py` のみ `openpyxl` を必要とし、無い場合は終了コード 2 で止まる。

### read_findings.py（T0・T1）

```
python scripts/read_findings.py --inspect <ブック.xlsx>
python scripts/read_findings.py --form-spec work/form-spec.json -o work/findings.json
```

`--inspect` は**セルの値をほとんど返さない**。シート名、各シートの行数・列数、ヘッダ行の候補（先頭10行のうち非空セルが最も多い行）とその列名だけを出す。数千行の申請書を会話に載せないための入口である。

通常モードは `form-spec.json` に従って指摘を読み出し、`findings.json` を書く。空行、ヘッダの再掲行、必須列が空の行は落とし、落とした件数を標準出力に出す。

| 終了コード | 意味 |
|---|---|
| 0 | 正常。`findings.json` を生成した |
| 1 | 様式の不整合（シートが無い、必須列が見つからない、有効な行が0件） |
| 2 | 引数の指定ミス、またはファイル・`openpyxl` が無い |

### cluster_findings.py（T2・T5）

```
python scripts/cluster_findings.py --findings work/findings.json --scope work/triage-scope.json -o work/clusters.json
python scripts/cluster_findings.py --clusters work/clusters.json --scope work/triage-scope.json --save-decisions
```

前者がクラスタリングと判定DBの再適用、後者が判定DBへの保存。保存モードでは `deferred` を保存しない。判定DBのパスは `triage-scope.json` の `decisions_db` から読む。

標準出力にクラスタ数、圧縮率、`auto_applied` 件数、`uniformity` の内訳を出す。

| 終了コード | 意味 |
|---|---|
| 0 | 正常 |
| 1 | 入力が不正（`findings.json` が空、判定DBが壊れている、判定が入っていないクラスタを保存しようとした） |
| 2 | 引数の指定ミス、またはファイルが無い |

### write_forms.py（T4）

```
python scripts/write_forms.py --clusters work/clusters.json --form-spec work/form-spec.json --out-dir out
```

申請書を `out/` にコピーして判定を書き戻し、`deviate` が1件以上あれば逸脱記録書も生成する。標準出力に書き込んだ行数と検算結果を出す。

| 終了コード | 意味 |
|---|---|
| 0 | 正常。書式検算も通過した |
| 1 | 書き込み先の列が見つからない、**指摘データの列と重なっている**、突き合わせに失敗した、または**書式検算に失敗した**（生成物は破棄される） |
| 2 | 引数の指定ミス、またはファイル・`openpyxl` が無い |

### check_triage.py（T5）

```
python scripts/check_triage.py work/clusters.json
```

未判定、不正な `verdict`、`false_positive` の FP コード欠落、`deviate` の DV コード・根拠・代替措置の欠落、`deferred` の理由欠落を検査する。標準出力に判定の内訳と `deferred` の一覧を出す。

| 終了コード | 意味 |
|---|---|
| 0 | 合格。未判定と根拠欠落がない |
| 1 | 未判定または根拠欠落がある |
| 2 | 引数の指定ミス、またはファイルが無い |

## よくある詰まり

| 症状 | 原因 | 対処 |
|---|---|---|
| `--inspect` でヘッダ行が見つからない | タイトル行や説明行が上にあり、非空セル数で負けている | `header_row` を目で見て指定する。自動推定は候補にすぎない |
| 必須列が見つからない | 列名に全角空白や改行が入っている | `form-spec.json` の列名は `--inspect` の出力からコピーする。手で打ち直さない |
| 有効な行が0件 | `header_row` が1行ずれている | データ行が「ヘッダ行の次」から始まっているか確認する |
| 書式検算に失敗する | 対象外セルが変化した。数式の再計算や日付書式の解釈で起きることがある | 検算を無効化せず、`form-spec.json` の書き込み列が正しいか確認する。それでも失敗するならユーザーに報告して判断を仰ぐ |
| 書き戻し後に行がずれる | 申請書側が並べ替えられている | `id_column` を指定して通番で突き合わせる |
| 「書き込み先の列が指摘データの列と重なっている」で止まる | `application_form.columns` に読み取り側の列名を指定している | 記入欄の列名に直す。同じ列を読み書き両方に使わない |
| クラスタがほとんど束ならない | `code` 列を指定していない | `form-spec.json` の `source.columns.code` に該当コードの列を指定する。ここが効きの大半を決める |
