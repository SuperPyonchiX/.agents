# 発火競合の処置

A2（競合候補の判断）の直前に読む。

スクリプトが候補として挙げるのは「description のトリガー文言か特徴語が重なっている組」でしかない。**重なっていること自体は問題ではない。** 隣接領域を扱うスキルの description が似るのは当然で、問題になるのは**エージェントがどちらを呼ぶべきか判断できないとき**だけである。

---

## まず何を見るか

判定に使うのは**両方の description だけ**。SKILL.md の本文は読まない。エージェントが発火を判断するとき手元にあるのも description だけなので、それ以上を読むと判定が甘くなる。

3つの質問に順に答える。

1. **この2つは同じ入力を受け取るか。** 入力が違えば（既存コード / 設計書 / 静的解析ツールの出力）、書き分けは容易
2. **同じ入力を受けるとして、成果物は違うか。** 違うなら振り分けの基準が存在する
3. **その基準が description から読み取れるか。** 入力・成果物で区別できれば相互の名指しは不要。併用する仕事なら、それを競合と取り違えない

---

## 判定表

上から順に当て、最初に該当したものを採る。

| # | 条件 | 処置 | 具体的にすること |
|---|---|---|---|
| 1 | 入力・成果物から区別できる、または併用する役割である | **問題なし** | 区別や併用の理由を1行残す。相互名指しを要求しない |
| 2 | 役割は違うが、実際の依頼文で選択を取り違える | **棲み分けを書く** | 取り違える相手だけ、担当範囲を1文で補う |
| 3 | 同じ入力・同じ成果物で、違いが粒度だけ（片方が他方の一部） | **統合する** | 広いほうに寄せ、狭いほうを削除するか `references/` に落とす。**削除はユーザーの判断を仰ぐ** |
| 4 | 片方の description が広すぎて、他方の担当まで拾ってしまう | **範囲を狭める** | 広いほうの対象を限定する語を足す。トリガー文言のうち他方に属するものを削る |
| 5 | 1本の description が2つ以上の異なる仕事を並べている | **分割する** | `workflow-skill-architect` に渡す。**このスキルの中で分割しない** |
| 6 | 上のどれにも当てはまらない、または判断に迷う | **要検討** | 迷った理由を書いて残す。2組続いたら A2 のループを止めてユーザーに相談する |

**「要検討」を安易に選ばない。** 逃げ道として使うと判定表が機能しなくなる。1〜5 を実際に当ててから選ぶこと。

## 処置の書き方

### 棲み分けを名指しで書く（処置2）

このリポジトリの既存スキルが使っている定型がある。同じ形に揃えると、読み手も機械も追いやすい。

```
〈何をするか〉。「〜して」「〜を〜して」で使う。
〈取り違える相手が担当する仕事〉は〈相手の名前〉。
```

自分の範囲を冒頭で言い切り、全体を200文字以内にする。不要な定型句や名指しを足さない。

振り分け先は3本まで。それ以上並ぶなら、そのスキルの範囲が広すぎる（処置4か5）。

### 範囲を狭める（処置4）

description を短くするのではなく、**限定する語を足す**。

| 広い | 狭めた |
|---|---|
| 「ドキュメントを作る」 | 「読者に作業を再現させる業務手順書を作る」 |
| 「コードを見る」 | 「既存の C++ コードを読んで規約違反を指摘する」 |
| 「不具合に対応する」 | 「動いているコードが期待どおり動かないときの原因究明を行う」 |

**発火の言い回しは減らさない。** スキルは使われなさすぎる傾向があるので、トリガー文言を削るのは他方に明確に属するものだけにする。

### 統合する（処置3）

削除を伴うので、**必ずユーザーの判断を仰ぐ**。提示するのは次。

- どちらに寄せるか、その理由
- 寄せた側に足りなくなる内容（狭いほうにしか無かった手順・参照・スクリプト）
- 削除ではなく `references/` への吸収で済まないか

## よくある誤判定

| 候補として挙がるが問題ではないもの | なぜ |
|---|---|
| 同じ技術領域を扱う複数のスキル（C++ 系、Next Design 系） | 特徴語が重なるのは当然。入力と成果物で分かれていればよい |
| 同じ成果物形式を出すスキル（どれも Markdown を書く） | 形式ではなく目的で分かれる |
| 定型句の重なり（「〜と言われたら使う」「明示的な言及がなくても」） | 定型なので情報がない。スクリプト側で除外しているが、取りこぼしはある |

| 候補に挙がらないが問題であるもの | どう気づくか |
|---|---|
| 語彙は違うが、実際の依頼文では同じ言い方をされる2本 | 実際の言い回しを2〜3個作って、どちらが発火すべきか自問する |
| 片方の description が抽象的すぎて、そもそも何にも発火しない | 「いつ使うか」が書かれているか。書かれていなければ競合以前の問題 |

**スクリプトの候補一覧は出発点であって、判定の全部ではない。** A2 を終えたあと、実際の依頼文言を2〜3個思い浮かべて、意図したスキルが選ばれるかを自問する。ずれていれば、候補に挙がっていなくても処置の対象にする。

## 判定の記録

`work/audit-report.md` の判定表に1行で書く。次回同じ組を見たときに、**同じ結論へ到達できる情報**を残すこと。

```markdown
| markdown-doc / show-me | 問題なし | 成果物が「Markdown ファイル」と「会話中の図」で分かれ、双方が名指しで振り分けている |
| cpp14-code-review / cpp14-defect-analysis | 問題なし | 入力が「読むコード」と「動かない現象」で異なる。defect 側が名指し済み |
| foo-doc / bar-doc | 棲み分けを書く | 成果物は違うが bar 側に名指しがない。bar の description 末尾に1文を追加する |
```
