# 本文監査（モデル更新時）

使うモデルが変わったときに、全スキルの**本文**を見直す手順。横断検査（A0〜A4）がスキル同士の関係を見るのに対し、こちらは各スキルの中身が新しいモデルでも意図どおりに働くかを見る。

古いモデル向けに書いた指示は、新しいモデルでは逆効果になることがある。強い強調（「必ず」「絶対に」の連発）への過剰反応や、もう要らない回避策、今のモデルでは古くなった固有名などがその典型。ただし見直しで**スキルの挙動を変えてはいけない**。直すのは指摘した行だけで、手順の構造には手を入れない。

## 流れ

| # | フェーズ | 出力 |
|---|---|---|
| B0 | 更新内容と対象の確定 | 旧→新モデル、対象スキル一覧の合意 |
| B1 | 機械抽出 | `work/body-scan.json` |
| B2 | スキル単位の判定ループ | `work/body-audit.md` の台帳 |
| B3 | 報告 | 判定の内訳と修正案の提示、是正の要否の回答 |
| B4 | 是正（任意） | 1スキルずつ修正 |

## B0: 更新内容と対象の確定

1. **どのモデルからどのモデルへ変わったか**をユーザーに確認する。推測で決めない。
2. 新しいモデルで変わった性質が分かっていれば聞く（強調への反応、ツール呼び出しの傾向、出力の長さなど）。公式の移行ガイドやリリースノートがあれば読む。**無ければ無いまま進め、B3 で「性質の変化は未確認」と明記する。**
3. リポジトリの規約ファイル（AGENTS.md など）があればパスを控える。B2 で規約との矛盾を見るのに使う。
4. 対象スキルの一覧を提示し、合意を得る。外部から取り込んだスキル（`LICENSE` を持つもの）は、上流との差分を増やさないため**既定で対象から外す**。含めるかはユーザーが決める。

**完了条件**: 旧→新モデルと対象スキルが確定し、合意を得たこと。

## B1: 機械抽出

```
python scripts/scan_bodies.py <skills-dir> -o work/body-scan.json [--skills a,b,c]
```

標準出力の表で、スキルごとの候補数と `score` を確認する。**この時点で直さない。**

| kind | 拾うもの | 目安 |
|---|---|---|
| `model-ref` | モデル名・モデル ID | 固定のモデル名が今も正しいか |
| `risky` | push・force・上書き・自動承認フラグなど | `confirm_nearby: false` は前後5行に確認の語が無い |
| `tool-specific` | 特定エージェント専用のツール名・機能 | 移植性の規約があれば照合する |
| `dated` | 年号と「最新」「時点」の組み合わせ | 時点依存の記述 |
| `emphasis_per_100` | 100行あたりの強調語数 | 6.0 を超えると `!` が付く |

**完了条件**: 終了コード 0 で `work/body-scan.json` が生成されたこと。終了コード 2 なら B0 に戻る。

## B2: スキル単位の判定ループ

台帳 `work/body-audit.md` を次の形で作り、1スキル判定するごとに追記する。

```
| ID | スキル | 箇所 | 種別 | 判定 | 修正案（1行） | 状態 |
|---|---|---|---|---|---|---|
| B-01 | notebooklm | SKILL.md:83 | risky | 維持 | —（生成系の必須フラグ。直前でユーザーの依頼を受けている） | 判定済 |
| B-02 | nextdesign-extension | references/dll-extension.md:39 | dated | 修正 | 「LTS の最新を確認する」に変え、版数は例示に下げる | 未着手 |
```

```
for スキル in score の高い順（1回の実行で最大 8 本）:
    候補の行とその前後 10 行だけを読む。本文を通読しない
    下の観点表を当て、候補ごとに 修正 / 維持 / 要確認 のどれかを付ける
    「維持」にも理由を書く（次回同じ行を見たときに同じ結論へ至れるように）
    候補が無くても、B0 で控えた規約ファイルとの矛盾が疑われる記述に気づいたら 1 行で記録する
    if 要確認 が 1 スキルで 3 件を超えた:
        そのスキルは部分的な見直しでは済まない。以降の判定を止めて B3 で「作り直しの相談」として挙げる
else:
    8 本を超えたスキルは「未判定」として一覧を残す。黙って打ち切らない
```

### 観点表

| 種別 | 修正にする条件 | 維持にする条件 |
|---|---|---|
| model-ref | 旧モデルを前提にした指示（出力が途中で切れる前提の分割、旧モデル名の固定指定） | 例示や履歴としての言及、ユーザーが選ぶ前提の記述 |
| emphasis 密度 | 取り消せる操作や好みの問題に強調が付いている。平叙文に戻す | 取り消せない操作・秘密情報・規約違反を防ぐ強調 |
| risky | 確認の手順が無いまま取り消せない操作をさせる。確認の一文を足す | 直前の手順で合意を取っている、復元できる操作、コマンドの必須フラグ |
| tool-specific | 規約で使わないと決めた独自機能に依存している | 「使えるなら使う、無ければこうする」の形で書かれている |
| dated | 版数や日付がそのまま判断基準になっている | 例示・履歴であると明記されている |

**自己監査の扱い**: このスキル（`skill-portfolio-audit`）と `workflow-skill-architect` も対象に含めてよいが、**判定だけ行い、修正はユーザーのレビューを経て手で行う。** 監査の基準そのものを監査の中で書き換えると、誤りが検出されなくなる。

**完了条件**: 対象スキルの全候補に判定と理由が付き、未判定のスキルがあれば一覧が台帳に残っていること。

## B3: 報告

1. 台帳を提示する。判定の内訳（修正 / 維持 / 要確認）、作り直しの相談に回したスキル、未判定、B0 で性質の変化を確認できなかった場合はその旨を含める。
2. 是正するかを尋ねる。ここで止まる。

**完了条件**: 報告を提示し、是正の要否について回答を得たこと。

## B4: 是正（任意）

1. **1スキルずつ**扱う。対象行の変更前後を並べて提示し、了承を得てから書き換える。
2. 直すのは台帳の「修正」の行だけ。ついでに周辺を書き直さない。
3. 書き換えたら次の2つを実行する。
   - `validate_skill.py <スキルディレクトリ>` が終了コード 0
   - `scan_bodies.py --skills <スキル名>` で、直した候補が消えているか、残っていても「維持」相当の形になっていること
4. 台帳の状態を「完了」にする。リポジトリの規約でコミット単位が決まっていれば従う（例: 1スキル1コミット）。

**完了条件**: 「修正」の行が全件「完了」になり、各スキルの検証が終了コード 0 であること。

**戻り条件**: 修正で validate の ERROR が出て、2回直しても消えない場合は、そのスキルの修正を元に戻して B3 の相談事項に回す。

## 禁止事項

- **候補の無い行や手順の構造まで書き直すこと。** 見直しの目的は挙動を保ったまま古さを取ることにある。
- **確認を得ずに本文を書き換えること。**
- **新しいモデルの性質を推測で断定し、それを根拠に直すこと。** 確認できていない性質は「未確認」と書く。
- **監査の基準（このスキルと `workflow-skill-architect`）を自動で書き換えること。**
