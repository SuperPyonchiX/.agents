# 監査チェックリスト

SKILL.md 手順2で読む。観点ごとに指摘を拾い、台帳に積む。判定はユーザーが行うので、ここでは「候補を漏れなく拾う」ことに徹する。

## a. コードから導出できる情報

エージェントが自力で調べられる内容は、書いてあっても毎セッションのコンテキストを無駄にする。

- ディレクトリ構成の羅列（`ls` / Glob で分かる）
- 依存パッケージの一覧（package.json / requirements.txt 等を読めば分かる）
- ファイルごとの役割説明のうち、ファイル名・配置から自明なもの
- ビルド・テストコマンドは**例外的に維持を推奨**（探すコストが高く、間違えると被害が出るため）

拾ったら「削除しても、エージェントは◯◯を読めば同じ情報に到達できる」の形で根拠を書く。

## b. 曖昧・矛盾した指示

従いようがない指示は、ある分だけノイズになる。

- 判定基準のない形容（「きれいに」「適切に」「なるべく」）だけの指示
- 同一ファイル内・ファイル間で食い違う指示（矛盾として台帳に積み、どちらが正か判定を仰ぐ）
- 誰も守っていないことが git 履歴から明らかな指示（例: 「必ず◯◯形式でコミット」に反するコミットが多数）
- 期限切れの指示（「移行が終わるまで」「当面は」で始まり、状況が変わっていそうなもの）

## c. 手順書に育った節（スキル切り出し候補）

「常に知っておくべき事実」ではなく「特定の場面の作業手順」になっている節は、Agent Skills に切り出すと必要なときだけ読まれる形になる。

判定の目安（複数当てはまるほど候補として強い）:

- 番号つき手順が5ステップ以上ある
- 特定の作業（レビュー、リリース、デプロイ、ドキュメント作成）のときにしか読まれない
- 「〜のときは」で始まる条件つきの長い節
- 節の中にさらに小見出しがある

切り出し候補は削減行数が大きいので優先度を高くする。ただし切り出し自体は別工程（workflow-skill-architect）。

## d. 重複

- 同じ内容が複数ファイルに書かれている（CLAUDE.md と AGENTS.md の二重管理）。片方を参照に置き換える提案をする
- 同じルールが言い回しを変えて複数回登場する
- README 等の人間向け文書と重複していて、エージェント向けに要らないもの

## e. 全体の長さ・構造

- ファイル合計が数百行を超えている場合、上の a〜d を適用した後の想定行数を見積もる
- 頻繁に参照される重要ルール（禁止事項・必須ゲート）がファイル後半に埋まっていないか。**削除ではなく移動**の提案をする
- 「説明」と「指示」が混在した節。指示だけ残して説明を削る提案をする

## 拾わないもの（指摘しない）

- 禁止事項・安全ゲート・確認手順そのものの削除。表現の簡潔化提案はよいが、機能を弱める提案はしない
- ユーザーの文体・好みに関する指示（応答スタイル等）。効果測定できないが、削る根拠もない
- 根拠を示せない「なんとなく長い」。行数と代替手段を示せないものは台帳に積まない
