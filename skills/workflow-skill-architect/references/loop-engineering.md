# ループエンジニアリング

反復を含むスキルを設計するときに読む。

## ループの三要素

どんなループも **生成 (produce) → 評価 (evaluate) → 修正 (revise)** に分解できる。スキルにはこの3つを別々の工程として書く。ひとまとめに「良くなるまで直して」と書くと、エージェントは評価をせずに書き直しだけを繰り返す。

評価は**可能な限り機械的に**する。優先順位:

1. スクリプト実行（テスト、リンター、スキーマ検証、ビルド） — 最も信頼できる
2. 明示的なチェックリストとの照合 — 項目が具体的なら実用的
3. LLM による自己評価 — 最後の手段。自分の出力には甘くなる

3 を使わざるをえないときは、「自分の出力を評価する」のではなく「他人が書いたものとして、この基準に照らして不合格な箇所を列挙する」形で書かせると多少マシになる。

### その先: ループごとスクリプトにできないか

上の優先順位は「評価をどこまで機械化するか」の話だが、もう一段上がある。**評価だけでなく修正と続行判定も決定的に書けるなら、ループ全体をスクリプトにして、エージェントは起動と結果報告だけを担当する。**

エージェントがループを回すと、周回ごとにコンテキストを消費し、前の周の記憶が薄れ、上限を数え間違える。決定的に書ける部分をエージェントに回させ続ける理由はない。

| 修正の性質 | どう実装するか |
|---|---|
| 決定的に書ける（テンプレート埋め、整形、リトライ、パラメータ探索） | ループごとスクリプト化する。エージェントは実行して結果を読むだけ |
| 判断が要る（何が悪いか仮説を立てて直す） | エージェントのループのまま。評価だけスクリプトに寄せる |
| 中間（判定と集計は機械的、修正は判断が要る） | 検証と履歴管理をスクリプトに、修正をエージェントに分ける |

スクリプト側に閉じ込める場合も、**終了条件の三点セットは変わらず必要**。上限回数は引数にし、収束しなかったことが終了コードと出力から分かるようにする。「静かに上限で止まって成功したように見える」のはスクリプトでも起きる。

判断材料になるのは「そのループを人間が手で回すとしたら、毎回同じ操作をするか」。同じならスクリプト、その場で考えるならエージェント。

## 終了条件は必ず3つ書く

ループを書くときは常にこの3つをセットで明記する。1つでも欠けると暴走するか、逆に1周で満足して止まる。

1. **成功条件** — これを満たしたら抜ける（例: 全テストがパス、スキーマ検証エラー0件）
2. **上限** — 最大何周まで（例: 最大5周）。上限に達したら**止まる**
3. **諦め条件（エスカレーション）** — 収束しないと判断する条件と、そのときの振る舞い

「良くなるまで繰り返す」は終了条件ではない。「エラーがなくなるまで、最大5回。3回目までに同じエラーが消えなければ、原因の仮説と試したことをまとめてユーザーに相談する」が終了条件。

### 収束しないときの扱い

同じ失敗が2回続いたら、**同じ方針での修正をやめる**。3回目も同じ直し方をするのはほぼ確実に無駄なので、スキルには次のように書く:

> 同一のエラーが2周続けて残った場合、修正を続けずに一度立ち止まる。何を試して何が変わらなかったかを列挙し、前提そのものを疑う（入力が想定と違う / 検証基準が誤っている / アプローチが不適合）。方針を変えられるならそれを明記して再開し、変えられないならユーザーに判断を仰ぐ。

## ループの型

### 検証ループ (verify-fix)
最も一般的。成果物を作り、検証にかけ、失敗した箇所だけを直す。**全体を作り直させない**こと（毎回ゼロから書き直すと直った箇所が壊れる）。「検証結果で指摘された箇所のみを修正し、それ以外は変更しない」と明示する。

### 探索ループ (generate-select)
候補を複数出して選ぶ。1周ごとに1案ずつ改良するより、3案出して比較したほうが良い結果になる領域（命名、設計案、文章の切り口）で使う。選択基準を先に決めてから生成させる（後から基準を作ると最初に出た案を正当化しがち）。

### 対話ループ (human-in-the-loop)
人間のフィードバックを挟む。**どこで止まってユーザーに聞くか**を工程として明示すること。書かないと、エージェントは全部やりきってから見せる（そして手戻りが大きくなる）。判断コストの高い分岐、後戻りが困難な操作、好みが結果を左右する箇所の直前に置く。

### 評価ループ (eval-driven)

上の3つは**成果物**を回すループだが、これは**成果物を作る指示のほう**を回す。スキルやプロンプトそのものを改善するときに使う。1周は「複数のテストケースを実行 → 結果を評価 → 指示を書き直す」。

他の型と決定的に違うのは、**1つの入力で直すと過学習する**こと。目の前のケースが通るように指示を書き足していくと、そのケース専用の指示になり、他の入力で使えなくなる。だから:

- **必ず複数のテストケースをまとめて回す。** 1件だけ見て直さない
- 修正は個別ケースへの継ぎ足しではなく、**一般化した記述**にする。「このときはこうする」を増やすのではなく、なぜそうするのかを書いて他のケースにも効くようにする
- 直っていないケースだけでなく、**すでに通っていたケースが壊れていないか**も毎周確認する（他のループの「指摘箇所のみ修正」に相当する歯止めがここでは効かない。指示の変更は全ケースに波及する）

評価が主観的な領域（文章のトーン、デザイン）では、無理に自動判定に落とさず人間のレビューを工程に組み込む。評価ループは対話ループと組み合わせるのが普通。

終了条件は他と同じ三点セットに加えて、**改善が頭打ちになったら止める**を入れる。全ケース合格に達しなくても、2周続けてスコアが動かないなら、指示の書き換えでは解決しない問題（テストケースが悪い、そもそも扱えない要求）を疑う。

比較対象を用意できると精度が上がる。**指示を使った場合と使わない場合**を同じ入力で走らせて差を見ると、指示が効いているのか元々できていたのかが分かる。効いていない指示は消したほうが軽くなる。

> このループの実装一式（テストケースの並列実行、比較対象の同時実行、採点、結果ビューア、description の自動最適化）を持つツールが使えるなら、自分で組まずにそちらへ渡してよい。使えるものが何かは環境による — SKILL.md の「実行環境による差分」を参照。

## 各周回のログ

周回ごとに何を記録するか決める。記録がないと、エージェントは前の周で何を試したか忘れて同じ修正を繰り返す。最小限これだけ:

```
## 周回 2
- 検証結果: 3件失敗 (test_parse_empty, test_unicode, test_large_file)
- 原因の仮説: 入力正規化が空文字を想定していない
- 加えた変更: normalize() に空チェックを追加
- 結果: 2件解消、test_large_file は残存（周回1でも失敗）
```

「結果」に前周との差分を書かせるのが肝。差分がゼロなら収束していないと判断できる。

## 擬似コードでの書き方

SKILL.md にはループを擬似コードで書くと誤解が少ない:

```
for 周回 in 1..5:
    成果物を生成 or 修正する
    scripts/validate.py を実行する
    if 検証パス:
        break（成功として終了）
    if 今回の失敗が前回と同一:
        方針を見直す or ユーザーに相談する
    失敗内容を progress.md に追記する
else:
    5周しても未達 → 残課題と試行履歴をまとめて報告し、勝手に続行しない
```

## よくある失敗

- **無限ループ**: 上限がない。必ず数値で上限を書く
- **評価の省略**: 生成と修正だけが書かれていて検証工程がない
- **全体再生成**: 毎周ゼロから作り直し、直った箇所が壊れる
- **早すぎる打ち切り**: 1周で「だいたい良い」と判断して抜ける。成功条件を機械的に書けば防げる
- **静かな失敗**: 上限に達したのに、達成したかのように報告する。上限到達時は必ず未達であることを明示させる
