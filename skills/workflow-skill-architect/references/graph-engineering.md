# グラフエンジニアリング

作業を複数のノードに分割し、依存関係を DAG として設計するときに読む。

## なぜグラフにするのか

長い手順を上から順に書くと、エージェントは「どこまでが1つの仕事か」「何が終わっていれば次に進めるか」を推測することになる。グラフにする目的は3つ:

- **並列化** — 依存のないノードは同時に進められる（サブエージェントがある環境で効く。ただし待ち時間が縮むだけでトークンは増えるので、スキルの本文では指示しない。後述の「サブエージェントに委任するノードを決める」）
- **再開可能性** — ノード単位で完了を記録できるので、途中から再開できる
- **責務の明確化** — 入力と出力が決まっていれば、そのノードだけを差し替え・再実行できる

逆に言えば、この3つが不要なら分割しなくていい。

## ノードの定義

**1ノード = 入力と出力が明示された1つの責務。** 目安は「一度に読み込める情報量で完結する作業」。

- 細かすぎる（10個以上のノード、1ノードが1コマンド）→ 受け渡しのオーバーヘッドが本体を上回る
- 粗すぎる（1ノードが「調査して設計して実装する」）→ 分割の意味がない

各ノードは、スキルルートの `assets/templates/node-contract.md` の形式で定義する:

```
### ノード: extract-requirements
- 目的: 入力文書から要件を構造化して抜き出す
- 入力: workspace/inputs/*.md
- 出力: workspace/work/01-requirements.json（スキーマは data-contracts.md 参照）
- 前提: 入力が空でないこと
- 失敗時: 要件が0件なら status="empty" で出力し、後続をスキップ
```

## エッジは「データ依存」で引く

エッジを引く基準は、**後続ノードが前ノードの出力を実際に必要とするか**。「なんとなくこの順番」で引かないこと。順序の都合で引いたエッジは並列化の機会を潰す。

判定法: 「ノードBは、ノードAの出力ファイルを読むか？」読まないなら、エッジは不要で並列に置ける。

## fan-out / fan-in

```mermaid
graph TD
    A[入力の解析] --> B[観点1で調査]
    A --> C[観点2で調査]
    A --> D[観点3で調査]
    B --> E[統合]
    C --> E
    D --> E
    E --> F[出力の生成]
```

**fan-out** で重要なのは、各枝が**重複しない担当範囲**を持つこと。「観点1〜3で調べて」だけだと同じことを3回調べる。各枝に「何を担当し、何を担当しないか」を書く。

**fan-in（統合ノード）** で重要なのは、**統合ルールを事前に決めておく**こと。ここを書かないと、エージェントは全部の出力を単純に連結する。決めておくこと:

- 矛盾があったときどちらを優先するか
- 重複をどう畳むか
- 一部の枝が失敗した場合に続行するか中止するか

## 条件分岐

分岐は「どの条件でどの枝に行くか」を表で書く。曖昧な自然言語だとエージェントごとに判断がぶれる。

| 条件 | 次のノード |
|---|---|
| 入力がコードファイル | analyze-code |
| 入力が仕様書 | analyze-spec |
| どちらでもない | ユーザーに確認 |

「どちらでもない」の行を必ず用意すること。想定外の入力で止まれるようにしておかないと、エージェントは無理やりどちらかに寄せる。

## サイクルはループとして切り出す

DAG に循環があるように見えたら、それはループなので、グラフのノードとして囲い込み、内部を `loop-engineering.md` に従って設計する。グラフの中に暗黙の巻き戻り（「問題があればステップ2に戻る」）を書くと、何周したのかを誰も管理しなくなる。

```mermaid
graph TD
    A[設計] --> B[実装ループ<br/>生成→テスト→修正 最大5周]
    B --> C[レビュー]
```

## サブエージェントに委任するノードを決める

**スキルの本文で委任を指示するのはレビュー（成果物を合否基準で検証する）ノードだけにする。** それ以外のノードには委任について何も書かない。分割するかどうかは実行する環境の判断に任せる。

- レビューは、書いた本人の文脈（意図、迷った末の判断）を持ち込まずに見ることに価値がある。委任の効果がトークンの増加に見合うのはここ
- 並列化で縮むのは待ち時間で、トークンは減らない。並列にできるノードがあっても、委任を指示しない
- Codex は直接の依頼か、スキル・AGENTS.md の委任の指示があったときだけサブエージェントを起動する。指示が無いノードは Codex では逐次で動き、Claude Code などは従来どおり自分の判断で分割する

例外として、本体のコンテキストがあふれる量の読み込み（数十ファイルの走査など）は委任を指示してよい。ただしノード表の「委任」列に理由を書く。理由を書けないなら指示しない。

次のノードは委任しない。

- ユーザーに確認・承認を求めるノード（サブエージェントからはユーザーに聞けない環境がある）
- 他のノードと同じファイルに書くノード
- 会話の中で決めた方針に依存し、それをファイルに書き出せていないノード

### 委任を書く形

**委任は、ノードごとに依頼の形で書く。** 許可の形（「並列に実行できる場合は〜」）では Codex は起動しない。

```
ノード review は、サブエージェントに渡して実行する。渡すのは work/02-draft.md と
references/criteria.md のパスだけにし、作成時の意図や判断の説明は渡さない。
サブエージェントが使えない環境では、作成を終えてから criteria.md を読み直し、
自分でレビューする。
```

### 委任するノードに渡す指示

渡す指示には必ず含める（テンプレートは `data-contracts.md` の「サブエージェントに渡す指示のテンプレート」）:

- タスクの説明（何をするか）
- 読むべき入力のパス（会話の文脈は引き継がれない前提で書く）
- 出力先のパスと形式
- **やらないこと**（範囲外の作業に踏み込ませない）

サブエージェントは呼び出し元の会話履歴を持たない。「さっき決めた方針で」は通じない。方針そのものをファイルに書いて、そのパスを渡す。

レビューを委任するときは、**成果物と合否基準だけを渡す。** 作成者の結論や「ここは意図的にこうした」という説明を渡すと、レビューがそれに引っ張られ、委任した意味が消える。

### サブエージェントが使えない環境

グラフは**トポロジカル順の逐次実行**として使う。設計としてのグラフは無駄にならない（依存関係と再開可能性の恩恵は残る）。委任するはずだったレビューは、作成が終わってから合否基準を読み直し、別の工程として自分で当てる。

## SKILL.md への書き方

グラフは mermaid で図示したうえで、ノード一覧を表にする。図だけだと入出力が読めず、表だけだと全体像が見えない。「委任」列には、委任を指示するノードだけ「サブエージェント」と書き、それ以外は「—」（指示しない）にする。

| ノード | 依存 | 入力 | 出力 | 委任 |
|---|---|---|---|---|
| parse-input | — | inputs/ | work/01-parsed.json | — |
| research-a | parse-input | work/01-parsed.json | work/02a-research.json | — |
| research-b | parse-input | work/01-parsed.json | work/02b-research.json | — |
| merge | research-a, research-b | work/02*.json | work/03-merged.json | — |
| review | merge | work/03-merged.json, references/criteria.md | work/04-review.json | サブエージェント |

表の下に、前節「委任を書く形」の依頼文を置く。表の列だけでは委任の指示として読まれないことがある。
