# データ契約（工程間・エージェント間の受け渡し）

工程やエージェントをまたいで成果物を渡すときに読む。

## 原則: 会話ではなくファイルで渡す

長い中間結果を会話のコンテキストに載せて次の工程に渡すのは、うまくいかない。量が増えると圧迫され、要約されて情報が落ち、サブエージェントには引き継がれない。

渡すのは **ファイルパス + 形式の約束**。受け手は必要な部分だけ読む。

```
❌ 「調査結果は以下の通りです（3000語）。これを踏まえて設計してください」
⭕ 「調査結果は work/02-research.json にある。schema は下記。これを読んで設計せよ」
```

## ワークスペースの構成

```
workspace/
├── inputs/     # 読み取り専用。元データ
├── work/       # 中間生成物。工程間の受け渡しはここ
├── outputs/    # 最終成果物。ユーザーに見せるものだけ
└── state.json  # 進捗（state-and-progress.md 参照）
```

`work/` と `outputs/` を分けるのが肝。分けないと、中間ファイルが最終成果物に混ざってユーザーが混乱する。

## ファイル名の規約

`NN-ノード名.拡張子` の形にする。番号があると依存順が一目で分かり、名前があると中身が分かる。

```
work/01-parsed.json
work/02a-research-market.json
work/02b-research-tech.json
work/03-merged.json
```

並列ノードは `02a` / `02b` のように同じ番号 + 添字にする。

## 出力形式を固定する

各ノードの出力形式は、スキルの中に**実例つきで**書く。スキーマだけだと解釈がぶれるので、最小の実例を必ず添える。

```json
{
  "node": "research-market",
  "status": "ok",
  "summary": "3行以内の要約。次の工程はまずここだけ読む",
  "items": [
    { "id": "m1", "claim": "...", "source": "...", "confidence": "high" }
  ],
  "issues": []
}
```

共通して入れておくと効くフィールド:

- `status`: `ok` / `partial` / `error` — 後続が続行判断に使う
- `summary`: 受け手が全文を読まずに済むための要約
- `issues`: 気づいた問題や前提の破れ。ここが空でないときは統合ノードが拾う

`status` と `summary` を共通化しておくと、統合ノードは全ファイルの summary だけ読んでから、必要なものだけ本体を開ける。コンテキストの節約になる。

## 失敗を型として表現する

失敗を自然文で書かせると、後続が判定できない。失敗も出力形式の一部として定義する。

```json
{
  "node": "research-b",
  "status": "error",
  "reason": "入力文書に該当セクションが存在しない",
  "recoverable": false,
  "partial_results": []
}
```

そのうえで、後続ノードの指示に「`status` が `error` の入力があった場合どうするか」を書く。書かないと、エージェントは失敗ファイルを正常なものとして読み、空の結果を正常な結果として扱う。

## 大きいデータの扱い

出力が大きい場合、受け渡すのは要約 + 参照パスにする。

```json
{
  "summary": "42件のログ異常を検出。うち重大が3件",
  "detail_path": "work/02-log-analysis-full.jsonl",
  "highlights": [ "...上位3件のみ..." ]
}
```

後続は要約で判断し、掘る必要があるときだけ detail_path を開く。

## サブエージェントに渡す指示のテンプレート

```
タスク: <1〜2行で何をするか>
読むもの:
  - workspace/inputs/spec.md（元の要求）
  - workspace/work/01-parsed.json（構造化済みの要件）
書くもの:
  - workspace/work/02a-research.json（形式は下記の通り）
形式: <スキーマ + 最小実例>
やらないこと: <範囲外の作業。実装まではしない、等>
判断に迷ったら: <ユーザーに聞くのか、仮置きして issues に書くのか>
```

最後の2行が抜けやすい。範囲を切らないとサブエージェントは仕事を広げるし、迷ったときの振る舞いを決めておかないと勝手に決めて先に進む。
