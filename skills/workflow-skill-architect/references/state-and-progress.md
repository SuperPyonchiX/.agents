# 状態管理と進捗管理

長時間実行、中断からの再開、進捗の可視化が必要なスキルを設計するときに読む。

## いつ必要か

次のどれかに当てはまるときだけ入れる。当てはまらないのに入れると、状態ファイルの更新が本来の作業を圧迫する。

- 工程が5つ以上ある、または実行が長い
- 途中で中断されうる（ユーザーの割り込み、コンテキスト上限、セッション終了）
- 複数のエージェント / セッションが同じ作業を引き継ぐ
- 失敗したときに最初からやり直すコストが大きい

## 2種類のファイルを使い分ける

**機械が読む `state.json`** — 再開判定に使う。構造が固定されていること。

```json
{
  "workflow": "skill-name",
  "started_at": "2026-08-11T09:00:00+09:00",
  "updated_at": "2026-08-11T09:24:00+09:00",
  "nodes": {
    "parse-input":  { "status": "done",    "artifacts": ["work/01-parsed.json"] },
    "research-a":   { "status": "done",    "artifacts": ["work/02a-research.json"] },
    "research-b":   { "status": "failed",  "error": "入力に該当セクションなし", "attempts": 2 },
    "merge":        { "status": "pending", "artifacts": [] }
  }
}
```

status は `pending` / `running` / `done` / `failed` / `skipped` の5つで足りる。増やさない。

**人間が読む `progress.md`** — ユーザーへの報告と、エージェント自身が経緯を思い出すために使う。追記のみ。

```markdown
## 09:24 research-b 失敗（2回目）
入力文書に「性能要件」の節が見つからない。1回目は見出し表記の揺れを疑って再試行したが同じ結果。
文書側に該当情報がない可能性が高いため、merge は research-a のみで続行し、欠落を出力に明記する。
```

`state.json` だけだと「なぜそうなったか」が残らず、`progress.md` だけだと再開時の判定が曖昧になる。両方が要るのはそのため。ただし小規模なワークフローなら `progress.md` 1つで十分なことも多い。

## 更新のタイミング

- ノード開始時に `running` に更新
- ノード完了直後に `done` + 生成物のパスを記録
- 失敗時は `failed` + 理由 + 試行回数

**まとめて最後に書かない。** 途中で落ちたときに何も残らないのでは、状態管理を入れた意味がない。

## 再開の手順をスキルに書く

状態ファイルを持つスキルには、必ず冒頭に再開の分岐を書く。

> 作業開始時に `workspace/state.json` の有無を確認する。存在する場合:
> 1. 内容とタイムスタンプをユーザーに提示し、続きから再開してよいか確認する
> 2. `done` のノードは再実行しない。その生成物をそのまま使う
> 3. `running` のまま残っているノードは中断されたものとみなし、`pending` に戻して再実行する
> 4. `failed` のノードは試行回数を確認し、上限に達していれば再試行せずユーザーに相談する

`done` のノードをスキップするには、**生成物が実際に存在するか**も確認すること。state.json が `done` でもファイルが消えていることはある。

## 冪等性

各ノードは「何度実行しても同じ結果になる」ように書く。特に副作用のある操作（ファイルの追記、外部への送信、コミット）は、再実行時に二重に起きないようにする。追記より上書き、追加より「あれば更新・なければ作成」を選ぶ。

## 並列実行時の書き込み

複数ノードが並列に走るとき、**同じファイルを複数が書かない**。状態が壊れる。

- 各ノードは自分専用のファイルに書く（`work/02a-*.json`, `work/02b-*.json`）
- `state.json` の更新は、並列実行を統括する側（親エージェント）だけが行う
- 統合は fan-in ノードが読み取り専用でまとめる

## ユーザーへの見せ方

進捗をどの粒度で報告するかもスキルに書く。書かないと、毎ノードごとに実況するか、最後まで沈黙するかのどちらかに振れる。目安:

- 節目（fan-out の開始、ループの収束、統合の完了）で1〜2行
- 失敗と方針変更は必ず即時に報告する
- 逐一の成功報告は不要
