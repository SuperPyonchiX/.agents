# ファイル分割（プログレッシブディスクロージャ）

SKILL.md が長くなってきたとき、または分岐ごとに必要な情報が違うときに読む。

## 3階層の読み込み

| 階層 | 中身 | 読まれるタイミング |
|---|---|---|
| メタデータ | name + description | 常時（全スキル分が並ぶ） |
| SKILL.md 本文 | ワークフローと判断基準 | そのスキルが発火したとき |
| `references/` `scripts/` `assets/` | 詳細・実装・雛形 | 必要になったときだけ |

コストが違う。description は全スキル分が常にコンテキストにあるので短く鋭く。SKILL.md 本文は発火のたびに全文読まれるので、**判断に必要なものだけ**を置く。詳細は下の階層に落とす。

## 何を SKILL.md に残すか

判定基準は「**この情報がないと、どの参照を読むべきか判断できないか**」。

| SKILL.md に置く | 参照ファイルに落とす |
|---|---|
| 全体のワークフロー | 各工程の詳細な手順 |
| 分岐の判定表 | 分岐先ごとの具体的なやり方 |
| 全工程で守るべき原則 | 一度しか使わない仕様やスキーマ |
| 参照ファイルの一覧と読むタイミング | 長い実例、テンプレート、失敗例集 |

## 分割の判断基準

**排他的な分岐がある** — どれか1つしか読まないなら、必ず分ける。

```
cloud-deploy/
├── SKILL.md          # どのクラウドか判定する
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

**使用頻度が違う** — 毎回使うものは本文、稀にしか使わないものは参照へ。

**長さ** — SKILL.md が 500 行に近づいたら分割を検討する。ただし行数は目安で、本質は「読む側が必要としない情報が混ざっているか」。

**逆に分けないほうがいい場合** — 常に一緒に読むものを分けると、読み込みが増えるだけで損。相互参照が多くて行き来が必要になるものも、まとめておいたほうがいい。

## リンクには必ず「いつ読むか」を添える

これが最も落としやすい。ファイル名を並べるだけでは、エージェントはそれを読まない（または全部読んで本末転倒になる）。

```
❌ 詳細は references/loop-engineering.md を参照。

⭕ 反復・検証・自己修正を含むスキルを書くときは、
   references/loop-engineering.md を読んでから工程を書く。
```

参照ファイルが 300 行を超えるなら、冒頭に目次を置く。

## スクリプトは読まずに実行できる

決定的な処理（検証、変換、集計、パッケージング）は `scripts/` に置く。スクリプトは**中身をコンテキストに読み込まなくても実行できる**のが利点。毎回エージェントに同じコードを書かせるより、速く、確実で、コンテキストも食わない。

SKILL.md には使い方だけ書く:

```
検証には scripts/validate.py を使う:
    python scripts/validate.py <対象パス>
終了コード 0 で合格。不合格時は失敗項目を標準出力に列挙する。
```

## assets はコピーして埋める

テンプレート、雛形、定型文は `assets/` に置き、「コピーして埋める」と指示する。SKILL.md 本文に長いテンプレートを貼ると、使わない回でもコンテキストを食う。
