# Workflow Skill Architect

エージェントに渡すスキルを「手順書」ではなく「実行アーキテクチャ」として設計するためのスキル。

前提として押さえておくべきこと: スキルの品質を決めるのは文章量ではなく、**制御構造が明示されているかどうか**。うまくいかないスキルはたいてい、(1) 終了条件のないループ、(2) 依存関係が曖昧なまま並べられた手順、(3) 中断すると最初からやり直しになる状態管理の不在、(4) 次の工程に何を渡すのか決まっていないデータ受け渡し、のどれかで壊れる。この4点を最初に決めることが、このスキルの中心的な仕事。

---

## 全体の流れ

1. **意図をつかむ** — 何をさせたいのか、いつ発火させたいのか
2. **ワークフロー構造を判定する** — 直列 / ループ / グラフ / ハイブリッド
3. **必要な設計ドキュメントだけを読む** — 判定結果に応じて `references/` から
4. **骨組みを生成する** — ディレクトリ、SKILL.md、参照ファイル、必要ならスクリプト
5. **状態とデータ契約を確定する** — 必要な場合のみ
6. **レビューする** — `scripts/validate_skill.py` + `references/review-checklist.md` を検証ループで回す
7. **テストして反復する**

**重要な原則: 構造は必要になってから足す。** ループも状態ファイルもデータ契約も、それ自体がエージェントの負担になる。3ステップで終わる作業に DAG と state.json を持ち込むと、本来の作業よりオーバーヘッドのほうが大きくなる。以下の判定表で「構造なし」に該当したら、堂々と構造なしで書くこと。

---

## ステップ1: 意図をつかむ

会話の中に既に材料があることが多い（「さっきの作業をスキルにして」など）。その場合はまず会話から抽出し、足りない部分だけ質問する。最低限そろえる:

1. **このスキルは何をできるようにするのか**（成果物は何か）
2. **いつ発火してほしいのか**（ユーザーがどんな言い方をするか。description の材料になる）
3. **成功の判定基準は何か**（これが曖昧だとループが設計できない）
4. **決定的に処理できる部分はあるか**（あれば `scripts/` に切り出す。LLM に毎回やらせるより速く確実）

3 は特に重要。「良い感じの資料ができること」では検証工程が書けない。「全テストがパスすること」「スキーマに適合すること」「章立てがテンプレ通りであること」のように、機械的または目視で一意に判定できる形にまで落とす。落としきれない主観的なもの（文章のトーン、デザインの好み）は無理に基準化せず、人間のレビューを工程に組み込む。

## ステップ2: ワークフロー構造を判定する

| 兆候 | 採る構造 | 読む参照ファイル |
|---|---|---|
| 手順が固定で分岐がなく、各ステップが前の出力をそのまま受ける | **直列**（構造なし。箇条書きの手順で十分） | なし |
| 一発で品質基準を満たせず、生成→検証→修正の反復が要る | **ループ** | `references/loop-engineering.md` |
| 独立に進められる部分作業があり、最後に統合する | **グラフ (DAG)** | `references/graph-engineering.md` |
| 実行が長い / 途中で中断されうる / 扱うファイルが多い | **状態管理を追加** | `references/state-and-progress.md` |
| サブエージェントや別セッションに作業を渡す | **データ契約を追加** | `references/data-contracts.md` |
| SKILL.md が 500 行に近づく / 分岐ごとに読む内容が違う | **ファイル分割** | `references/file-splitting.md` |

複数該当は普通のこと。実務でよくある組み合わせは「グラフの各ノードの中に検証ループがある」形。その場合はグラフを外側、ループを内側として、両方の参照を読む。

判定した構造は、生成する SKILL.md の中に **図または明示的な記述として残す**こと。構造がテキストに書かれていなければ、それを使うエージェントには存在しないのと同じ。

## ステップ3〜4: 骨組みを生成する

```
skill-name/
├── SKILL.md          # 必須。frontmatter (name, description) + 本文
├── references/       # 分岐ごと・詳細ごとに読み込むドキュメント
├── scripts/          # 決定的処理。読み込まずに実行できる
└── assets/           # 出力に使うテンプレート等
```

このスキル自身がこの構成の実例になっている。`references/` に設計ドキュメント、`scripts/` に検証スクリプト、`assets/templates/` に雛形を置いている。

SKILL.md 本文の推奨構成（`assets/templates/SKILL.md.template` をコピーして使う）:

- 冒頭 2〜3 行で「このスキルは何をするものか」と設計上の勘所
- ワークフロー図（グラフなら mermaid、ループなら擬似コード）
- 各工程の指示（命令形で書く）
- 終了条件・失敗時の扱い
- 参照ファイルへのポインタ（**いつ読むかを添えて**）

frontmatter の `description` は発火の唯一の手がかりなので、**何をするか + どんな場面で使うか**を両方書く。エージェントはスキルを使わなすぎる傾向があるので、やや押しつけがましいくらいでちょうどいい（「〜という話が出たら、明示的に言及がなくても使うこと」）。日本語で使うスキルなら、想定される日本語の言い回しを description に含めること。**英語は併記しない** — 日本語でしか依頼しないなら重複するだけで、発火に寄与せずコンテキストだけ食う。英語で依頼する運用があるとき、または description を語句一致で絞り込むツールを使うときに限り、英語の発火語と排他先を1文だけ足す。

## ステップ5: 状態とデータ契約

グラフ・ループ・長時間実行のいずれかがある場合のみ。`references/state-and-progress.md` と `references/data-contracts.md` を読み、次を決める:

- ワークスペースのディレクトリ構成と、成果物のファイル名規約
- 各ノードが出力する形式（JSON スキーマ or テンプレート）
- 進捗の記録先と更新タイミング
- 中断からの再開手順

`assets/templates/` に state ファイルとノード契約の雛形がある。

## ステップ6: レビュー（検証ループ）

レビューは一度当てて終わりにしない。**生成 → 検証 → 修正**の反復として回す。成果物はステップ3〜5 で出来ているので、ここは検証と修正を回す工程。

```
for 周回 in 1..3:
    python scripts/validate_skill.py <生成したスキルのディレクトリ>
    references/review-checklist.md の主観項目を当てる
    if ERROR 0件 かつ 主観項目に未対応なし:
        break（成功として終了）
    if 今回の指摘が前回と同一:
        同じ直し方を繰り返さない。前提を疑い、方針を変えるかユーザーに相談する
    指摘された箇所のみを修正する（スキル全体を書き直さない）
else:
    3周しても未達 → 残っている指摘と試したことをまとめて報告する。
    達成したかのように報告しない
```

**検証**は2段構え。まず機械的に:

```
python scripts/validate_skill.py <スキルディレクトリ>
```

終了コード 0 で合格。ERROR は必ず直す。WARN は判断のうえ対応する。このスクリプトが見るのは frontmatter、リンク切れ、孤児ファイル、行数といった**機械判定できる項目だけ**なので、合格しても「良いスキル」になったことにはならない。

続けて `references/review-checklist.md` を当てる。スクリプトが見ない主観項目がレビューの本体で、特に次の2つは落としやすい:

- 終了条件（成功条件・上限・諦め条件）のないループが混入していないか
- 参照ファイルへのリンクに「いつ読むか」が添えられているか

**修正**は指摘された箇所のみに限定する。毎周ゼロから書き直すと、前の周で直した箇所が壊れる。

**上限は3周**。到達したら止まり、未達であることを明示して報告する。

## ステップ7: テストして反復する

現実的なユーザー発話を 2〜3 個作り、ユーザーに見せて合意を取ってから実行する。サブエージェントが使える環境なら並列で、使えない環境（Claude.ai など）なら自分で SKILL.md を読んで順に実行し、結果をユーザーに提示して感想を聞く。

見るポイントは出力の良し悪しだけではない。**指示のどこで迷ったか**を自分で言語化して、その箇所を書き直す。迷ったということは、そこの記述が曖昧だということ。

ここから先、評価の自動化・ベンチマーク・description の最適化まで踏み込むなら `skill-creator` に渡す。次節を読むこと。

---

## skill-creator との役割分担

Anthropic 提供の `skill-creator` スキルとは**競合しない。両方が発火するのが正常**で、どちらか一方を選ぶものではない。担当する軸が違う。

| | このスキル | skill-creator |
|---|---|---|
| 担当 | **アーキテクチャ** — 制御フローをどう構造化するか | **プロセス** — 測りながら反復して良くするか |
| 具体的には | ループの終了条件、DAG 分解、状態管理、データ契約 | テストケースの実行、採点とベンチマーク、description 最適化、パッケージング |
| 主な出力 | 構造が明示された SKILL.md 一式 | 評価結果と、それに基づく改訂 |

**両方が発火したら、順に使う。** 典型的な流れ:

1. このスキルで構造を設計し、スキル一式を書く（ステップ1〜6）
2. `skill-creator` の評価ループに渡し、テストケースを回して測る
3. 結果を持ってこのスキルの観点で構造を直す（終了条件が緩い、ノードの粒度が悪い、等）
4. 2〜3 を繰り返し、仕上がったら `skill-creator` でパッケージングする

つまり **構造設計はこちら、評価インフラは向こう**。評価ループそのものの設計思想は `references/loop-engineering.md` の「評価ループ (eval-driven)」にあるので、渡す前に読んでおくと結果を解釈しやすい。

片方しか無い状況でも困らないようにしてある。`skill-creator` が無ければステップ6の検証ループとステップ7の手動テストで足りるし、逆に構造が単純なスキルなら `skill-creator` だけで完結する。

## 実行環境による差分

このスキルの `references/` は環境に依存しない。環境ごとに変わるのは次の3点だけで、いずれも**無ければ代替手段がある**。他の環境（Codex 等）へ持ち出すときはここだけ読み替えればよい。

| 前提 | ある場合 | 無い場合 |
|---|---|---|
| サブエージェント | グラフの独立ノードを並列実行する | トポロジカル順に逐次実行する。設計としてのグラフは無駄にならない（`references/graph-engineering.md`） |
| `skill-creator` | 評価・最適化・パッケージングを渡す | ステップ6の検証ループとステップ7の手動テストで代替する |
| `.skill` パッケージング | `skill-creator` の packaging スクリプトで生成する | ディレクトリのまま配置すれば動く。パッケージ化は必須ではない |

スキルを書くときも同じ配慮をする。特定の環境でしか動かない手順を本文に埋め込まず、「使えるなら使う、無ければこうする」の形で書くこと。

## 参照ファイル

必要になったときに読む。全部読む必要はない。

| ファイル | 読むタイミング |
|---|---|
| `references/loop-engineering.md` | 反復・検証・自己修正を含むスキルを書くとき |
| `references/graph-engineering.md` | 作業を分割して並列化・統合するとき、サブエージェントに割り振るとき |
| `references/state-and-progress.md` | 長時間実行、中断からの再開、進捗の可視化が要るとき |
| `references/data-contracts.md` | 工程間 / エージェント間で成果物を受け渡すとき |
| `references/file-splitting.md` | SKILL.md が長くなってきたとき、分岐が増えたとき |
| `references/review-checklist.md` | 書き終わったとき（毎回） |

## スクリプト

```
python scripts/validate_skill.py <スキルディレクトリ>
```

ステップ6の検証工程で実行する。frontmatter の有無、`name` とディレクトリ名の一致、`references/` `scripts/` `assets/` へのリンク切れ、孤児ファイル（`references/` に限らず `templates/` `examples/` `assets/` も再帰的に走査し、SKILL.md からも `references/` からも参照されていないものを WARN する）、行数超過を機械的に判定する。終了コード 0 で合格、ERROR があれば 1 を返し、指摘を標準出力に列挙する。主観的な項目は見ないので、`references/review-checklist.md` と併用すること。

## テンプレート

`assets/templates/` に雛形がある。コピーして埋める。

| ファイル | 使うとき |
|---|---|
| `assets/templates/SKILL.md.template` | SKILL.md 本文を書き始めるとき（ステップ3〜4） |
| `assets/templates/node-contract.md` | グラフのノードを定義するとき（ステップ5） |
| `assets/templates/state.json.template` | 状態管理を入れるとき（ステップ5） |
