# Implementation Plan Grill

計画の穴は書いた本人には見えない。だから観点表を機械的に当てて論点を洗い出し、1件ずつ確定するまで着工させないのがこのスキルの仕事。失敗しやすいのは (1) 質問せずに推測で埋めて着工する、(2) 調べれば分かることを質問してユーザーの時間を奪う、の2つ。

## 使う場面

| 場面 | 入力 | 質問の出し方 |
|---|---|---|
| 既にある計画を問い詰める | 会話・Markdown・チケット・設計書。他人が書いたものを含む | 手順3のとおり、推奨回答つきで質問する |
| 自分が計画を書いている途中（Claude Code のプランモードなど） | 書きかけの計画 | 手順2の観点表を当てて論点を洗う。質問は環境の仕組み（プランモードの質問機能）に任せ、無い環境なら手順3と同じ |

計画が存在しない（「〜を作りたい」だけ）場合は対象外。先に計画の草案を一緒に作るかを確認する。

## 手順

### 1. 材料を読む

計画が参照しているコード・設計書・過去の類似実装を**先に自分で読む**。ここを飛ばすと後の論点が的外れになる。

### 2. 観点表を当てて論点台帳を作る

計画を次の観点でスキャンし、書かれていない・決まっていないものを論点として台帳に積む。

| 観点 | 拾うもの |
|---|---|
| 前提 | 暗黙の仮定。「〜のはず」で書かれている箇所 |
| スコープ | やらないことが明記されているか。膨らむ余地 |
| 入出力契約 | 各工程・関数の入力と出力。境界値の扱い |
| 依存関係 | 変更が波及する先。他の作業・ライブラリとの競合 |
| エッジケース | 空・最大・重複・同時・順序逆転・異常系 |
| 失敗時の挙動 | 途中で失敗したらどうなるか。ロールバック手段 |
| 検証方法 | 完成をどう判定するか。判定可能な形になっているか |

対象が組込みC/C++（割り込み・RTOS・レジスタ・車載規格が絡む）なら、`references/embedded-probes.md` を読んで8観点を追加する。

台帳は会話に表で提示する（件数が多ければファイルに書き、パスを示す）。

```
| # | 論点 | 観点 | 状態 |
|---|---|---|---|
| 1 | 入力CSVが空のときの挙動が未定義 | エッジケース | 未解決 |
| 2 | 既存のparse系関数と役割が重複しないか | 依存関係 | 未解決 |
```

### 3. 論点を潰す

- コード・資料・git履歴から答えが読み取れる論点は、**質問せず自分で調べて確定**させる。根拠（ファイルパス・該当箇所）を台帳に残す
- 残りを手戻りが大きい順に**1回3件まで**、**必ず推奨回答つき**で質問する（「AとBがありえます。過去の類似実装がAなので、Aを推奨します」）。推奨なしの丸投げは禁止する
- 回答を台帳に反映する。台帳の状態（確定◯件 / 未解決◯件）を毎回提示する
- 質疑の往復は**3回まで**。残った論点は「保留」に落とし、リスクとして計画書に明記する

### 4. 計画書に固める

未解決論点が0件になったら（または打ち切られたら）、結果を計画書にまとめる。

- 保存先: 元の計画がファイルならそのファイルを更新する。会話上の計画だったら保存先をユーザーに確認する（不要と言われたら会話への提示のみ）
- 構成: 確定した計画本文 / 確定事項（論点と結論の一覧）/ 保留事項（残った論点とリスク）/ 検討して却下した代替案

**完了条件: 計画書（または会話での最終版）を提示し、ユーザーから「これで着工してよい」の合意を得たこと。**

## 終了条件と失敗時の扱い

- 成功: 未解決論点0件、かつユーザーが最終版に合意した
- 打ち切り: 質疑が3往復に達した、またはユーザーが「もう十分」と言ったら、残りを保留に落として計画書に明記する。**保留を黙って捨てない**
- 想定外: 質疑の途中で計画の根幹（目的そのもの）が揺らいだら中断し、「計画を作り直すか」をユーザーに確認する

## 禁止事項

- ユーザーが回答していない論点を、推測で「確定」に変えること
- コードや資料を読めば分かることを質問すること
- 合意前に実装を始めること
