# Implementation Plan Grill

論点の洗い出しそのものは任せてよい。このスキルが縛るのは、洗い出した論点の**閉じ方**である。失敗しやすいのは (1) 答えの出ていない論点を推測で埋めて着工する、(2) 調べれば分かることを質問してユーザーの時間を奪う、(3) 打ち切った論点を黙って捨てる、の3つ。

## 使う場面

| 場面 | 入力 | 進め方 |
|---|---|---|
| 既にある計画を問い詰める | 会話・Markdown・チケット・設計書。他人が書いたものを含む | 手順1〜4 |
| 自分が計画を書いている途中（プランモードなど） | 書きかけの計画 | 手順1〜2で論点を洗う。質問は環境の質問機能に任せ、無ければ手順3 |
| 計画は無く、要件書・仕様書・議事録などの資料から Q&A 表が欲しい | 資料 | `references/document-qa.md` の Q1〜Q5。要確認が残ったら手順3に合流する |

計画が存在しない（「〜を作りたい」だけ）場合は対象外。先に計画の草案を一緒に作るかを確認する。

## 手順

### 1. 材料を読む

計画が参照しているコード・設計書・過去の類似実装を、論点を立てる前に自分で読む。

### 2. 論点台帳を作る

前提・スコープ・入出力契約・依存関係・エッジケース・失敗時の挙動・検証方法の7観点で、書かれていない・決まっていないものを論点として台帳に積む。対象が組込みC/C++（割り込み・RTOS・レジスタ・AUTOSAR/CERT が絡む）なら、`references/embedded-probes.md` の8観点も当てる。

台帳は `| # | 論点 | 観点 | 状態 | 根拠・回答 |` の表で会話に提示する。件数が多ければファイルに書き、パスを示す。

### 3. 論点を潰す

- コード・資料・git履歴から答えが読み取れる論点は質問せずに確定させ、根拠（ファイルパス・該当箇所）を台帳に書く
- 残りは手戻りが大きい順に**1回3件まで**、**必ず推奨回答と理由をつけて**質問する（「AとBがありえます。過去の類似実装がAなので、Aを推奨します」）
- 回答を台帳に反映し、「確定◯件 / 未解決◯件 / 保留◯件」を毎回提示する
- 質疑は**3往復まで**。残った論点は「保留」に落とす

### 4. 計画書に固める

- 保存先: 元の計画がファイルならそのファイルを更新する。会話上の計画なら保存先をユーザーに確認する（不要なら会話への提示のみ）
- 構成: 確定した計画本文 / 確定事項（論点と結論）/ 保留事項（論点とリスク）/ 却下した代替案

**完了条件: 最終版を提示し、ユーザーから「これで着工してよい」の合意を得たこと。**

## 終了条件と失敗時の扱い

- 成功: 未解決論点0件、かつユーザーが最終版に合意した
- 打ち切り: 3往復に達した、またはユーザーが「もう十分」と言ったら、残りを保留として計画書に明記する
- 想定外: 計画の根幹（目的そのもの）が揺らいだら中断し、「計画を作り直すか」をユーザーに確認する

## 禁止事項

- ユーザーが回答していない論点を、推測で「確定」に変えること
- 根拠（ファイルパス・資料の箇所・ユーザーの回答）を示せない論点を「確定」にすること
- コードや資料を読めば分かることを質問すること
- 推奨回答なしで質問を丸投げすること
- 保留にした論点を計画書から落とすこと
- 合意前に実装を始めること
