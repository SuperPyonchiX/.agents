# 組込みC/C++向けの追加観点

SKILL.md 手順2で、対象が組込みC/C++と分かったときに読む。汎用観点（前提・スコープ・入出力契約・依存関係・エッジケース・失敗時の挙動・検証方法）に、この8観点を追加して論点を拾う。

各観点の質問例は「そのまま聞く」ためのものではない。計画に該当する記述があるか確認し、**書かれていない場合にだけ**論点として台帳に積む。

## 1. 割り込み・並行性

- この処理は割り込みコンテキストとタスクコンテキストのどちらで動くか。両方から呼ばれる関数はあるか
- 共有変数への同時アクセスはあるか。排他はどの機構か（割り込み禁止 / ミューテックス / アトミック）。禁止区間の長さは許容内か
- ISR の中でやる処理は最小になっているか。重い処理をタスク側へ逃がす設計か
- 再入の可能性はあるか（同じ割り込みの多重、ネスト）

## 2. タイミング・実時間性

- デッドラインはあるか。最悪実行時間（WCET）はデッドラインに収まる見込みか
- 周期処理のジッタ許容値は決まっているか
- タイムアウトはすべての待ちに入っているか。無限待ちになる経路はないか
- タイマのオーバーフロー（カウンタ一周）を考慮しているか

## 3. メモリ・リソース

- 動的確保を使うか。使うなら断片化と枯渇時の挙動が決まっているか（原則は静的確保）
- スタック使用量の見積りはあるか。再帰・大きなローカル変数はないか
- ROM/RAM の残量に対して増分は許容内か
- バッファサイズの根拠は何か。あふれたときの挙動が決まっているか

## 4. 電源・リセット・状態復帰

- 処理の途中で電源断・リセットが起きたらどうなるか。不揮発データの整合性は保てるか
- 初期化順序に依存はあるか（ペリフェラル→ドライバ→アプリの順で成立しているか）
- ウォッチドッグとの関係。この処理が長引いたときにWDTを踏まないか

## 5. フェイルセーフ・異常系

- センサ値・通信データの異常（範囲外、欠落、遅延、重複）をどこで検出し、どう縮退するか
- エラーの通知先と記録方法は決まっているか
- 故障注入テストで検証できる設計か

## 6. ハードウェア依存

- 対象マイコン・ボードのエラッタに該当する機能を使っていないか
- レジスタアクセスに volatile が要る箇所を認識しているか
- エンディアン・アラインメント・パディングに依存する箇所はあるか（通信フレーム、共用体キャスト）
- 実機がないと検証できない部分はどこか。その部分の検証計画はあるか

## 7. 規約適合（AUTOSAR C++14 / CERT C++）

- 計画している実装手段に、規約が禁止する構文・機能が含まれていないか（例外、動的キャスト、可変長配列など、プロジェクトの適用プロファイルによる）
- 逸脱が必要になりそうな箇所は、先に逸脱申請の要否を確認したか
- 静的解析（CodeSonar / Helix QAC）で新たな指摘が大量に出る見込みはないか

## 8. テスト容易性

- ハードウェア依存部を切り離してホスト環境で検証できる構造か（依存の注入点はあるか）
- 割り込みタイミング起因の不具合を再現する手段はあるか
- 検証の合否は機械判定できる形か（目視波形確認だけに頼っていないか）
