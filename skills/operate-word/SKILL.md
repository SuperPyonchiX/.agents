# Word 文書の操作

python-docx で .docx を読み書きし、見た目は PDF にして画像で確かめる。
失敗しやすいのは4点。既定のテンプレートが US Letter で和文フォントも効かない、見た目は1語でも内部で断片に分かれていて置換が当たらない、既存文書のスタイルを無視して書式を直書きする、変更履歴の包み忘れで直した箇所が校閲で見えない。

## 手順

### 1. 中身を把握する

```
python scripts/inspect_docx.py <docx> [--outline] [--section N] [--full] [--out FILE]
```

用紙・余白・ヘッダー・フッター・使われているスタイル・表や画像やテキストボックスや脚注の数・コメントと変更履歴の件数・フィールドと、本文（見出しは `#`、箇条書きは `-`、表は Markdown の表、テキストボックスと脚注も含む）が出る。python-docx の `paragraph.text` と違い、変更履歴で挿入した文字とコンテンツコントロールの中の文字も出る。

出力を絞る:

- 本文が2万字を超えると、本文の代わりに `§番号` 付きの見出し一覧が出る。必要な節だけ `--section N` で読む
- 全文を読む・要約する依頼では `--full` を付けるか、`--out` でファイルに出して分けて読む
- 置換だけの依頼なら全文を出さず、`--outline` か手順2の `--dry-run` から始める
- 読み取り・要約だけの依頼はこの手順で終わる

`.doc` は読めない（終了コード2）。ユーザーの了承を得て Word か LibreOffice で `.docx` に変換してから扱う。

### 2. 作る・直す

| やること | やり方 |
|---|---|
| 新しく作る | `references/creating.md` を読み、雛形（A4・和文フォント・ページ番号）から始める。社内様式を渡されたらそれを開いて本文だけ入れる |
| 文言を置き換える | `docx_replace.py` で置換する（下記）。変更履歴付きなら `--track` |
| 段落・表を足す・消す | python-docx で直接編集する。足す段落のスタイルは、前後の段落と同じものを `inspect_docx.py` の出力から選ぶ |
| コメント、置換以外の変更履歴 | `references/review-markup.md` を読む |
| どれにも当てはまらない（脚注・テキストボックスの追加や編集、差し込み印刷など python-docx が扱わない要素） | 止まり、扱えない要素であることをユーザーに伝え、Word での手作業か作り直しかを確認する。XML を推測で書き換えない。文言の置換だけなら脚注・テキストボックスも `docx_replace.py` で扱える |

**既存の文書を直すときの決まり**

- 原本は変えず、別名で保存する
- 書式は既存のスタイルに合わせる。`run.font` で色やサイズを直書きしない。新しい見た目が要るなら、まずユーザーに既存スタイルで足りないか確認する
- 校閲中の文書（`inspect_docx.py` で変更履歴やコメントが1件以上）を直すときは、変更履歴付きで直すかをユーザーに確認する

**文言の置換**

```
python scripts/docx_replace.py <in.docx> <out.docx> --find 旧 --replace 新 [--find 旧2 --replace 新2] [--track 校閲者名] [--dry-run]
```

1. `--dry-run` で一致箇所（場所と前後の文字）を出し、意図しない箇所に当たっていないか見る
2. 本番を実行する。`--dry-run` も置換を手元で順に行うので、件数は本番と同じになる

本文・表・コンテンツコントロール・テキストボックス・すべてのヘッダーとフッター・脚注・文末脚注が対象。`--find` は上から順に適用するので、前の置換結果に後の `--find` が当たると連鎖する（注意が出る）。入れ替え（A↔B）は一時的な文字列を挟んで3回に分ける。

終了コード1で止まったら、出力の理由で分ける。

| 出力 | 対処 |
|---|---|
| 置換 0 件で、置換しなかった一致も無い | 表記ゆれ（全角・半角、スペースの有無）か、段落をまたいでいる。`inspect_docx.py` の本文で実際の表記を確かめる |
| 置換しなかった（タブ・改行・図・脚注番号・フィールドの境目をまたぐ） | `--find` を境目の手前と後ろに分けるか、その箇所だけ手で直すかをユーザーに確認する |
| 置換しなかった（他の変更履歴の挿入の中） | 先にその変更履歴を Word で承諾してもらうか、履歴なしで置換してよいかをユーザーに確認する |

### 3. 見た目を確かめる

作った・直した文書は PDF にして画像で見る。`to_pdf.py` と `pdf_to_png.py` は `operate-pdf` スキルのもの。このスキルの zip に operate-pdf は含まれないので、利用可能なスキル一覧から operate-pdf の実体パスを解決して `<operate-pdf-dir>` を置き換える。未導入なら、使える Office の PDF 出力と画像表示で同じ観点を確かめる。

```
python "<operate-pdf-dir>/scripts/to_pdf.py" <docx> --outdir <作業フォルダ>
python "<operate-pdf-dir>/scripts/pdf_to_png.py" <作業フォルダ>/<名前>.pdf [--pages 1-3]
```

見るもの: 用紙と余白、和文フォント、見出しの階層、表の列幅とはみ出し、改ページ位置、空の段落や記号だけの行、ヘッダー・フッター・ページ番号。

- 文言の置換だけで、置換後の文字数がほぼ変わらないなら、画像は置換した箇所のあるページだけでよい
- 崩れがあれば原因の箇所だけを直して作り直す。2周目以降は直したページだけを `--pages` で出し直して読む
- `pdf_to_png.py` は既定で先頭30ページまでしか画像にしない。それより長い文書は `--pages` で分ける
- 周回の上限（3周）と諦め方は `operate-pdf` の「見た目の確認ループ」に従う

## 完了条件

- 置換は `docx_replace.py` が終了コード0（すべての `--find` が置換され、置換しなかった一致が0件）。`--allow-missing` で書き出したなら、置換しなかった箇所と理由をユーザーに伝えたこと
- 変更履歴付きの置換は、`docx_replace.py` の「変更履歴: 挿入 N・削除 M」が置換した件数と合うこと（削除だけの置換は挿入0）
- 作成・編集したものは、ページ画像に崩れが無いこと。変換エンジンが無く確かめられなかったら（`to_pdf.py` が終了コード3）、構造検査までの結果と「見た目未確認」をユーザーに伝え、完成扱いにしないこと

## 禁止事項

- 原本を上書きすること
- 置換が見つからなかったとき、似た文字列を推測して置き換えること
- 箇条書きの記号（「・」「●」）や段落番号を本文に直接打つこと
- 変更履歴付きで頼まれた修正を、履歴なしで書き換えること

## 参照ファイル

| ファイル | 読むタイミング |
|---|---|
| `references/creating.md` | 新しく文書を作るとき。雛形のコードと落とし穴の表 |
| `references/review-markup.md` | コメントを付ける、置換以外の変更履歴（段落の追加・削除）を付ける、既存の変更履歴を扱うとき |

## スクリプト

依存は `python-docx`（`pip install python-docx`、コメントを付けるなら 1.2 以降）。無ければ終了コード2で止まるので、導入をユーザーに確認する。`scripts/wordml.py` は2本が共有する読み取り部品で、直接は実行しない。

| スクリプト | 用途 | 終了コード |
|---|---|---|
| `scripts/inspect_docx.py` | 構造と本文を Markdown 風に出す | 0 出力した / 1 開けない / 2 引数ミス（無い `--section` 番号を含む）・`.doc`・依存不足 |
| `scripts/docx_replace.py` | 断片をまたいで書式を保ったまま置換する。`--track` で変更履歴付き | 0 全件置換 / 1 見つからない語か置換しなかった一致がある（書き出さない。`--allow-missing` で置換できた分を書き出す） / 2 引数ミス・開けない・入出力が同じ・依存不足 |

置換後の文字は、一致した範囲の先頭の書式になる。段落をまたぐ文字列、削除済みの変更履歴の文字、コメントの中は置換しない。

PDF 化と画像化は `operate-pdf` スキルの `to_pdf.py` と `pdf_to_png.py`（要 `pypdfium2` `Pillow`）を使う。
